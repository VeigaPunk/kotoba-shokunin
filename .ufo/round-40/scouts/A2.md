**Seat question:** is the committed scope set still correct after C1 lands? Does any
row need to enter or leave the set?

**Answers.**
1. **The set is still CORRECT — no row needs to enter, no row needs to leave.** All
   four `omp.catalogue.*` rows remain unreachable from IND's own substrate set; the
   other 24 do not become unreachable under C1.
2. **But the set is not load-bearing in two places**, and C1 as declared closes

   *weakly* held out (a blind builder that guesses nothing but the harness's gate
   lands on the live truth); `omp.catalogue.matched`/`.missing_names` are genuinely
   held out. The four rows' shared `reason` overstates the case for two of them.

## 1. SET CORRECTNESS — HOLDS (no entry, no exit)

### 1a. The four rows are still unreachable from IND's substrate set

IND's docstring names its substrate set: the omp binary, the skill cache, the skill
roots, the opencode log and the opencode configs. I built a blind derivation using
**exactly** those inputs (`.ufo/round-40/drafts/a2/exp-r-blind-e2e.txt`):

```
live truth : {"omp.catalogue.found": true, "omp.catalogue.matched": 7,
              "omp.catalogue.missing_names": [], "omp.catalogue.total": 7}
blindly readable: offered names = 7, cache rows = 14
blind rule picked: 2026-10-15T05:02:56.169Z  -Projects-shokunin-kumitate-shokunin/…
blind derivation : {"omp.catalogue.found": true, "omp.catalogue.matched": 0,
                    "omp.catalogue.missing_names": ["godspeed","omarchy",
                    "reverse-engineer-anything","shokunin","swarm","tower","ufo"],
                    "omp.catalogue.total": 7}
BLIND DERIVATION MATCHES LIVE TRUTH: False
```

So the rows stay out of the join: the substrate set reaches a *different* value.

### 1b. Sub-finding — two of the four rows are only WEAKLY held out

The blocker's shared `reason` says re-deriving the row blind "would be guessing".
That is exactly right for `matched`/`missing_names` and **overstated** for
`found`/`total`. Measured (`exp-t-derivability-split.txt`, `exp-o-blind-derivable.txt`):

```
gate-passing blocks: 534 ; total histogram {7: 533, 34: 1}
distinct totals among gate-passing blocks: [7, 34]
modal total: 7 with 99.8% of gate-passing blocks
the driver's own five blind rules landing on the live truth (7): 3/5
```

A blind builder that guesses **only** the harness's gate (`min(10, len(known))`
entries, which the blocker's own text quotes) lands on `total = 7` — the live truth —
with no rule knowledge at all. `found` is reachable by the weaker guess "any
gate-passing block exists". Only `matched`/`missing_names` need the *selected* block,
and those are genuinely held out.

This does not make the scope-out false — the probe's falsifier ("a single distinct
total across every blind-plausible rule") is not met, and the row *is* underivable
when the gate is not assumed. It means **the row split is real and the shared
`reason` string should say so**: `found`/`total` are held out by the *gate's
indeterminacy*, not by the selection rule. Filed as a documentation-accuracy item,
same class as r39 R1's F-9.

## 2. THE TWO ESCAPE ROUTES (the substantive findings)

### F-A2-1 (HIGH) — a flat payload bypasses the scope path entirely

`parse_independent` falls back to a flat dotted map, and tries `checks`, **`expected`**,
`re_derived`, `observations` in that order (`compare_harness_independent.py:279-283`
at `bb8dcecd`). A payload of the form `{"expected": {<id>: value}}` therefore joins
**all 28 rows** — including the four scoped ones, on values harvested from the
harness's own stdout — and the committed scope file is never consulted:

```
$ python3 verifiers/compare_harness_independent.py --live-json <live> --independent-json <flat>
  D1 flat {"expected": harvest}                  exit=0  n=28  all checks agree
  D3 flat {"checks": harvest}                    exit=0  n=28  all checks agree
  D4 flat {"observations": harvest}              exit=0  n=28  all checks agree
  D5 flat {"expected": harvest} + --expect-n 28  exit=0  n=28  all checks agree
  E1 CONTROL flat minus catalogue ids            exit=2  uncovered checks
  E2 CONTROL flat with a wrong value             exit=1  disagreements
```

Controls prove the branch is otherwise honest (uncovered ids and divergent values are
still caught) — the hole is specifically that the flat form has no scope channel at
all, so a scope-out cannot be *committed* against it.

**It survives C1 as declared.** C1's (a) says "drop `expected`/`expected_value` from
`IND_VALUE_KEYS`" — that is the *record* key list, not the flat-map key list at
`:279`:

```
  D2 flat {"expected": harvest} under simulated C1  exit=0  n=28  all checks agree
```

The two lists are separate literals; patching one does not close the other. Also note
`--expect-n 28` does not catch it (D5), because the flat payload legitimately carries
28 ids.

**Proposed minimal patch** (one list, one branch):

```python
FLAT_MAP_KEYS = ("checks", "observations")      # drop "expected"/"re_derived"
```
and, in the flat branch, refuse any key whose name is a value-channel name the live
IND never emits; or simplest: drop `expected`/`re_derived` from the flat key list too.
A payload that can only speak in the derived channels cannot hand the driver the
harness's own numbers as if they were a re-derivation.

### F-A2-2 (HIGH) — the probe's `target` is payload-chosen, not committed

`load_scope_file` validates each entry's `reason` and `kind` and returns the
`probe_contract`; `check_scope_probes` enforces the contract's **`kind`** field
(`:595-600`). Nothing pins the probe's **`target`**. `recompute_probe` recomputes the
census over whatever absolute path the *payload* names, then compares the result to
the *payload's own* declared observable:

```
$ python3 verifiers/compare_harness_independent.py --live-json <live> --independent-json <re-aimed>
  honest (real carrier)                exit=0 n=24  all checks agree
  probe re-aimed at fabricated dir     exit=0 n=24  all checks agree
```

The fabricated directory is a `/tmp` tree I created with two `<skills>` blocks whose
five blind-plausible rules disagree (`distinct_totals [1, 3]`) — a truthful census of
a surface with nothing to do with the catalogue. The full red→green flip
(`exp-f-launder.txt`), where the instrument's carrier is a surface on which the row
*is* derivable blind:

```
--- BEFORE (honest probe on the carrier the instrument was given) ---
  honest  (row IS derivable blind)         exit=2  false blocker: … every blind-plausible
                                                    rule agrees on one total [2] …
--- AFTER (same payload, probe re-aimed at a fabricated surface) ---
  re-aimed (false blocker laundered)       exit=0  all checks agree, both instruments green

BEFORE exit=2  AFTER exit=0  -> flip red->green: True
only the probe block changed; every check value is byte-identical: True
```

So the lock that R1's F-1 declared decisive ("a **recomputed** probe the driver runs
itself") recomputes against a surface the payload selects. The committed file is a
ceiling on *which rows* may leave the join, but the evidence corroborating each
row's blocker is still supplied by the thing under test. This is the same class as
r38 R1-D1: a self-declaration that the driver accepts because it cannot reach the
committed truth.

**The receipt does not close it either.** `scope_locks` records the committed set and
the probe kind — and nothing else:

```
"scope_locks": {"committed_set": ["omp.catalogue.found", …],
                "probe_kind": "rule-spread-census"}
does the receipt name any probe TARGET? False
```

**Proposed minimal patch** (one field per entry, one check):

```json
"omp.catalogue.found": {"kind": "rule-in-author-scope", "reason": "…",
                        "probe_target": "/home/vgpnk/.omp/agent/sessions"}
```
then in `check_scope_probes`, after the kind check:
```python
want = committed[cid].get("probe_target")
if want and probe.get("target") != want:
    problems.append(f"false blocker: scoped row {cid} probe target {probe.get('target')!r} "
                    f"is not the committed target {want!r}")
```
and add `probe_target` to `scope_locks` in the receipt. This is a small change and it
is the one that makes the committed file actually load-bearing rather than a
ceiling on a self-serve channel.

### F-A2-3 (MEDIUM) — the per-record probe channel is unread (R1 F-3's shape, one channel over)

The driver prefers the top-level `scoped_out_probes` map and falls back to
per-record `probe` blocks, but never cross-checks the two. A payload whose top-level
probes are honest while its per-record probes point elsewhere still reads exit 0:

```
  B3 record-channel probe divergent   exit=0  n=24  all checks agree
```

Same class as R1's F-3 (`_record_list` reads the first of `results`/`rows`/`checks`),
which C1's (b) is closing for values. **Recommendation:** whatever cross-channel
reconciliation C1 lands for values should cover the probe channel too — otherwise
the fix closes F-3's value shape while leaving its structural twin open.

### Controls (the locks that DO work)

```
  A1 live IND payload, live driver      exit=0  n=24  all checks agree
  B1 scope_out emptied (rows still null) exit=2  "scoped_out is present but empty"
  CONTROL all-rules-agree carrier       exit=2  "false blocker: … derivable without
                                                 reading the harness's rule"
  CONTROL truncated top-level probes    exit=2  "false blocker: … carries no probe block"
  E1 flat minus catalogue ids           exit=2  uncovered checks
  E2 flat with a wrong value            exit=1  disagreements
```

The lock reacts correctly to the target *content* (an all-agree carrier fails closed)
and to a missing probe; the hole is specifically the missing *binding* between the
committed entry and the target path (F-A2-2) and the missing scope channel in the
flat form (F-A2-1).

## 3. LANDING CONSTRAINTS FOR C1 (measured, so the fix is not built against a guess)

1. **Reconciliation must be by VALUE, not by record.** IND's three channels are
   *not* record-identical by design (`exp-a-channel-reconcile.txt`):
   ```
   results[i] == rows[i] byte-equal: False
   key-set symmetric difference results vs rows: ['evidence', 're_derived']
   records that differ at record level: 28/28 -> a naive reconcile FAILS live
   records that differ at value level: 0/28
   checks carries no status: True   (bare {id: value} dict, no status/probe)
   ```
   A C1 implementation that reconciles `results` vs `rows` as dicts will fail the
   live payload. It must compare `results[k]['re_derived']` vs `rows[k]['value']` vs
   `checks[k]`.
2. **`checks` carries no `status` and no `probe`.** Any reconciliation that expects
   a status field on every channel will fail live. Scoped rows appear in all three
   id sets with `None` — that is the legitimate shape:
   ```
   omp.catalogue.found  results.re_derived=None rows.value=None checks=None
                        (status SCOPED_OUT in both record channels, absent in checks)
   ```
3. **A committed row cannot escape as UNLANDED-empty** — measured:
   ```
   committed rows emitted UNLANDED-empty  exit=2  "scoped_out is present but empty"
   ```
   (that arm tripped the empty-declaration guard; the value channel alone is not
   enough to hide a committed row).
4. **The four scoped rows must keep their probe blocks in BOTH channels.** The driver
   reads `scoped_out_probes` first; the per-record channel is the fallback. A C1
   change that drops either would fail closed on the live payload (B2/CONTROL above).
5. **F-2/F-3 flip under C1 as declared** — this seat reproduced R1's numbers and
   confirms the declared after-text is achievable (`exp-l-C1-F2F3.txt`,
   `exp-m-flatmap-and-f2.txt`):
   ```
   C1 F-2 faithful (harvested expected)   exit=0  -> under sim C1  exit=2  channel split
   C2 F-3 rows-shadow (results clean)     exit=0  -> under sim C1  exit=2  channel split
   ```

## 4. VERDICT FOR THIS SLICE

**The committed scope set is still correct after C1: no row enters, no row leaves.**
The four `omp.catalogue.*` rows remain out of the join, the other 24 remain in it,
and the live payload still reads 24/24 exit 0 under a simulated C1.

**But the audit says the file is not yet the lock it is described as.** Two
independent payloads reach exit 0 without the committed set constraining them —
a flat `{"expected": …}` payload that never enters the scope path (F-A2-1), and a
re-aimed probe target (F-A2-2). Both are one-list / one-field fixes. Neither is
closed by C1 as its text is currently written. Until at least F-A2-1 is closed, the
headline "24/24 over the landed scope" can be produced by a payload the scope file
never saw.

**Recommendation to the integrator:** C1's claim text should be widened by one line
— "the scope set must be load-bearing on *every* accepted payload shape" — or F-A2-1
should be filed as its own claim; and the `probe_target` field (F-A2-2) is the
cheapest single change that makes the committed file do what its `why` says it does.
