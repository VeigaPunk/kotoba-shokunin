### Shape 3 — a fenced block whose opener is indented 4: is that even a fence?

**No.** Per CommonMark 4.5 an opening fence may be indented at most 3 spaces;
4+ columns is indented code. cmark confirms:

```

  <code_block sourcepos="1:5-1:8" xml:space="preserve">````
</code_block>
  <paragraph sourcepos="2:1-3:8">
```
— a one-line indented code block containing the fence text, then the row as an
ordinary paragraph (i.e. **live**, a real promise).

* `pre-c3` and `live`: both gates read the 4-indent line as an opener and treat
  the region as fenced → the row is **not** harvested. cmark says live, so this is
  **OVER-STRICT** (a loud false fail, not a silent pass) — the `B1` arm.

* `mid-r40` (F2): correct, agrees with cmark.
* Note the interaction with shape 3's own container reading: `B2` (opener at 4

## 2. New family found by this seat — Unicode / `str.splitlines()` tails

Not in any prior scout report I could find; same silent-false-PASS class.

Both corpus gates read the README with `read_text().splitlines()`
(`verify_corpus_integrity.py:364,400`; `verify_corpus_independent.py:264`) and test
the closer's tail with `not m.group(2).strip()` (Unicode-aware). cmark accepts
**only ASCII space/tab** after a closing fence. Two independent divergences:

**(a) Unicode whitespace in the tail.** cmark treats `\xa0` (NBSP), `\u2000`
(EN QUAD) and `\u3000` (IDEOGRAPHIC SPACE) as *content*, so the line is not a
closer and the region stays open; Python's `strip()` removes them, so both gates
read the line as a legal closer:

```
$ printf '````\n````\xa0\n| Quoted | `knowledge/b.md` | basis |\n````\n' | cmark --sourcepos -t xml
  <code_block sourcepos="1:1-4:4" xml:space="preserve">````
| Quoted | `knowledge/b.md` | basis |
</code_block>
```

End-to-end, at `mid-r40`: `C3` (NBSP), `C4` (EN QUAD), `C5` (IDEOGRAPHIC) are
**silent false-PASS on both gates** (`i:0/0 d:0/0`, row harvested, cmark says
content). The same family survives **all three revisions** — r39's C3 fix and
F2's cap both leave it untouched, because neither changes `strip()`.

**(b) `splitlines()`-only line separators.** `str.splitlines()` splits on
`\x0b` (VT), `\x0c` (FF), `\x85` (NEL), `\u2028` (LS), `\u2029` (PS); cmark does
not. A tail of `\x0c` therefore becomes a *line break* to the gates and a
**bare, perfectly legal closer** appears:

```
$ python3 -c "print(repr('\`\`\`\`\n\`\`\`\`\x0c\nrow\n\`\`\`\`\n'.splitlines()))"
['````', '````', '', 'row', '````']       # the \x0c becomes an empty line
```
— the second element is now ` ```` ` with an empty tail, which closes the region
early. cmark sees one 4-line block. End-to-end at `mid-r40`: `C6`–`C9` are
**silent false-PASS on both gates**. Same on `pre-c3` and `live`.

**Live incidence: 0.** Corpus sweep (`out/CORPUS-SWEEP.txt`): 53 docs, 146
fence-like lines, `tab_in_indent=0`, `indent_ge4=0`, `tail_unicode_space=0`,
`tail_splitlines_char=0`, `blockquote_fence=0`. Debt with a working exploit.

## 6. My own defects (disclosed, not smoothed)

1. **Inverted verdict polarity, twice.** My first unit classifier mapped
   `gate_opaque` and `cmark_content` the wrong way round, which reported the
   `pre-c3` exploit shapes as "agree" — a **false green on the very defect I was
   hunting**. I caught it when a plain-fence control read as an exploit; both wrong
   runs were discarded, not kept. The second inversion was on the checklist
   column (`inside` = content, not opaque). Fixed in `classify()` with the
   polarity written out in the docstring.
2. **Line-numbering confound.** My unit harness fed `\n`-split lines to
   instruments that call `str.splitlines()`, so the C6–C9 family compared line
   numbers cmark never sees. This produced a whole matrix of meaningless
   "UNDER-OPAQUE" readings. Fixed by feeding the `splitlines()` view and locating
   the row in *that* numbering.
3. **Proxy-vs-pipeline confound.** My first unit harness inferred "harvested" from
   "not in the fence set". That is wrong for any line a gate declines for a
   non-fence reason (indentation, `>` prefix), and it is what made the container
   arms read inconsistently between my two probes. Fixed by calling each gate's own
   harvest function (`file_column_tokens`/`fenced_lines` and `coverage_cells`).
4. **A container-probe bug.** My first `container_family.py` used
   `line.startswith("|")` on the raw line to locate the row, so 4-space-indented
   rows were missed entirely and every container shape reported `live`. Fixed to
   `ROW in line`.
5. **`container_e2e.py` format-string bug** (4 revisions vs a 3-column format
   string) crashed on the first 4-rev run; fixed with generic column building. The
   crashed run is in the transcript, the fixed run is the saved receipt.
6. **My candidate mutant had a group-index bug** on the first write (I widened the
   regex to 3 groups but left the body reading `group(1)`/`group(2)`). Caught by
   `py_compile` plus a 3-shape smoke test before any number was used.
7. **Seat-brief premise correction.** The brief says the "r39 container-relative
   change" might interact. There is no such change in the corpus gates: r39
   (`df0e6e1`) touches only `verify_corpus_*.py`'s fence predicate, and the
   container model lives in `verify_skill_checklist.py` (r37, `c8e233d`). I
   measured the gates directly rather than assuming the brief's premise.
