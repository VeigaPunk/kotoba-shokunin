# X2 | probe-channel-extra — channel-agreement bypasses the C1 builders might miss (round 40)

**Question:** do the *other* channel relationships bypass the C1 closure — a
`results` list that is a strict subset of `rows`, per-row `status` fields
disagreeing across channels, a `checks` map with extra keys `results` lacks,
numeric-vs-string type confusion (999 vs `'999'`)?
**Answers:** on the **frozen r39 driver** (`bb8dcecd`) **all four families
bypass** (30/46 shapes reach exit 0). On the **landed r40 driver**
(`698ad2d5`, seat P2's reconciliation) three of the four families **fail
closed**, and the fourth — intra-record key precedence — **survives**: a
channel-consistent full copy reads **exit 0, 24/24, even under
`--strict-headline`, with `"NOT DERIVED"` in every derived field**. The C1
seat's own `expected-launder` fixture is landed **red** and agrees with me.

The tree moved repeatedly under this seat — I measured **eight distinct driver
blobs** (`bb8dcecd` → `727ec676` → `488215e9` → `5ef6a2ec` → `22acd08f` →
`2daeee7a` → `aa823387` → `698ad2d5`); every number below names the driver sha
it was measured at, and every battery run is **bracketed** by the unmutated
control (exit 0 at both ends of the window) so a stale capture cannot
masquerade as a rejection. That bracketing turned out to be necessary, not
decorative — see F-6.

## THE SURVIVING CLASS — intra-record key precedence (F-2, HIGH)

### S-1 `expected` still outranks the derived channels

`IND_VALUE_KEYS = ("expected", "expected_value", "re_derived", "value",
"observed")` (`:131` at `698ad2d5`) is consumed per record as
`vkey = next((k for k in value_keys if k in record), None)` (`:304` at
`698ad2d5`). The cross-channel
reconciliation compares **channels**, so a divergence *within one record* is
invisible to it.

Mechanism, via the driver's own parser:

```
$ python3 proof-f2.py            # at 2daeee7a; re-verified at 698ad2d5
IND_VALUE_KEYS: ('expected', 'expected_value', 're_derived', 'value', 'observed')
record:  {"check": "a.b", "expected": 7, "re_derived": "NOT DERIVED",
          "value": "NOT DERIVED", "status": "DERIVED"}
parse_independent -> {'a.b': 7}       # the harvested value, not the derived one
```

Full-copy arm (`n6-channel-consistent-copy`, rebuilt at 12:45:41 from the
window captures — all four bracketed windows captured byte-identical payloads,
`ind.json` sha256 `cca49e2d…`, so the attribution is unambiguous; payload
sha256 `abdb97d65d3a5074`; every one of the 24 joined rows carries the
**harvested live value** in
`expected`/`expected_value`, `"NOT DERIVED"` in both derived fields, and every
published channel agrees so the reconciliation passes):

```
12:45:41 control legit: exit=0  24/24
         n6 full copy: exit=0  24/24  reason: all checks agree, both instruments green
         n6 full copy --strict-headline: exit=0  24/24 (strict column)
12:45:55 control legit: exit=0  (window held)
```

Channel-level parse of the same payload (`omp.offered.skills`):

```
results: {"expected": 7, "expected_value": 7, "re_derived": "NOT DERIVED",
          "status": "DERIVED", "value": "NOT DERIVED"}
rows:    {"value": 7, "status": "DERIVED"}
checks:  7
parsed channels: results=(7,'DERIVED')  rows=(7,'DERIVED')  checks=(7,None)
```

All three channels agree on `7` — the reconciliation is satisfied — and the
join reads the **harvested** `7` while the record's own derivation says
`"NOT DERIVED"`. Zero derivation, full agreement, exit 0. This is R1's r39 F-2
reproduced against the r40 landing.

**The C1 fixture agrees with me.** `verifiers/fixtures/…/expected-launder`
declares exit 2 and reads **exit 0**; `--self-test` reports 3 failures
(exit/names/named-failure) and the floors guard fails
`compare_harness_independent observed=118 floor=118 self_test_failures=3`.
The fixture's own `why` field names the reason the C1 seat already understood:
*"The disagreement is WITHIN the record (foreign key vs derived keys), so a
closure that only reconciles the three channels against each other still
misses it."* That prediction is correct, and the landed fix is exactly the
three-channel reconciliation it describes.

### S-2 `status` vs `state` in one record (same class, one field over)

`status = record.get("status", record.get("state"))` (`:309`, `:561` at
`698ad2d5`) reads
`status` when present and never compares it to a sibling `state`. A record
carrying `status: "DERIVED"` and `state: "UNLANDED"` parses as DERIVED:

```
$ python3 - <<'EOF'
import sys; sys.path.insert(0, "verifiers")
import compare_harness_independent as d
rec = {"check": "a.b", "value": 7, "status": "DERIVED", "state": "UNLANDED"}
d.parse_independent({"results": [rec], "rows": [{"check": "a.b", "value": 7, "status": "DERIVED"}],
                     "checks": {"a.b": 7}}, st := {})
print(st)   # -> {'a.b': 'DERIVED'}
EOF
{'a.b': 'DERIVED'}
```

Probe `x3-status-vs-state` reads exit 0 at `698ad2d5` (and at `bb8dcecd`).
Severity is lower than S-1 only because the live IND emits `status` alone
(`grep -c '"state"' verify_harness_independent.py` → 0), so the key is
payload-supplied; but the same argument applies to `expected`, which the live
IND also never emits.

## F-6 — the frozen-capture trap (operability, mine)

Mid-round, my own frozen captures went **stale**: the probe census reads the
live session tree, which sibling seats are growing. Measured:

```
$ python3 probe-stability.py      # 12:35, frozen captures
declared == recomputed: False
  session_files: declared=763 recomputed=764      <- one new session file
=> the legit payload then reads exit 2 ("false blocker") on every driver
```

A frozen `--independent-json` capture therefore has a **shelf life of minutes**
when the tree is active, and every `exit 2` on a stale capture is an artifact.
All four of my battery columns were re-measured in fresh windows **bracketed by
the unmutated control** (exit 0 at both ends) after this was found; the raw
pre-bracket runs are kept but marked superseded (`battery-*-driver.txt` vs
`battery-*-window.txt`). This is worth recording for the C1 counting clause:
"the live comparator still exits 0 24/24" must be measured on a *fresh*
capture or with the live path, not on a frozen fixture of a moving tree.

## MY OWN DEFECTS (disclosed)

1. **Two probe bugs produced false readings before I caught them.**
   (a) my first `n5` full-copy mutated the legitimately-empty `oc.dup.*` rows
   to `"NOT DERIVED"`, and the driver rejected the payload for an unrelated
   membership reason — a false "closed". Rebuilt as `n6` (numeric rows only,
   channel-consistent) and kept both.
   (b) `x13c` initially assumed a 1-valued row exists (it does not); rewritten
   as `False`-vs-`0` on a real row.
2. **My first frozen-capture batteries were silently invalid** once the session
   tree grew (F-6). I only found this by re-running the legit control, which
   read exit 2. The pre-bracket columns are kept but marked superseded; the
   report's numbers are the bracketed ones.
3. **I ran one battery while a sibling was mid-write** (`488215e9`): 13 exit-0
   shapes that included shapes the fix closes — a false "the fix didn't work"
   reading. Discarded and re-measured after the file settled; the `NameError`
   crash state (`5ef6a2ec`) is also on record.
4. **`x4d`'s mechanism note was wrong on first write** ("control"); corrected
   in place — it is a live bypass via the record-level probe fallback.
5. **My `floors` reading was initially taken through a pipe** (`cmd | tail`),
   so `$?` measured `tail` and reported 0 — twice, once even after I wrote the
   defect down. Re-run directly (`> /tmp/floors.txt; echo $?`): the guard
   **exits 1** at `698ad2d5` with
   `FAIL compare_harness_independent observed=118 floor=118 self_test_failures=3`.
   The report's floors line is the direct reading.
6. **The background task rewrote the shared capture/probe files while a
   foreground run was reading them** — I stopped it and re-ran serially. Two
   windows (`pA`/`pB` first pass) were discarded for this reason.
