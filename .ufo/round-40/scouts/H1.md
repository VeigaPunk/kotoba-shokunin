## 2. What a drop breaks (measured on copies, never the live tree)

A literal drop (`IND_VALUE_KEYS` → `("re_derived","value")`) does **not** merely red
the driver's self-test — it **crashes** it, because the first `expected`-keyed arm
sits outside any `try/except`:

```
$ python3 drafts/h1/variants/v1-drop-tuple.py --self-test
  File ".../v1-drop-tuple.py", line 1033, in self_test
    check("independent: results list", parse_independent(ind_records) == ...)
CompareError: independent: record a.b carries no value (keys ('re_derived','value')):
              {"check": "a.b", "expected": 1}
```

The guard does catch it — `check_assertion_floors.py --script
compare_harness_independent=<variant>` → `FAIL … observed=0 floor=97
summary=missing`, **exit 1** — so a dropped tuple cannot land silently. But the
self-test must be repaired in the same change.

Consumer count, measured by iterating the crash (`drafts/h1/drop-consumers.txt`):
**4 in-process crash sites** (self_test lines 1032, 1056, 1167/1168) then **21 CLI/receipt
arm failures** whose stubs also feed `expected`/`observed`. The two arms at `:1052`
(nested `expected` map) and `:1056` (`observed` record key) are *semantic* — they
**certify the very doors the fix closes** and must be inverted, not renamed.

## 5. Feasibility of the reconciliation arm (P1's (b))

`drafts/h1/reconcile-experiment.py` + `reconcile-consumers.txt`:

* **The live IND payload is already channel-consistent under `canon()`** — measured
  `results == rows == checks` on all 28 ids (raw equality; they are the same values
  copied into three channels). So reconciliation does **not** red the live join —
  v4/v5 both read **exit 0, 24/24** on the real instruments.
* **Strict `canon()` equality is the right rule, and it is not what I first wrote.**
  The IND's three channels agree *raw* on the live payload (all 28 ids), so strict
  reconciliation is safe live — measured: v4/v5/v6 all read **exit 0, 24/24** on the
  real instruments. My first reconciliation variant red the live join because it
  compared channels across *differently-rendered* payloads I had built, not because
  the rule was wrong. I also built the weaker rule (channels agree if `canon`-equal
  **or** both empty) as `variants/v7-empty-equiv.py`: it passes the whole battery
  too, but on `r10-representation-only` — `results=0` vs `rows=[]` for one id, the
  same quantity in two renderings — **v6 exits 2 and v7 exits 0**. The live IND
  publishes the *same* value in all three channels, so `0`-vs-`[]` between channels
  is a payload artifact, not a rendering the instrument produces; **v6's strict rule
  is the correct and safer one**, and v7 is recorded as the weaker variant it is.
* **Exactly one self-test arm must change** to a reconciliation fix: `:1048`
  (`"rows preferred over a sibling checks map"`, which asserts read-first as a
  *feature*). Patching only that arm takes the reconciliation variant's self-test
  from crash → `0 failure(s) over 97 assertions`.
