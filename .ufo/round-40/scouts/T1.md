## 2. Why two layers, and what each one can and cannot see

The live join exercises only the happy path. The live IND emits **no `expected`
key at all** (measured: key histogram over its 28 `results` records is
`{check, re_derived, status, value}` plus `probe` on the 4 scoped rows), and its
three channels agree on all 28 rows. So R1's F-2/F-3 live in code paths the live
input never reaches — **a live-only regression read cannot see a candidate
driver that changes them.**

I measured this rather than asserting it. Six single-anchor mutants of the frozen
HEAD driver, run through layer 1:

```
m-zero-the-numerator   rc=1  caught  [headline, agreement-block]
m-drop-one-scope       rc=1  caught  [exit, reason, scoped_out, row-removed ×24]
m-fix-shrinks-agreement rc=1 caught  [headline, agreement-block, row-removed]
m-drop-expected-key    rc=0  NOT caught  (live input carries no `expected`)
m-drop-observed-key    rc=0  NOT caught  (same)
m-read-first-rows      rc=0  NOT caught  (live channels agree, so first == all)
m-flip-adjudication    rc=0  NOT caught  (live rows are all mode `equal`+DERIVED)
```

So layer 1 catches behaviour changes; layer 2 (the ledger) catches channel
changes. Neither alone is sufficient.

## 5. The constraint C1 must satisfy — the driver's own self-test pins F-3 as correct

`compare_harness_independent.py:1047`:

```python
check(
    "independent: rows preferred over a sibling checks map",
    parse_independent({"checks": {"a.b": 99}, "rows": [{"check": "a.b", "value": 1}]}) == {"a.b": 1},
)
```

This asserts read-first as the **contract**, and the module docstring's interface
contract says the same. So closing F-3 cannot be done by changing `_record_list`
alone: the self-test and the docstring must change in step, or the self-test goes
red and `check_assertion_floors.py` trips. Measured on my candidate: the
self-test fails at exactly this arm (25 ok, then
`channel divergence for a.b: checks=99 but rows.value=1`). My candidate rewrites
the arm to assert the payload *fails closed* and adds an agreeing-channels arm
(97 → 98 assertions); floors must be bumped in step
(`compare_harness_independent` floor is currently **97**, live 8/8 EXACT).

A second, related constraint: an aggressive rule that rejects `expected`-only
records breaks the self-test's documented shapes (`ind_records` at :1032 and the
`nested expected map` arm at :1051 both use `expected` as the value key). The
F-2 payload is distinguishable because it carries `expected` **alongside** derived
channels reading "NOT DERIVED" — a cross-check there is sufficient and leaves the
documented shapes intact. My first candidate rejected `expected`-only and crashed
the self-test; that wrong version is in the draft history.

## 6. NEW residual (mine) — a duplicate id within one channel is last-write-wins

Found by cross-checking my candidate against **V2's** independent battery
(`.ufo/round-40/drafts/v2/f3-battery.py`, arms A7/A8) rather than trusting my own
ledger. `parse_independent` does `out[cid] = record[key]`, so a duplicate id is
resolved by position:

```
$ (payload: omp.offered.skills appears twice in `results`, 999 first, honest 7 last)
divergent-first  vals=[999, 7]  HEAD exit=0 24/24   candidate exit=0 24/24   <- INVISIBLE
divergent-last   vals=[7, 999]  HEAD exit=1 23/24   candidate exit=2          <- caught
```

The attacker picks the ordering, so the divergent value is silently discarded
and the join reads 24/24 exit 0. This is a **third door in the F-2/F-3 family**,
not covered by R1's findings, by my A/B/C payloads, or by the cross-channel
reconciliation (which compares channels, not duplicates *within* one). It is
**open on the frozen HEAD driver and on my candidate**. Filed as ledger payload
**E**, reported in every suite verdict, deliberately **not gated** — it is open
on HEAD too, so gating on it would fail every candidate including a correct one.

## 9. My own defects (disclosed, not smoothed)

1. **First payload A was malformed.** I rebuilt every record from the live
   observed map and stripped the scoped records' `status`/`probe`, so the payload
   died on scope validation (`scoped_out names omp.catalogue.found but its status
   is 'DERIVED'`) instead of exercising the launder. It read exit 2 and I nearly
   filed it as "closed" — that would have been a false-green. Fixed to keep
   scoped records intact; both runs are in the draft history.
2. **`exit 2` fail-closed states were swallowed as harness errors.** My first
   `state_from_run` raised `HarnessError` on a no-stdout exit 2, so the
   `drop-one-scope` mutant read as a harness crash (`rc=2`) rather than as drift.
   Fixed: a fail-closed rejection is now a *state* (recorded with its class line),
   and that mutant now registers 31 named changes including 24 `row-removed`.
3. **`--report -` does not write to stdout** — the driver treats `-` as a path.
   My first version used it and would have produced a file literally named `-`;
   caught before any measurement. Now `--report` to a temp file, so the JSON and
   the row table come from **one atomic invocation** and cannot disagree.
4. **First candidate rejected `expected`-only records**, crashing the driver's
   self-test at assertion 1032 (uncaught `CompareError`, not a clean failure).
   Too aggressive; narrowed to the cross-check that the actual F-2 payload
   requires. Kept as a disclosed negative.
5. **First candidate's reconciliation walked only the two list channels**, so
   payload C (`checks` dotted map) still read exit 0 — I reported "A and B close,
   C open" from that run rather than claiming the set closed.
6. **Known blind spot in layer 1, measured not assumed:** the driver's markdown
   truncates cells at 72 chars (`show(..., limit=72)`), so a difference confined
   to the tail of a >72-char value would not register as a row change. Longest
   live cell is **68** and the longest raw IND value is **66** — zero exposure
   today, and the harness prints `max_cell` every capture so a future >72 value
   is visible rather than assumed safe.
7. **Layer 1's four uncaught mutants are a limitation, not a claim of coverage.**
   Section 2 lists them explicitly.
8. **A `rc=$?` after a pipe measured `tail`, not python.** My first capture of
   the landed state printed `EXIT=0` for a floors run that actually exits 1
   (the `FAIL ... self_test_failures=9` line was on screen next to it). Caught
   when I re-ran without the pipe; `POST-LANDING.txt` carries the corrected
   `REAL_EXIT=1` / `SELFTEST_EXIT=1`. Same class as the `rc-after-tee` bug V3
   disclosed in r39.
9. **The section-5 constraint was measured on my candidate, not on the landing.**
   I claim the self-test pins read-first at :1047 on the frozen HEAD bytes — that
   is measured. I do **not** claim C1 hit that exact arm; the landing's 9 failures
   are in the new fixture battery, and whether C1 also rewrote the :1047 arm is
   visible in its own diff, not measured here.
