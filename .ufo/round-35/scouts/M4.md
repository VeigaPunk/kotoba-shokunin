# Scout M4

## Task
Red probe: pins sha drift. Does `verifiers/check_substrate_pins.py` (sha `bcfd5230…`, baseline `80949255…`) catch a moved substrate pin at HEAD 48a0720, and can a drifted pin still read green? Read-only repo; every baseline copy on `/dev/shm/m4probe` (`TMPDIR=/dev/shm`; `/tmp` 80% full). Only this fragment written.

## Commands
- `python3 verifiers/check_substrate_pins.py` / `--json` ×2 / `--self-test`; `check_assertion_floors.py`.
- Pin-side drift on baseline copies: omp sha `0`*64; opencode sha `f`*64; both; swapped shas; 1-nibble edit; r18 baseline replayed (`git show 02302c5:verifiers/baseline.json`); trailing `\n` on the sha value; `--json` agreement.
- Binary-side: full `cp` of the live 254 MB omp, then one mid-file byte flipped; symlink to it; fixture `mini.bin` pinned-to-itself then moved.
- Silent-accept probes: comma-decimal mtime pins (9/15 digits, ±0.9 s / ±0.999999999 s / +1.0 s on a fixture binary, dot vs comma paired); duplicate JSON keys (stale-first/live-last and the reverse); `_v2` / `-binary-` key shapes; `--repo` on a fully drifted `git archive` tree; FIFO and `/dev/zero` as `--omp-binary`.

## Findings
- **Drift is caught, on both sides, non-tautologically.** omp / opencode / both-drift / swapped shas / 1-nibble → exit 1 naming each pin (`DRIFT n/3`), other pins still PASS; `--json` `exit_code` agrees. The byte-flipped copy of the live omp → exit 1 (`got=681d5c53…`), so the real bytes are hashed, not a cached digest. r18 replay → exit 1 on sha and mtime (red-before reproducible).
- Live: `OK 3/3 pins hold`, mtime `delta 0 ns (tolerance 0 ns)`; text and `--json` byte-identical across runs (`82468d25…` / `890de993…`); self-test `0 failure(s) over 62 assertions`; floors 6/6, `pins 62/62`.
- **New M4-1 — comma-decimal mtime pin silently weakens the pin.** `FRAC_RE = \.(\d+)` (`:110`) only sees a `.` fraction; `fromisoformat` accepts `,` but then the fraction is dropped from `frac_ns`. `2026-10-16T05:15:11,226207850-03:00` → `(…11_000000000, tolerance 999999999)`, reported as `PASS … delta 226207850 ns (tolerance 999999999 ns)`. On a fixture: dot pin rejects +0.9 s and +0.999999999 s; the comma pin accepts both. A 15-digit comma fraction is accepted where the dotted form is `BAD_PIN` 3.
- **New M4-2 — duplicate keys resolve last-wins silently.** `{"omp_binary_sha256": "0"*64, "omp_binary_sha256": <live>}` → exit 0 `OK 3/3 pins hold`; the reverse order → exit 1. Same for opencode. No duplicate-key diagnostic anywhere; a stale pin left in the block is invisible if the live value is appended after it.
- `--repo` plumbing works: a `git archive` tree with both shas drifted → exit 1 (2/3); missing baseline → exit 3 `NO_BASELINE`; explicit `--baseline` wins.

## Defects
1. **M4-1 (medium, freshness):** comma-decimal mtime pin is accepted with a ±1 s window instead of ns-exact — a ~0.9 s binary move passes. The pin's stated precision is silently discarded; only the `.` form carries it. (The self-test's `tolerance 999 ns` assertion covers the dot form only.)
2. **M4-2 (low-medium, freshness):** duplicate JSON pin keys are not detected; last-wins, so a stale-then-live duplicate block reads green.
3. **Carried, still open (r30 D2 / r32):** a sha value with a trailing `\n` passes `SHA_RE` (`$`) → `DRIFT` exit 1, not `BAD_PIN` 3, and the FAIL line carries a raw newline (`…64-hex\n got=…`) — two tiers for one malformation class.
4. **Carried, still open (r30 D3):** `omp_binary_sha256_v2` / `omp-binary-sha256` with a bogus value → exit 0, key absent from output, against the docstring's "never a silent skip".
5. **Carried, still open (r30 D1):** no automated caller runs live mode. On the fully drifted `/dev/shm/m4tree`, `check_assertion_floors.py --repo` prints `PASS pins observed=62 floor=62` and exits 0 while live mode on the same tree exits 1 `DRIFT 2/3`.
6. **LOW (robustness):** a FIFO or `/dev/zero` as `--omp-binary` hangs `sha256_of` forever (no size/type cap; `timeout 4` → 124). Not reachable from the pinned paths, but the read loop is unbounded.

## Limits
- The live omp is 254 MB; only one full copy was made (on `/dev/shm`), and the drift on it is a single mid-file byte flip, not a real rebuild.
- Comma/duplicate probes are hand-edited JSON; whether any producer (`verify_harness_claims.py`, a re-pin script) can emit them was not traced.
- Not probed: Unicode-digit offsets, mtime pins on opencode beyond one bogus value (→ exit 1 as expected), and `--json` behaviour under the FIFO hang.
- Concurrency: an integrator merge (`UU LOG.md`, `A README.md`) was in the index mid-run; both guard files stayed byte-identical to `HEAD` (`bcfd5230…` / `80949255…`) and every number above was measured against those bytes. No git mutation issued here.
