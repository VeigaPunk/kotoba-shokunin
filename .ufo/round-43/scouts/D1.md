## Verdict

**P1 must bind the canonical independent value set before the scope-out is applied.** The comparator accepts several independent value-map representations and does not constrain their key sets against the committed scope-out set. A valid map can therefore carry values for committed scope-out IDs without declaring those IDs scoped out; the scope checks validate payload declarations, but do not require the payload to declare every committed exclusion.

The r41 census/C02 evidence identifies six relevant heldout arms. Five all-record map/wrapper arms (`heldout-flat-dotted-map`, `heldout-nested-checks-map`, `heldout-nested-expected-wrapper`, `heldout-nested-observations-wrapper`, `heldout-wrapper-precedence-expected-over-observations`) were accepted at 28/28, exit 0. `heldout-expected-only-full-copy` is distinct: it copies the 24 scored/in-scope values in `expected`-only records and is accepted at 24/24, exit 0. Thus do not describe that arm as an all-28 value copy. C02 ranks these direct payload-only doors first; they need neither a planted carrier nor a committed-file edit.

## Exact read surface and precedence

The line references below are for `verifiers/compare_harness_independent.py` at SHA-256 `1742dcccad1118399f0aa959f7ea6884d5992834d8c4c8b94e108277ae87df76` (live file and `git show b1be35f:...` byte-identical at the captured instant).

1. **Decode/root selection — `extract_json` (207–243).** A whole JSON value is parsed first; otherwise the parser extracts the last balanced top-level object from noisy text. It uses ordinary `json.loads`, so duplicate object members are already collapsed last-key-wins before any channel validation. H04 measured a duplicate top-level `results` key and a duplicate per-record value key accepted on these same comparator bytes. A P1 validator operating only on the decoded dict cannot detect the discarded copy; reject duplicate members at decode time or leave this residual explicitly outside P1.

2. **Direct row channels — `CHANNEL_KEYS`, `_record_list`, `_dotted_map`, `_channel_maps` (246–358).** The recognized channel names, in iteration order, are `results`, `rows`, `checks`. For each non-null channel, a list is parsed as records; a dict is accepted only when it is a nonempty map whose every key is a string matching the dotted-ID grammar. Other types and non-ID maps fail closed. A direct `checks` dotted map is therefore a channel, not a later wrapper fallback. A present but malformed `checks` map errors before fallback; an empty dict is not a valid dotted map. Bare JSON lists are supported by `_record_list` for consumers, but `_channel_maps` only treats the payload itself as a record list in neither independent nor live parsing.

   Record identity uses the first string in `check` → `id` → `name` (`_record_id`, 265–269); later aliases are not reconciled. Independent record value uses the first present key in `expected` → `expected_value` → `re_derived` → `value` → `observed` (`IND_VALUE_KEYS`, 130–131; selection at 304–308). There is a partial consistency check at 309–338: if `expected`/`expected_value` and at least one of `re_derived`/`value`/`observed` coexist, the first foreign key is checked against each derived key. It does not reconcile `expected` against `expected_value`, or reconcile derived aliases when no foreign expected key exists. The heldout expected-value, re-derived/value, observed-key, and ID-alias arms expose these gaps.

3. **Direct-channel precedence is agreement, not first-channel-wins — `_reconcile` (361–411).** Every non-null direct channel is parsed. Names are sorted and the first alphabetical map is the comparison base (`checks`, then `results`, then `rows`); every other channel must match its values canonically, its membership exactly, and any statuses that both channels provide. This is not an escape hatch to choose a conflicting row channel: divergence/membership is rejected. Same-channel duplicate IDs with different values are rejected, but the last duplicate record overwrites the saved status when values agree. A map channel carries no per-ID status. When any channel parses successfully, `parse_independent` returns that reconciled map and ignores top-level `expected`, `re_derived`, `observations`, and bare-map-looking extra data.

4. **Nested wrapper / bare-map fallback — `parse_independent` (426–466).** It runs only when `_channel_maps` found no channel. It tests dotted maps in this exact order: `checks` → `expected` → `re_derived` → `observations`; the first valid, nonempty dotted map wins and later wrappers are not compared. If none is valid, the entire top-level object is accepted as a bare dotted map, but only if it is nonempty and every key matches the dotted-ID grammar. Map values are otherwise unconstrained, and there is no allowed-ID/key-set check. Thus `expected` shadows conflicting `observations`; a valid `checks` channel shadows wrapper maps; and an extra non-dotted top-level metadata key makes a bare dotted map invalid. The C02 wrapper-precedence arm is the concrete example of the accepted first-valid wrapper shadow.

5. **Scope-out does not close the value maps — `parse_scoped_out` (564–610), `check_scope_probes` (740–820), `build_meta` (1918–1937).** `scoped_out` is an optional top-level map; omission yields `{}`. A supplied entry must name a parsed ID, have record status exactly `SCOPED_OUT`, and have a nonempty reason. The committed scope set is then used to reject payload-declared IDs outside that set and validate their probes. It is not used to subtract committed IDs from the independent value map, nor to require the payload’s declaration to equal the full committed set. A dotted map has no record status, and a wrapper can return values without a `scoped_out` map at all. Consequently the join sees 28 independent IDs rather than the honest 24 when these maps carry all live values; the four committed exclusions do not protect themselves merely by being in the scope file.

6. **Other map readers (adjacent, not the P1 value source).** `parse_live` first reconciles direct channels using only `observed`, then `_record_list` selects the first record-list in `results` → `rows` → `checks` (or accepts a bare list) for observed/verdict/mode extraction (469–495). A map-only live payload is not sufficient. `build_meta` separately builds `expected_map` from `expected` fields in that selected live record list and computes the secondary metric against every independent map entry (1952–1960); it is not the primary join and should not be mistaken for the C1 guard. For scope evidence, the top-level `scoped_out_probes` map wins wholesale; per-record `probe` fallback is read only if that map is empty (1927–1936). These are probe/status integrity surfaces, not alternate independent value-map readers.

## P1 contract to close the surface

- Establish the allowed ID set from the live check IDs minus the committed scope-out IDs, independently of the independent payload’s own scope declaration. Apply it to every accepted record channel, dotted channel map, wrapper map, and bare dotted map before joining. The accepted independent value set must not gain a committed scope-out ID; extra IDs fail with exit 2 and a class-named reason. Missing allowed IDs must remain an exit-2 uncovered result. Preserve the honest 24/24 join.
- Reject a substantive value supplied for a committed scope-out ID in **any** accepted value field/channel, even if a different channel or wrapper wins selection. If record-form scope-out sentinels remain supported, specify the exact sentinel/status representation rather than treating a map’s presence as derivation evidence.
- Reconcile all simultaneously supplied value/identity aliases and all accepted representations, or reject conflicting/ambiguous representations. Do not leave first-valid wrapper precedence, `check`/`id`/`name`, or value-key priority as a laundering route. Keep the direct-channel disagreement checks; do not replace them with a single selected channel.
- Make the contract closed over input syntax: reject duplicate JSON members before dict construction. Decide whether unknown nested extension maps are out of contract or forbidden; H04’s nested `extensions...channels` result is explicitly conditional because the current parser neither reads nor rejects unknown subtrees. Do not claim that P1 reconciles arbitrary nested JSON.
