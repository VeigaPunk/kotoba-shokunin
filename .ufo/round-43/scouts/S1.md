## Prioritized open-door list

Ordering follows C02: least attacker control/prerequisite first, then impact. A cited arm is open only for the measured payload and frozen comparator bytes; “accepted” does not automatically mean the primary value join changed.

### 1. Payload-only maps can supply values for all rows and expand the joined scope — immediate C1 target

The claim's exact held-out target is this six-arm family: `heldout-expected-only-full-copy`, `heldout-flat-dotted-map`, `heldout-nested-checks-map`, `heldout-nested-expected-wrapper`, `heldout-nested-observations-wrapper`, and `heldout-wrapper-precedence-expected-over-observations` (claims.json:15–20; census:15–21; C02:7–12; Y02:30–41). Every arm is accepted in the frozen replay. The map/wrapper variants can supply the four normally scoped-out rows as well as the ordinary joined rows, producing a 28-row rather than 24-row comparison; the expected-only full-copy is separately serious because it passes with no derivation field at all. C02 ranks this as the highest-reachability class: an independent-payload supplier needs neither a carrier nor a committed-file edit. The claim's after-condition must hold for every named form, including a scoped-out row with a supplied value and a map whose keys exceed the honest derived set—not just for one canonical JSON encoding.

**Do not silently omit adjacent map variants found outside the six-arm claim target:** R01 also records `root-shape-nested-re-derived-map` and `R1-A3-flat-map-no-status-channel` passing, plus conflicting root `checks`/`expected` and `expected`/`observations` representations where the selected copy wins (R01:28–33, 38–44). Treat them as separate regressors/held-out cases; closing the six exact arms is not proof that the map channel is closed.

### 2. Raw JSON duplicate members bypass parsed-channel checks; selected value aliases are not reconciled

H04's raw JSON forms are payload-only and were not in the V10 matrix: a duplicate top-level `results` key with divergent copy first and honest copy last is accepted; so is a duplicate per-record `re_derived` key with conflicting first value and honest last value. Reversing the top-level key order makes the divergent copy effective and fails named, showing last-key-wins decoding rather than a harmless duplicate. R02 independently confirms these accepted shapes (H04:28–46; R02:19–27; Y01:25–29; A01:25–32). Reject ambiguous duplicate members during JSON decoding or include them in the declared/validated schema.

Also open in the ordinary parsed object: `heldout-expected-value-secondary-shadow`, `heldout-rederived-vs-value-shadow`, `heldout-observed-key-shadow`, and `heldout-id-alias-conflict` (census:15–17; C02:11–15; Y02:30–35). Conflicting `expected`/`expected_value`, `re_derived`/`value`, or `re_derived`/`observed` fields can be ignored while the selected field keeps the join green; conflicting `id`/`name` beside the canonical `check` is ignored. R01 additionally reports `check`/`id`/`name` alias conflicts and conflicting root maps accepted (R01:30–34, 38–44). These are payload self-consistency/identity gaps; distinguish them from the map family above when scoring whether they alter the joined row set.

### 3. Duplicate records can last-write-win status and live metadata

The census arm `heldout-duplicate-id-status-shadow` and H01/H02/R02/Y02's same-value duplicate variants let a later `DERIVED` copy conceal an earlier `UNLANDED` copy; reversing the order changes the verdict. Conflicting duplicate values are a different shape and are closed on the measured comparator. H01 also measures `--expect-n` against unique parsed IDs rather than raw record multiplicity, so repeated identical live IDs are not rejected by that count guard (H01:16–24; R02:19–22; Y02:50–54). Y01 cites E01's accepted 10,000 identical `x.y` rows and rejected conflicting-value control (Y01:25); this is a multiplicity/metadata issue, not an additional demonstrated joined-ID expansion.

The broader live-side duplicate case is important: H05's equal-`observed` duplicate rows can replace `mode` or `verdict` by position. The later `mode=positive` row can turn an equal-mode disagreement into a passing positive comparison; later `verdict=PASS` can mask an earlier `DRIFT`, while reversing order exposes the drift. See item 6 for the full caller-controlled-live boundary (H05:22–43; R02:21–23; Y02:50–56).

### 4. Status/state aliases, omitted status, and unvalidated top-level fields

The census arms `x2-state-shadow`, `status-nonstring-hides-state`, and `top-level-status-and-alternatives` remain open, as does the duplicate-status case above (census:18–19; C02:14–16). A record's selected `status` masks contradictory `state`; a null/non-string `status` can hide `state=UNLANDED`; and a scored row with status omitted can leave the provisional list empty. H02/R02/Y02 also show that a top-level `unlanded` summary does not repair an absent or contradictory record status (H02:39–48; R02:21–24; Y02:50–54).

The payload's top-level reporting fields are accepted without reconciliation: `landed`, `unlanded`, `provisional`, `n`, `total`, `headline`, `alternatives`, and Y02's `falsifier`/present-token claims may contradict record data without affecting the join. Unknown/foreign top-level fields including `overrides`, `metadata`, `alternatives`, and `r01_extra_top_level` also ride through; these are the un-contract field boundary, distinct from a demonstrated value bypass (H02:24–25, 45–48; R01:34–42; Y01:24, 28; Y02:52–55; A01:27–32). H05's nested top-level `observed` summary is likewise ignored: it can contradict the record list but did not itself move the primary join (H05:24–27, 43–45).

Scoped-out reason/evidence can drift from the committed explanation, and a legitimate scoped-out row may still carry a value (`w1-scoped-row-carries-value`); those latter cases do not themselves add the excluded row to the primary comparison, but leave the excluded evidence unvalidated.

### 7. Carrier and invocation/scope-file trust boundaries

- **Payload-selected probe target, carrier required:** `r1-f4-payload-chosen-probe-target` passes with a locally authored two-file carrier and changes what the probe attests. This does not expand the committed four-ID set; it is probe-evidence substitution. C02 places it after payload-only doors because the attacker needs a writable carrier (C02:20–22; H06:33–35; R02:22–24; Y02:43–47).
- **Relative `--scope-file` resolved against process CWD, receipt against `--cwd`:** `r1-f3-prime-scope-file-cwd` passes only when a planted process CWD supplies the extra scope row; the receipt describes the honest file while the enforced scope contains the additional `omp.offered.skills` scope-out. H06 gives the planted-cwd run/control and source mechanism; R01/R02/Y02 reproduce the receipt/set mismatch (H06:19–35; R01:31–33; R02:22–24; Y02:37–41). This is high impact—scope membership changes—but requires control of invocation CWD/path resolution, so keep its reachability below payload-only classes.
- **Caller-selected absolute scope path:** `scope-file-caller-selected-absolute` is accepted when the caller explicitly supplies the planted file. The census correctly treats the absolute-scope arm as a caller-selected trust input, not a payload-only bypass of the selected file; include it in policy if callers/arguments are untrusted (census:13, 20; C02:22–24; Y02:39–41).
- **Scope metadata validation gaps:** H03's wrong-but-enumerated blocker `kind` passes against an alternate copied scope file even though its unchanged reason contradicts that kind. This establishes a semantic validation gap if a committed entry is misclassified; it does **not** show that the current committed scope row is wrong. Y01 also reports E02 accepting a missing `probe_contract` and an unused non-dotted scope ID. These are scope-policy/schema checks, not the current planted-CWD scope-set bypass (H03:21–35; Y01:27–29).

### 8. Receipt provenance, races, mutability, and output-path collision

These are evidence-chain/operability doors, not all primary join bypasses; keep them visible rather than folding them into the payload channel count.

- H06's `frozen-inputs` receipt label establishes file-backed input, not producer provenance: a probe-authored input can receive that mode. A controlled post-read file mutation yields a successful join receipt whose consumed-text SHA differs from its later `file_sha256`. The receipt's invocation fields are editable and have no built-in signature/verifier path (H06:37–45, 51–61).
- H01 shows `--report` can alias and overwrite an input after it has been read/hashed; the run's result is computed, but the source path no longer contains the attested input bytes. This requires caller-selected path collision and is an evidence-clobber risk, not a demonstrated verdict bypass (H01:18–24).
- H06's tested `--no-stamp` behavior is intentional absent a protocol requirement for mandatory stamps. H01's forged payload receipt fields were ignored in favor of the driver's generated receipt; those tested receipt-spoofing fields are closed, not open (H01:13–16; H06:47–49).
