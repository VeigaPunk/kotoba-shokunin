## Results

**Honest control remains green.** `python3 verifiers/compare_harness_independent.py --no-stamp` at the pinned comparator/scope bytes returned exit 0: 24/24 protocol, strict 20/24, 4 adjudicated, 4 scoped out; both producers exited 0 with 28 checks. The frozen-byte comparator over the same captured inputs returned the same result.

**Wrong-but-enumerated blocker kind is accepted — residual metadata door.** The real payload contains all four scope rows, each with status `SCOPED_OUT`; the real committed file contains the same IDs. For `omp.catalogue.found`, I changed only the copied `--scope-file` row's `kind`, leaving its reason, probe contract, probe, and payload unchanged. The committed reason says the selection rule is “inside the harness's own authored scope” (`verifiers/harness-independent-scope.json:14-16`), yet the `external-authority` variant still returned exit 0 / 24/24 on both frozen and live comparator bytes. `substrate-absent` also returned 0 / 24/24; `rule-in-author-scope` control did likewise. Variant SHAs and exact commands are in the results log.

This is **not** a payload-only way to extend the allow-list: the live committed file currently has the correct `rule-in-author-scope` value, and the experiment supplies a mutated `--scope-file` to model a wrongly classified committed entry. It demonstrates that a bad classification already present in a committed scope file is not caught. `load_scope_file()` checks only membership in `SCOPE_KINDS` (`compare_harness_independent.py:138, 641-646`); the later scope check validates probe kind against `probe_contract.kind` (`:791-795`), not the committed row's blocker `kind` against its reason or an allowed kind for that row.

**Enum boundary works, but only syntactically.** All three accepted `SCOPE_KINDS` values were exercised end-to-end with the real scoped-out payload and all were accepted. An unrecognized `not-a-SCOPE_KINDS-value` was rejected on both drivers with exit 2 and the named “not one of” error. The issue is therefore not arbitrary enum injection; it is the acceptance of a valid enum member that misstates the blocker (the external-authority case is directly inconsistent with the unchanged reason).

**Empty reasons fail closed in both channels.** With a whitespace-only reason in the payload's `scoped_out` mapping, the comparator returned exit 2: `independent: scoped_out reason for omp.catalogue.found is empty`. With a whitespace-only reason in the copied committed scope entry, it returned exit 2: `scope file row omp.catalogue.found carries no blocker reason`. Both reproduce on frozen and live bytes. Parser checks are at `compare_harness_independent.py:595-608` and `:641-642`.

Supplemental gate: `python3 verifiers/compare_harness_independent.py --self-test` returned exit 0, `0 failure(s) over 118 assertions`; its existing empty-reason assertion is self-test 65. The adversarial enum-mismatch case is not covered by that battery.

## Verdict / limits

- **Depth (this hunt): residual found.** Empty-reason and unknown-enum cases remain closed. No fresh payload-only scope-set expansion was found in this slice. A committed row can nevertheless carry a semantically wrong but enumerated blocker kind and still leave the join green; record it as a committed-metadata classification gap, not as a bypass of the current correct committed set.
- **No fix landed:** H03 is a hunt/verification seat and this defect requires a policy decision about binding row kinds to actual blockers (or narrowing the accepted enum), not a probe-only patch.
- Probe limitation: wrong-kind evidence uses a generated alternate scope file; it does not show that the actual committed scope file is currently misclassified. Frozen and live comparator/scope bytes were identical, so the run establishes persistence at the verification HEAD, not a code before/after delta.
