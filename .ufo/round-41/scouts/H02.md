### `secondary_agree` — count is not constrained to its denominator

On the genuine captures, `secondary_agree=20`, rendered as `20/24` against the joined-scope denominator. The code builds `expected_map` from the first live record list and sums *all* independent ids whose value strictly matches that map (`compare_harness_independent.py:1952-1960`); it neither filters scoped-out ids nor emits the member list. JSON exposes the bare integer (`:1071`), while the denominator is `scope_n` (joined rows plus uncovered rows, excluding scope-outs; `:838-849`).

Two discriminators prove the mismatch:

- Setting only the four independent `SCOPED_OUT` rows' values to their corresponding live `expected` values, while preserving their committed scope-out status and probes, leaves the primary join at protocol `24/24`, strict `20/24`, adjudicated `4`, exit 0—but `secondary_agree` becomes `24` over the same `24` denominator (battery line 9). The counter now includes four rows absent from the joined scope, masking the four strict mismatches.
- Setting those scoped-out values and the four adjudicated values to live expected values, consistently across independent `results`/`rows`/`checks`, yields protocol `24/24`, strict `24/24`, zero adjudicated, exit 0, but `secondary_agree=28` with a joined-scope total of `24` (line 10). This is a synthetic adversarial payload, not a live instrument result; it demonstrates a report numerator greater than its denominator.

Additional isolation: rewriting all 24 joined live `results[].expected` values to independent values changes `secondary_agree` from `20` to `24` without changing primary exit/protocol/strict/adjudicated outputs (line 6). Adding a `rows` shadow whose `expected` fields match the independent instrument while `results[].expected` remains unchanged is accepted and leaves the counter at `20` (line 8): the secondary counter uses only the first list and expected fields are outside the cross-channel reconciliation. A duplicate live id with the same observed value but conflicting `expected` values is likewise accepted; last expected wins and changes the count to `21` (line 7). Removing all live expected fields yields `0` without affecting the primary exit (line 11). Each arm's mutated payload hashes and results are in the referenced JSONL line; reproducer: the battery command above.

**Verdict:** open. `secondary_agree` is informational, but currently its denominator/membership do not describe the same set; it can be inflated or exceed the joined-scope total. The output should either define and enumerate the precise joined membership (and require expected values where used) or label this as a separate all-payload count with its own denominator. A mode/value channel fix alone does not address this.

### `provisional` flag — record status works; alias/summary channels do not reconcile

Control: setting the joined row `omp.db.rows` to `status=UNLANDED` consistently in independent `results` and `rows` produces `provisional_rows=[omp.db.rows]` and exit 1, even while the top-level `landed`/`unlanded` summary is contradictory (line 13). The record-status path works.

Open cases:

- For that row, setting `status=DERIVED` and `state=UNLANDED` in both record channels, plus top-level `unlanded=[omp.db.rows]`, `landed=0`, is accepted with provisional empty and exit 0 (line 14). Status extraction uses `record.get("status", record.get("state"))` (`:339`, also `:589-594`); if both aliases are present, `state` is silently ignored. The channel split check likewise sees only the selected status. This reproduces the intra-record status/state residual previously noted by X2, now scoped to provisional reporting.
- Removing both record status fields but retaining `unlanded=[omp.db.rows]` at top level also gives provisional empty and exit 0 (line 15). The comparator does not read/reconcile the independent instrument's top-level `landed`/`unlanded` fields. This is the previously reported R1 F-6 residual, re-measured here because it can conceal why the provisional list is empty.

The provisional list itself is derived from parsed statuses, not from an input `provisional` array: `annotate_statuses()` only adds a row when a recognized status is non-`DERIVED`/`OK` and protocol is true (`:823-835`). A zero count is therefore only meaningful after validating all status representations; current checks validate cross-record `status` values but not the `state` alias or top-level summary.
