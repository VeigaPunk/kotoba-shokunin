The successful receipt says `scope_file.path=verifiers/harness-independent-scope.json`, records the *honest repository* scope SHA, and has `scope_locks.committed_set` of length 5. The driver actually enforced the planted file. It reports `driver_cwd` as the repo from `--cwd`, while Python's process cwd was `drafts/h06/planted-cwd`—the cwd used to resolve the relative scope path. Thus the receipt's path/digest and committed set visibly contradict one another if audited against the committed file; the important failure is that the comparator neither detects nor rejects that mismatch and still gives the altered join exit 0. The honest-cwd control rejects the same payload with exit 2 (`laundering`).

Source explains the split: `load_scope_file()` calls `Path(path).read_text()` at `verifiers/compare_harness_independent.py:613-624`, resolving a relative path against process cwd; `render_receipt()` instead prefixes the relative scope path with its `cwd` argument at `:1196-1201`, and main passes resolved `args.cwd` at `:2036-2039`. Fixing the trust gap requires resolving the scope path once against the intended repo root and using that exact resolved path/bytes for both enforcement and receipt.

**Probe boundary:** the added scope entry copies a valid existing blind probe; the mutated row keeps its derived values while declaring `SCOPED_OUT`. That makes this an intentional composite of the cwd door with an already-reported scope/value inconsistency, not a claim that H06 found a new probe kind. From the honest repo cwd, the committed-set lock rejects it as expected.

### D3 — OPEN/qualified: post-read mutation yields a successful receipt with split hashes

At `16:38:00.180–16:38:04.331Z`, a child-only `sitecustomize` hook appended one JSON whitespace byte *after* `Path.read_text()` returned the live input and before `side_receipt()` re-read the file. The compare still returned exit 0 / `frozen-inputs`. `inputs.live.sha256` (consumed text) was `0bc250f5197c9dbbdbdce7e15c4220e0904118a8c290f81295aa18464b0b0341`; the later `file_sha256` was `8828d654c665c97f5d7b9c5a9f88418ac3af36544819c4305b1bc21b23b30108`. The result file is `receipt-digest-race.json`.

This is a controlled TOCTOU probe: the implementation hashes consumed text, then separately reads the current path for `file_sha256` (`:1149-1172`), and does not require those values to agree. Both digests are present, so a careful auditor can see the split; the driver still emits a passing receipt rather than flagging that the file no longer represents the bytes it consumed. Independent opened-byte hashing (or rejecting a mismatch) would close this residue.

## Verdicts and handoff

- **Depth: OPEN.** The scope-file cwd mismatch remains across frozen r39 → b1be35f → worktree; an altered scope/payload passes only when launched from the planted cwd. The receipt does not enforce its own attested scope digest. `frozen-inputs` also does not prove producer origin, and receipts are mutable.
- **Operability: qualified.** Ordinary file receipts record matching hashes; the `--no-stamp` behavior is intentional. A controlled between-read mutation still returns exit 0 with mismatching digests, and there is no receipt verifier/signature.
- **Calibration: measured.** All quoted verdicts above are tied to the exact driver SHA and run instants; no calibration document, scorecard, or instrument was changed by this seat.

No code fix landed here. Handoff targets: use one canonical scope path/byte buffer for both load and receipt; bind file digest to the consumed bytes and reject/report a race; state narrowly that `frozen-inputs` only means file-backed inputs unless producer provenance is independently verified; if receipts are meant to be tamper-evident, sign or externally pin them and add a verifier. Treat `--no-stamp` as optional report behavior unless the protocol makes stamps mandatory.
