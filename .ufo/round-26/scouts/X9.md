## Findings

- **Slice answer: confirmed.** Corrupting one commit-hash citation in the clone
  flips the independent instrument 0 -> 1, naming the exact site and isolating the
  `commit_unresolvable` class; `--json` carries the same site. Non-vacuous on COMMITS.
- **Agreement under fault** with the primary instrument on the identical mutation,
  same site string; both agree green at HEAD (`tracked_files=53`, `report_total=36`,
  `commit_total=27`, all zero-classes 0) — matches `verifiers/corpus-baseline.json`.
- Deterministic (two byte-identical runs); self-test 52/52; no over-fire on content;
  all red probes (hash, nonhash, pointer, env-absent) flip as specified.

## Defects named

1. `verifiers/verify_corpus_independent.py:313` and `:346`: `with open(path, ...)`
   assumes every `git ls-files` entry exists in the working tree. A tracked corpus
   file deleted from the tree (a normal mid-round state) raises an uncaught
   `FileNotFoundError` -> traceback on stderr, **0 bytes of stdout**, exit **1**.
   `analyse()` guards only repo/corpus/README (`:381`-`:386`); `analyse_index`
   survives via `os.path.exists` (`:275`), so the crash surfaces in the pointers
   pass first. **Exit-code collision:** crash and genuine verdict both exit 1, so a
   caller reading only the exit code cannot distinguish them — the docstring
   contract (`:29`) reserves 2 for environment-unreadable, which this is. Primary
   instrument exits 2 with `INCONCLUSIVE: cannot read tracked file ...` on the
   identical state. Still unpatched at HEAD (the M8 class, deferred r21/r24).
