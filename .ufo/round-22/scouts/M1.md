## Findings
**F1 — probe hypothesis confirmed for the two extraction-bearing callees.**
Renaming `Co` (primary probe) flips the self-test to exit 1 with exactly the
expected naming:

```
self-test FAIL: new-callees: exit 0: got 1
self-test FAIL: new-callees: PASS literal_present: got 'FAIL surfaces.literal_present: 1 loader literal(s) not verifiable: omp:gemini/GEMINI.md (no (Id|Cl|jD[ef]|Tl|dr|GW|Co|Dl|Hj)(<v>, <group>, "<file>.md") call shape for (gemini, GEMINI.md) in omp dump) ...'
2 failure(s) over 75 assertions
```

Renaming `Dl` fails identically, naming `omp:claude-md/CLAUDE.md`. In both
runs the remaining checks still PASS inside the (b2) invocation —
notably `PASS surfaces.no_uncovered_class: all 1 extracted loader class(es)
declared` — so detection rides on `surfaces.literal_present`'s loader-group
pair assertion (`verify_surfaces.py:522-529`), not on `no_uncovered_class`.
The failure message names both the fixture subtest (`new-callees`) and the
class id plus the full `CALLEE_SHAPES["omp"]` allowlist string
(`verify_surfaces.py:159-162`). The self-test is a live detector of a
callee-rename on the fixture: the per-harness allowlist mutation is caught.

**F2 — the rename is only detectable for `Co`/`Dl`, not `Hj`.**
Renaming `Hj(e, "cursor", "rules")` → `Hk(...)` yields exit 0, 75/75
assertions green. Reasons, all verifiable in-source:
- `OMP_CALL_RE` requires a `\.md`-suffixed file argument
  (`verify_surfaces.py:157`), so the non-`.md` `(cursor, rules)` call is
  never extracted — the `Hj` line contributes nothing to
  `extract_classes` even in the pristine fixture;
- `omp:cursor/rules` is declared `loader-literal` in
  `verifiers/fixtures/surfaces/baseline-clean.json:20-23`, so
  `literal_present` only probes literal `"rules"` presence
  (`verify_surfaces.py:516`), and `"rules"` survives the rename as a string.
Consequence for the probe's spec wording ("rename one callee" → expect exit
1): the expectation holds for `Co` and `Dl`; a `Hj`-only rename is silently
accepted. The `Hj` line in the fixture is a witness of the live binary's
shape (comment at `verify_surfaces.py:784-785`), not a detection point.

**F3 — control layers are clean.** Live tree and `/tmp` pristine copy both
exit 0 with 75 assertions; stderr carries exactly the 3 expected NO-SUCH
ERROR lines in every run; the corrupted runs' extra stdout is limited to the
2 `self-test FAIL` lines each (`grep -c` = 2 for both co and dl).

No defect was found in the (b2) detector itself for the load-bearing callees:
both `Co` and `Dl` renames are caught with a named FAIL and exit 1.

## Limits (what I did NOT verify)
- Only `--self-test` was exercised; the live-binary path (`--omp-strings`
  against a real dump) and exit-2/exit-3 environment paths were not probed.
- Only single-token renames of exactly `Co`, `Dl`, `Hj` were probed; other
  corruption classes (line deletion, literal edits, dump truncation) are
  covered by the other fixtures' subtests (b)/(c)/(b3) and were not re-run
  beyond the clean control.
- The 75-assertion count and (b2) behavior are pinned to this HEAD
  (`b16300f`); any future fixture edit must re-derive them.
- No other verifier (`verify_harness_claims.py`, checklist, corpus, fault
  injection) was run; my probe is scoped to `verify_surfaces.py --self-test`.
