## Findings

F1 — **The gate counts `len(text.splitlines())` and trailing blank lines
COUNT.** `verify_skill_checklist.py:1805` (`lines = text.splitlines()`) feeds
`check_line_budget` (`:1084`, `n = len(lines)`). Appending one blank line to a
600-counted-line file yields 601 and flips PASS→FAIL; there is no `rstrip`, no
trailing-blank discount. (v600_dropblank vs v601_trailblank; v602_trailblank
= 602.)

F2 — **The boundary is inclusive at 600.** 600 counted lines → `PASS … 600
lines within budget 600 (from box at line 329)`, gate exit 0 with all ten
checks PASS. 601 counted lines → exit 1. Claim B's target (`<=600`) is
exactly one counted line less than the current file; removing a single blank
separator line (line 453, after `## Sources`) already reaches green, so the
required delta is small and the box map (41 boxes) is unaffected by deleting
non-box content.

F3 — **Verbatim verdict strings** (for the round-22 report/L0 record):
- PASS: `PASS trigger.line_budget: evaluated 600 — 600 lines within budget 600 (from box at line 329)` / `exit 0`
- FAIL: `FAIL trigger.line_budget: evaluated 601 — 601 lines exceed budget 600 (from box at line 329)` / `exit 1`
(the limit's provenance is always spelled `from box at line 329`; `from
--max-lines` never appears while SKILL.md:329 carries an integer.)

F4 — **The box binds over the flag.** `--max-lines 1000` still reports
`budget 600 (from box at line 329)`; the flag is only a fallback
(`box_line_budget`, `:1073-1081`).

F5 — **`wc -l` is NOT the gate's counter.** With no final newline the gate
counts `wc -l + 1`: `v601_nonl` prints `wc -l 600` yet FAILs at 601, and
`v600_nonl` prints `wc -l 599` yet PASSes at 600. Claim B's
`counting_command` (`wc -l SKILL.md (<=600)`) can therefore read green while
the gate is red — see D1.

F6 — **Threshold-extraction trap.** `LINE_BOUND_BOX_RE` requires only the
shape `file … <int> … line(s)`; `INT_RE` then takes the *first* integer
anywhere in the box text. Inserting `3` between `File` and `600 lines`
silently sets the budget to 3 (`v601_boxpreint` → `exceed budget 3`). Inert
only because the box map pins the box text by sha256 (see D2/D3).

F7 — **Harness fidelity (for future /tmp lanes).** A bare `cp -a` to a
differently-named directory manufactures three spurious FAILs that have
nothing to do with the probe:
`trigger.name_directory` (`name 'kotoba-shokunin' != directory 'repo'`),
`trigger.citation_resolves` (`line 591: '../.ufo/reports/round-7/kotoba.md'
does not resolve from /tmp/m5/repo`), `governance.citation_resolves`
(`LOG.md:177 ../.ufo/reports/round-9/kotoba.md`, `LOG.md:255` round-11,
`LOG.md:311 ../PROTOCOL.md`). Mirroring the fleet root (symlinks to every
live fleet entry + the copy named `kotoba-shokunin`) reproduces the live
verdicts exactly (9 PASS / 1 FAIL). Any lane reporting "extra reds in /tmp"
should first apply this fix.

F8 — Round-22 target semantics for claim B, stated as a test: after the edit,
`python3 verifiers/verify_skill_checklist.py` (default paths, cwd = repo
root) must print `PASS trigger.line_budget: evaluated N — N lines within
budget 600 (from box at line 329)` with `N <= 600` and exit 0; any trailing
blank line left at EOF counts against N.

## Defects named (each: path:line + evidence)

D1 — `verifiers/verify_skill_checklist.py:1805` (`lines = text.splitlines()`)
vs claim B's `counting_command` at `.ufo/round-22/claims.json` (B:
`wc -l SKILL.md (<=600) && python3 verifiers/verify_skill_checklist.py
(exit 0)`): the two counters disagree whenever the final line is
unterminated. Evidence: `v601_nonl` — `wc -l` 600 (would satisfy the stated
command) but gate `FAIL … evaluated 601`. A landing commit could thus satisfy
B's written counting command while B's falsifier (`line count still > 600`)
stays true. The gate's own counter is authoritative; `wc -l` should be
supplemented with `python3 -c "print(len(open('SKILL.md').read().splitlines()))"`.

D2 — `verifiers/verify_skill_checklist.py:1073-1081`
(`box_line_budget` / `LINE_BOUND_BOX_RE` `:362`, `INT_RE` `:364`): the budget
is the first integer in the whole box text, not the integer adjacent to
`lines`. Evidence: `v601_boxpreint` → `FAIL trigger.line_budget: evaluated
601 — 601 lines exceed budget 3 (from box at line 329)`. Consequence for
round 22: claim B must not reword the box at `SKILL.md:329` (e.g. adding
"moved 1 section" inside that box sentence) or the threshold changes
silently.

D3 — Same box, second failure mode: any box reword also breaks the map.
Evidence: `v600_boxearlyint` → `FAIL checklist.box_map_complete: … unmapped
box at line 329 (section 'Trigger-fidelity checklist', sha256 87bc619e23ae…)`
plus `… annotation claims 'trigger.line_budget' but the map records '<no
entry>'`. So a box edit costs both a threshold hazard (D2) and a map red —
claim B's edit must touch only non-box prose, and the round-22 acceptance
must re-run `checklist.box_map_complete` (it pins 41 boxes by hash).

D4 — `verifiers/verify_skill_checklist.py:1081` (limit provenance in the
verdict string, `"box at line %d" % b["line"]`): the provenance token embeds
the box's *current* line number, so any edit that shifts lines at or above
329 changes the verdict text while the semantics are unchanged — claim B's "verbatim verdict
string" evidence must be taken from the post-edit tree, not quoted from this
fragment (current string valid for HEAD `b16300f` only; the box sits at 329
and my `v600_dropblank` removal at line 453 leaves 329 intact).

D5 — Harness-level (no repo file): a relocated `cp -a` copy reds three
path/environment checks (F7). Not a defect in `verify_skill_checklist.py`
(the checks are correct: they are relative-path/environment claims), but a
reproducible trap for round-22+ lanes that probe on /tmp copies.
