## Defects named

**D-A8-1 — a filed line was rewritten in place, violating the rule the file's own heading
declares.** `46e9ec3` (`round-11` closure, kumitate r11) modified line 5 rather than
appending a superseding entry.

- Evidence: line 5 at `e333e7c` is 830 bytes, at `46e9ec3` is 1470 bytes;
  `cmp -l` reports the first differing byte at offset 151, with bytes 1-150 identical —
  i.e. the same entry, edited in place and extended. Visible text change:
  `…zero journal; unit ~/.config/systemd/user/webzites-keeper.timer…` →
  `…zero journal, empty LastTriggerUSec; unit ~/.config/systemd/user/webzites-keeper.timer…`
- Rule violated: `PROTOCOL.md:505-506` ("never rewrites a filed line").
- Already in the fleet ledger as **D-94** (`.ufo/reports/AGGREGATE.md:1197`: "`.ufo/l0-questions.md`
  is off-ledger: a filed question was rewritten in place rather than superseded by an
  appended entry"). Not remediated in-file: no supersession line naming the superseded
  wording, so the pre-rewrite wording is recoverable only from git. This is the one
  historical violation with actual content loss in the channel.

**D-A8-2 — the channel file was truncated to a 64-byte stub and later restored.**
`e0b4d9b` (`fleet: init shokunin root — manifest, lane conf, ufo dirs; lanes are own
repos`) reduced the file from 20563 bytes / 21 lines to a single 64-byte line; `e867f78`
(a merge, parents `415666f` `bdff08b`) restored it.

- Evidence: stub blob `f3193b9f…` = 64 bytes, sha256
  `d47174016e21c92274dfaad66b7b2cb28a5a7dfd51b676cdf695e49a9c3be6ff`, content
  `# L0 questions — append-only: <lane> | round-<N> | <question>\n`. The restore is
  content-preserving: `cmp -s -n 20563 ee1f621:<path> e867f78:<path>` exits 0 → the
  pre-truncation revision is a byte-prefix of the post-restore revision, +90 bytes
  appended (blank line, `--- 2026-10 relaunch ---`, the heading). So **no question text
  was lost**, but the file went backwards by 20499 bytes, which "append-only" forbids.
- Consequence for the channel: the heading at line 24 and the separator at line 23 are
  re-init/relaunch artifacts, not appends of the pre-relaunch generation; anything keying
  on line numbers across that boundary is wrong (which is why `PROTOCOL.md:507-508` bans
  line-number citations).

**D-A8-3 — the append-only rule has no mechanical guard.** The property is enforced by
convention alone: `git config core.hooksPath` exits 1 (unset), `.git/hooks/` contains no
non-sample hook, and no fleet-root script asserts prefix growth for this path (`grep -rln
"append-only"` hits only `.ufo/waves/*` closure-check/mutant scripts, which guard the
closure ledger, plus per-lane probe scripts). A future round could close this cheaply with
a verifier or hook that runs the same `cmp -n <prev_blob_size>` test against
`git rev-parse <prev>:<path>`; the baseline in this fragment supplies the expected value
for round 22.

**D-A8-4 — path collision on the L0 channel's filename (A2-adjacent, minor).**
`/home/vgpnk/Projects/shokunin/tsukuroi-shokunin/.ufo/l0-questions.md` exists as a
*different* file (1437 bytes, rows opening `tsukuroi | fleet-round-1 interactive
continuation | …`). Prompts instruct lanes to append to `.ufo/l0-questions.md` while also
naming the absolute fleet-root path; a lane that resolves that relative path from its own
repo root writes to a sibling-local file the aggregator never reads, and the append silently
vanishes from the channel. Round-22's escalation must use the absolute
`/home/vgpnk/Projects/shokunin/.ufo/l0-questions.md`.

## Limits (what was NOT verified)

- **No append was made and no append was observed.** This fragment is the "before" state
  only; it does not confirm that A2's round-22 escalation has happened, nor that it will
  use an append rather than an edit.
- Prefix audit covers only commits reachable from HEAD that touch this path (23). Reflog-only
  states, dangling objects, other branches, `FETCH_HEAD`/remote copies, and worktree copies
  in other repos were not audited (no network, no fetch).
- `git log --follow` reports 22 commits vs 23 plain; the difference is the merge `e867f78`,
  where following stops at the delete/add boundary. I did not resolve whether the path
  existed under a different name before `e0b4d9b`, so an earlier rename could hide a fourth
  violation older than `609ecb6` (the file's first appearance, 0 bytes).
- Git cannot separate "a lane rewrote a line" from "the operator answered in place"
  (`PROTOCOL.md:506` legitimises the latter). For `46e9ec3` the commit message and the
  fleet's own D-94 entry attribute it to a lane; the other two are a fleet re-init, not
  operator answers, per their commit messages.
- No fault-injection probe of the append path (`verifiers/fault_injection_corpus.sh` not
  run for this slice), so the append mechanism's failure modes (concurrent appends by
  parallel sessions, partial writes, editor adding a trailing newline) are untested.
- I did not cross-check other ledgers (`.ufo/state/*`, `history-pin.json`, `SCORECARD.md`)
  for a differing recorded size/digest of this file, so cross-ledger consistency of the
  baseline is unverified, and I did not check whether a parallel session currently holds
  the file open for writing.
- Findings 1-3 of the historical audit are read-only git forensics; nothing was mutated in
  the fleet root or any sibling repo, and `/tmp/round22-a8/` (including `l0_copy.md` with
  the probe line) is scratch.
