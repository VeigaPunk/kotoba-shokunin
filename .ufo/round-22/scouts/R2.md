## Findings

### F1 — The doc-derived omp extraction set reproduces exactly (blind, one shot)

Derived from census § A before looking at any output: table A declares **8**
machine-extracted classes (`agents-md/AGENTS.md`, `claude-md/CLAUDE.md`,
`opencode/AGENTS.md`, `gemini/{GEMINI.md,system.md,SYSTEM_TEMPLATE.md}`,
`github/copilot-instructions.md`, `windsurf/memories/global_rules.md`).
Live extraction from my own dump: 11 raw shape hits → **8** unique
`(group, file)` pairs, identical set, all 8 declared, `literal_present` 38/38.
The census's wider tables give 8 (machine) + 17 (hand-declared) + 4 (opencode § B)
+ 9 (§ C excluded) = **38 ids**, which my independent parser confirms equals the
baseline id set and the inventory row set, with zero literal and zero kind
mismatches. The deriver's arithmetic and the implementation agree on every id.

### F2 — The round-21 callee rename is real, and larger than the commit says

Per-callee `.md`-registration shapes in the **live omp dump**: only `Co` (4),
`Dl` (5), `Hj` (2) match; `Id`, `Cl`, `jDe`, `jDf`, `Tl`, `dr`, `GW` match
**0** each. So the historical allowlist yields `omp -> 0 pair(s)` — the
round-21 defect reproduced byte-for-byte — and the extended list yields 8.
Byte-level verbatim witnesses in the live binary (raw bytes, not `strings`):

```
// packages/coding-agent/src/discovery/agents-md.ts
var W$ = "agents-md"; var OQ = "AGENTS.md"; async function S1t(u) { return Hj(u, W$, "AGENTS.md");
// packages/coding-agent/src/discovery/claude-md.ts
var G$ = "claude-md"; var DQ = "CLAUDE.md"; async function T1t(u) { return Hj(u, G$, "CLAUDE.md");
Co(u, "gemini", "GEMINI.md") / Cl(u, "cursor", "rules") / Dl(u, "gemini", "settings.json")
```

The 2026-10-16 build is the "unminified source chunks" rebuild: source paths
(`packages/coding-agent/src/discovery/*.ts`) and readable function names are
present. Consequence for the census: its § A evidence column still quotes the
round-13 shapes (`jDe(e,Pqr,"AGENTS.md")`, `Pqr = "agents-md"`), none of which
occur in this binary (D6).

### F3 — The variable-resolution branch is load-bearing on live bytes (2 of 8)

`constant_table` (1112 entries over the live dump) resolves `Hj(u, W$, …)` →
group `agents-md` and `Hj(u, G$, …)` → group `claude-md`. Without the
`ASSIGN_RE` non-quoted-identifier branch those two pairs would surface as
`<unresolved-var:W$>`/`<unresolved-var:G$>` and FAIL. The docstring's
"minified bundles register the groups through variables" claim is therefore
still true in the 2026-10-16 rebuild — under new variable names.

### F4 — The per-harness split is correct and cheap, but its stated justification has no live witness

Round-21 comment (`verifiers/verify_surfaces.py:139-145`) claims "a name
harmless in one bundle over-matches the other". Measured from my own dump: the
three added names do occur as bare call tokens inside the opencode bundle —
`Co(` 102, `Dl(` 29, `Hj(` 6 (plus `jDe(` 1) — but **0** of them form the
shipped `(<v>, <group>, "<file>.md")` shape, so `CALL_RE` and `OMP_CALL_RE`
both extract `opencode -> 0 pair(s)` today. The split is thus (a) **necessary**
in the omp direction (0 vs 8, F2), (b) harmless and forward-defensive in the
opencode direction, (c) *unproven as an over-match on this substrate*. Related,
measured, not a defect but a standing risk: 6 of the 9 names in `OMP_CALL_RE`
are dead on the live build (0 shapes each), so the allowlist only grows — each
dead name is an un-retired over-match candidate.

### F5 — The vacuity guard matches its docstring on every checkable clause

`check_no_uncovered_class` docstring (`:539-547`), clause by clause:

- *"a harness dump from which ZERO loader classes extract while the baseline
  declares loader-group classes for it is a moved/renamed substrate — a FAIL"*:
  code `if loader_group_declared and not pairs` (`:556-561`). Confirmed both
  ways at unit level (E8: FAIL naming omp + 8) and at CLI level (row 5: exit 1
  with a 2-entry fixture baseline; row 1: PASS with the real 8).
- *"Guarded per loader-group kind only"*: baseline has 8 `omp` loader-group
  entries and **zero** opencode loader-group entries (measured from
  `surfaces-baseline.json`), so the guard is structurally inert for opencode.
- *"…covered by opencode_extract's own zero-extraction rule"*: verified, not
  taken on faith — fixture `strings-empty.txt` with the real opencode half
  yields `vacuity: extraction produced 0 class(es) from 6 rule(s)` (self-test
  case (oc0b), `:917-923`), so an opencode blackout still cannot pass on 0==0.
  Row 6 shows the same blackout leaving `no_uncovered_class` green, exactly as
  the docstring describes.
- *"the 2026-10-16 omp rebuild extracted 0 shapes here while literal_present
  failed every row, and this check still said PASS"*: the second half is
  confirmed from the round-21 diff (`git show 2ca8d01 -- verifiers/verify_surfaces.py`:
  the pre-round-21 body had no guard and returned `all %d extracted loader
  class(es) declared` on an empty `found`), and the first half from E8.

No clause of the guard's docstring is contradicted by the code. The guard is
also *scoped as a backstop, not as the detector*: killing a single callee
(row 10) leaves `no_uncovered_class` green while `literal_present` FAILs — the
right layering, since the guard only covers the all-shapes-vanished case.
