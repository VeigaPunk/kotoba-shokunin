## Findings

### F1 — Live pin state at HEAD `b16300f`: the guard would be GREEN, by measurement

All three `measured_against` binary pins match live, exactly:
`omp_binary_sha256` `bf1e86a9…` ✓ (round 21 re-pinned it), `omp_binary_mtime`
`2026-10-16T05:15:11.226207850-03:00` == `st_mtime_ns` `1792138511226207850` ✓ (ns-exact),
`opencode_binary_sha256` `d9123b9b…` ✓. So a landing round gets red-before green-after for
free by mutating a /tmp baseline copy (vectors 9–12), and cannot fake green: today's green is
the first *evidence* that round-21's prose re-pin is accurate.

### F2 — The mtime pin is nanosecond-precise, and the obvious parser is wrong by 874 ns

`datetime.fromisoformat("2026-10-16T05:15:11.226207850-03:00")` **truncates to microseconds**
(`.226207`) and `.timestamp()` rounds through a float → `1792138511226206976`, 874 ns *below*
the true `st_mtime_ns`. A guard written the obvious way reports `DRIFT` on a perfectly fresh
pin (cmd 5). The ns-exact recipe (cmd 6): extract the fractional digits as an integer
(`ljust(9,'0')[:9]`), strip them, `calendar.timegm(dt.utctimetuple())*10**9 + frac`. This is the
single highest-value line in the spec — without it the guard ships red on a green substrate and
the round "fixes" it by re-pinning repeatedly. Corollary: the pin must be *written* from
`st_mtime_ns`, not from a µs-truncating tool (cmd 12 shows a µs pin reds).

### F3 — uniform "sha256+mtime per pin" is impossible: the baseline pins mtime for omp only

`measured_against` keys are `omp_binary_sha256`, `omp_binary_mtime`,
`opencode_binary_sha256` (plus non-pin prose: `as_of`, `host`, `command`, `round18_move`,
`omp_round21_note`). There is no opencode mtime pin — unsurprising, its mtime is synthetic
(`1985-10-26`, cmd 3), an artifact of the packer, so it carries no provenance. Spec: compare
exactly the three keys, keyed by a table; ignore unknown keys; a *missing* pinned key is
`PIN_ABSENT` → exit 1 (deleting a pin must be as loud as drift, or the guard re-inherits the
inert-pin failure it exists to close).

### F4 — The guard must hash, never exec: exec-ing the pinned binary writes to another gate's input

My own identity probe (`opencode --version`, cmd 4) appended two lines to
`~/.local/share/opencode/log/opencode.log` (mtime `2026-10-19 01:26:14`):
`timestamp=2026-10-19T04:26:14.259Z level=INFO run=c2abaa53 message="cli starting" version=2.0.26 channel=latest local=false args="[\"--version\"]" role=cli`
(and the same at `04:25:59.932Z`). That log is precisely what `oc.log.*` harness checks read —
an exec-based "version check" is not read-only, it pollutes another gate's observation surface.
`omp --version` conversely left 64 files under `~/.omp` modified within 30 min (agent.db,
models.db-wal, and ~60 `omp.<date>.<pid>.log`; the fleet's concurrent omp lanes are the bulk,
but a `--version` run is not excludable from the set). Cmd 23 confirms no *counter* moved this
time (`cli starting` matches no counted grammar; 28/28 still green) — that is luck of grammar,
not a property. Spec rule: the guard opens the binary as bytes only.

## SPEC — `verifiers/check_substrate_pins.py`

**Purpose.** Enforce the three `measured_against` binary pins in
`verifiers/baseline.json`, so an unannounced substrate rebuild is a red gate instead of prose
that only a human notices (round-18→21: omp moved `55016ef5`→`ff59fc1b`→`bf1e86a9` with all
gates green, F1 D1).

**Inputs.** `--omp-binary PATH` (default `/home/vgpnk/.local/bin/omp`), `--opencode-binary PATH`
(default `/home/vgpnk/.opencode/bin/opencode`) — both mirroring `verify_surfaces.py:126-129`
`DEFAULT_BINARIES`; `--baseline PATH` (default `<repo>/verifiers/baseline.json`);
`--repo PATH` (default `Path(__file__).resolve().parent.parent`, the repo idiom) affecting only
the default baseline path; `--json`; `--self-test`. No positional args. Stdlib only
(`argparse, hashlib, json, os, re, calendar, pathlib`), Python ≥3.11; no new packages.

**Pins compared** (`(key, harness, kind)` table, in this order):
`omp_binary_sha256`→`omp`/`sha256`, `omp_binary_mtime`→`omp`/`mtime`,
`opencode_binary_sha256`→`opencode`/`sha256`. Unknown `measured_against` keys ignored.
sha comparison is case-insensitive on the hex string; mtime is parsed to epoch ns (`F2` recipe,
offset-aware, so a pin written in UTC or `-03:00` compares the same) and matched against
`os.stat(path).st_mtime_ns` (follows symlinks; the *effective* file is the measured one).

**Outputs (text).** One line per pin: `<pin> <VERDICT> <observed|expect/observed/detail>`.
**Outputs (`--json`).** `{"checks":[{pin,harness,kind,binary,expect,observed,verdict[,detail]}],
"pass":N,"fail":N,"exit_code":N}` — same shape/keys as `verify_surfaces.py:981-990`
`emit_json`, `indent=2, sort_keys=True`. Verdicts: `PASS`, `DRIFT`, `PIN_ABSENT`,
`UNREADABLE`, `NO_BASELINE`.

**Exit codes.** `0` all PASS; `1` any `DRIFT` or `PIN_ABSENT` **naming the pin** (drift line and
JSON entry both name it); `2` any `UNREADABLE` (missing/dir/perm — the run cannot measure);
`3` baseline absent/unparseable/no `measured_against` object. Precedence `3 > 2 > 1 > 0`;
the same code must be returned in `--json` mode (F1 D2 precedent: `verify_harness_claims.py:658`
returns 0 in JSON where the text path returns 3). The slice named only 0/1/2; 3 is kept because
both other baselines' verifiers document it (`verify_harness_claims.py:28-30`,
`verify_corpus_integrity.py:82-87`).

**Determinism.** Same tree + same binaries ⇒ byte-identical stdout in both modes (verified,
cmd 19); no wall-clock, hostname, duration, or pid field in the JSON; pin order fixed by the
table; `binary` reported as the path given (not a temp/resolved path). No writes anywhere —
never re-pins, never edits the baseline (an auto-repin would restore the inertness), never
execs a pinned binary (F4), no `__pycache__` (run as `__main__`).

**Cost.** 0.22 s live (both binaries, 1 MiB chunks) vs the harness gate's ~3 s — cheap enough to
run every round; no cache (a cache keyed on mtime would itself be an inert pin).

**`--self-test`.** In-process fixtures only (repo idiom: `verify_surfaces.py` 75 assertions,
`verify_skill_checklist.py` 1504, `verify_harness_claims.py` 10), so CI never needs 460 MB of
binaries and never touches `$HOME/bin`: match, sha-drift, mtime-drift-1ns, pin-absent,
unreadable, missing-baseline, plus the F2 ns-round-trip assertion (prototype: 7/7). Live
fixtures under `verifiers/fixtures/pins/` (dir convention exists: `fixtures/surfaces`,
`fixtures/checklist`).

**Out of scope (deliberately).** `measured_against.command`,
`as_of`, `host`, `round18_move` — reading the `command` pin would inherit F1 D2's exit-code
bug; `host`/`as_of` are provenance prose, not substrate identity.

### Ambiguities resolved

1. *Naming* — `check_*` breaks the 5/5 `verify_*` convention → recommend `verify_substrate_pins.py`.
2. *Per-pin "sha256+mtime"* — impossible uniformly; opencode mtime is unpinned and synthetic
   (`1985-10-26`) → compare exactly the three keys present.
3. *Missing pin key* — skip (silent) vs drift: chose exit 1 `PIN_ABSENT`, because a deleted pin
   is the same failure class as an unenforced pin.
4. *mtime-only drift* (bytes identical, file rewritten — a reinstall/touch) — chose exit 1 with
   verdict `DRIFT`; rejected "WARN + exit 0" (cmd 22 shows `cp` vs `cp -a` is exactly this case,
   and a silent reinstall invalidates the provenance claim just as much as new bytes).
5. *mtime precision* — µs vs ns: ns, from `st_mtime_ns`; a µs pin reds (cmd 12) so the writer
   must emit 9 digits.
6. *Precedence when both unreadable and drifting* — 2 over 1 (cannot name drift you could not
   measure).
7. *Exit 3* — added to the slice's 0/1/2 for repo consistency, incl. JSON mode.
8. *Flag spelling* — `--omp-binary/--opencode-binary` (surfaces), not `--omp-bin/--oc-bin`
   (harness); divergence recorded, not harmonized.
9. *Symlinks* — `os.stat` follows; dangling → `UNREADABLE`/exit 2.
10. *Whole-file vs streaming hash* — streaming, 1 MiB chunks (253 MB + 210 MB; `read_bytes()`
    would hold ~460 MB).
11. *`--repo`* with absolute `$HOME` defaults — kept for idiom parity; it only moves the
    baseline default.
12. *JSON determinism vs observability* — no `observed_at`/duration fields (they would break
    cmd 19's byte-equality); a consumer wanting "when" reads its own clock.

## Defects named (each: path:line + evidence)

1. **`verifiers/baseline.json:4-9` — `measured_against` has no consumer (the debt this spec
   closes).** Evidence (cmd 1, mine): `grep -c measured_against verifiers/*.py verifiers/*.sh`
   → `0` for all six files. Round-21 corroboration: `.ufo/round-21/scouts/F1.md` D1, `L04.md`
   F3, `LOG.md:1214` ("`measured_against` pins are inert (no gate reads them)").
2. **`verifiers/baseline.json:6` — pin precision is unstated and the obvious parser misreads
   it.** The value carries 9 fractional digits; `datetime.fromisoformat(...).timestamp()` yields
   874 ns less than `st_mtime_ns` (cmd 5), i.e. a naive guard reds a correct pin. Defect-shaped:
   the file records a pin no documented recipe can compare exactly.
3. **`verifiers/verify_surfaces.py:126-129` + `verifiers/verify_harness_claims.py:52-55` — the
   binary paths are hardcoded in two files, independently of the pins they are measured under.**
   Two gates can read different files than the pin names, and nothing notices; the pin guard's
   `--omp-binary/--opencode-binary` defaults are a third copy.
4. **`verifiers/surfaces-baseline.json:3` and `corpus/knowledge/instruction-surface-census-round13.md:23`
   — the opencode sha `d9123b9b…` is duplicated in prose** (additionally
   `corpus/knowledge/opencode-extraction-round14.md:5`, `corpus/knowledge/instruction-surface-census-round13.md:12`).
   After `measured_against` becomes enforced, these copies are the stale half of the same fact;
   they are not machine-compared today.
5. **`SKILL.md:545-585` vs claim B's line budget — the sixth instrument cannot be introduced
   without SKILL.md lines.** Live: `wc -l SKILL.md` → **601**; § "authority/evidence" lists one
   bullet per verifier. Landing the guard as documented costs ~2 lines in the very round trying
   to get ≤600. Interaction, not a file bug — named so the landing round plans for it.
