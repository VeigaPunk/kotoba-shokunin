## Defects named (each: path:line + evidence)

1. **The round-15 "verbatim bytes" idiom has no pointer-rebasing step.**
   `SKILL.md:591` carries `../.ufo/reports/round-7/kotoba.md` (a base-relative
   fleet-root pointer, valid only from the repo root). `verifiers/verify_corpus_integrity.py:208-214`
   resolves non-rooted tokens from *the citing file's own directory*
   (`:349`, `:490`), so pasting that line verbatim into
   `corpus/knowledge/source-library-round22.md` yields
   `corpus/knowledge/../.ufo/…` = `corpus/.ufo/…` → **`corpus.pointers.report_dead`
   0 → 1**, corpus verifier exit 1, unchanged by a baseline bump. Rebase forms
   that measure clean: 3-hop relative, or the corpus's own host-absolute
   convention (33 of 34 live report pointers are absolute — `corpus/README.md`,
   round-13 convention row). Note the ordering trap found while probing: a
   2-hop rebase (`../../.ufo/…`) resolves to the *repo-local* `.ufo`, which has
   only `reports/round-20`, `reports/round-21` — still dead.
2. **`verifiers/corpus-baseline.json` equal-mode counters are landing work, and
   the move silently changes two of them.** Any new corpus file shifts
   `checks.corpus.index.tracked_files.expect` (52 at HEAD) by one; any moved
   report pointer shifts `checks.corpus.pointers.report_total.expect` (34).
   Evidence: `sim.py` runs show `DRIFT observed 53 vs expected 52` and
   `observed 35 vs expected 34`; bumping exactly those keys returns exit 0.
   The file's own `notes.round21_refresh` shows the incumbent discipline
   (`--no-baseline --json` observation + a named note).
3. **Asymmetric instrument coverage on this exact drift.**
   `verifiers/verify_corpus_independent.py` exits **0** on the same tree where
   `verify_corpus_integrity.py` reports `corpus.index.tracked_files` DRIFT
   (53 vs 52): the independent index check has no equal-mode tracked
   denominator. A landing that remembers the author's baseline but skips the
   derivation is not caught by the second witness. (Severity: coverage gap in
   the witness pair, not a false verdict in either direction.)
4. **Simulation-side constraint, named so it is not read as a repo defect:**
   `git commit` was not permitted, so the new corpus file is visible to
   `git ls-files` only via `git add --intent-to-add` (exit 0, copy only), and
   `verifiers/fault_injection_corpus.sh` (which `git clone`s HEAD) cannot see an
   uncommitted move at all — only `--self-test` was exercised.

- Everything ran on `cp -a` copies under `/tmp/round22-s02/`; no live-tree edit,

  (`grep -c '^kotoba | round-22'` → **0**, file 49 lines) — the A2 escalation
  itself is another lane's slice, not measured here.

  (fault harness clones HEAD and is blind to uncommitted edits); only
  `--self-test` passed. The red-before/green-after pair for the move was taken
  with the corpus-equivalent counters instead.
- `verify_surfaces.py` / `verify_harness_claims.py` read host state
  (`~/.omp`, `~/.local`), which the move does not touch; their exit 0 does not
  exercise `SKILL.md`.
- I did not test the landing *sequence* (README row placement was simulated as
  the last row of the coverage map), nor EOF/trailing-newline hygiene, nor
  whether the moved prose's cross-references to other `SKILL.md` sections
  ("see the table rule above") read correctly from the corpus home — the
  `## Router model` and `## Decision tables` blocks contain such deictic
  references; a landing should re-read them in place.
- Only one 3-line stub shape was simulated (heading / blank / one pointer
  sentence). A no-blank-line 3-line variant keeps identical line counts.
- Section inventory was taken at `b16300f`; line ranges are points-in-time.
