## Findings

1. **The pin is inert, proved executably, not by grep.** Corrupting the omp binary sha in a
   /tmp copy leaves `verify_harness_claims.py` at `28/28 checks pass`, exit 0 (RUN A), while
   corrupting a `checks` entry flips the same gate to `DRIFT` exit 1 (RUN C). Round-21's
   evidence for this debt was static (`F1.md:169` — `grep -c … returns 0 for all six files`;
   `K09.md:134` D4 — pin-vs-live comparison); no round-21 scout is recorded as having run the
   corrupt-pin-and-run differential. This fragment supplies that falsification.
2. **Mechanism.** The sole baseline read in the harness gate is
   `verifiers/verify_harness_claims.py:569` — `baseline["checks"].get(cid, {}).get("expect")`,
   reached from `main` after `json.loads(args.baseline.read_text())` at
   `verifiers/verify_harness_claims.py:650`. Nothing else in the file (or the other five
   verifier files) touches `measured_against`; no gate hashes `baseline.json` itself. The 28
   `CHECKS` (`verifiers/verify_harness_claims.py:524`) contain no `*_binary_sha256` id — the only
   binary-derived invariants are `omp.elf.template_sha256` (the *compression prompt*, not the
   binary) and the `b"customize-opencode"` substring probe (`:477-478`).
3. **Worse than "inert": the block may vanish silently.** Deleting `measured_against`
   entirely still yields `28/28`, exit 0, in both text and `--json` (RUN D). Any consumer that
   treats the block's presence as provenance is reading an unenforced claim, and there is no
   gate that would notice its removal.
4. **What the P-guard must therefore do (requirement evidence for the prototype lane).**
   `check_substrate_pins.py` must (a) *require* `measured_against` to exist and (b) compare the
   file's pins against live `sha256(omp)`, `stat.mtime`, `sha256(opencode)` with a non-zero exit
   on either mismatch or absence; a consumer that only compares-when-present reproduces RUN D's
   blindness. The pins to enforce are `verifiers/baseline.json:5,6,8`
   (`omp_binary_sha256` `bf1e86a9…`, `omp_binary_mtime` `2026-10-16T05:15:11.226207850-03:00`,
   `opencode_binary_sha256` `d9123b9b…`). Note `verify_harness_claims.py` already exposes
   `--omp-bin/--omp-db/--oc-log/--oc-bin/--omp-sessions` fixture overrides
   (`verifiers/verify_harness_claims.py:626-630`), the natural injection seam for a guard of this class to be
   self-testable.
5. **Round-21 admits the debt in four places (verbatim quotes).**
   - `verifiers/baseline.json:7` (`measured_against.omp_round21_note`): "omp rebuilt 2026-10-16
     (ff59fc1b->bf1e86a9, v18.11.1, unminified source chunks; registration callees now Co/Dl/Hj).
     **Re-pinned by round 21; no check enforces this pin (named debt).**"
   - `LOG.md:1210` (§ Round 21, claim F): "`verifiers/baseline.json` omp sha/mtime re-pinned to
     `bf1e86a9` (**no check enforces `measured_against` — named debt**)."
   - `LOG.md:1214` (named-debt list): "**`measured_against` pins are inert (no gate reads them)**".
   - `SCORECARD.md:32` (freshness line): "omp sha/mtime re-pinned in `verifiers/baseline.json`
     (**still unenforced by any check — named debt**)."
6. **Documentary wrinkle, not a gate issue:** `verifiers/baseline.json:2` `as_of` is
   `2026-10-14T09:58:47.702772-03:00` — the round-18 measurement time — although round 21
   re-pinned the omp sha/mtime on 2026-10-16. The file's own timestamp does not name the moment
   of its last edit; `round18_move` (line 10) likewise predates the round-21 note. Same
   subclass as the pin itself: self-describing metadata that nothing verifies.
