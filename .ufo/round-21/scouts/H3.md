## Findings

**F1 — `.ufo/interactive-sessions/` is correctly ignored.** Confirmed live:
`git status --ignored --short` reports `!! .ufo/interactive-sessions/`, and
`git check-ignore -v` attributes it to `.gitignore:1`. The 2 session files under it
(`20261015T050057Z/...jsonl`, `.../__advisor.jsonl`) appear only in
`--ignored` listings, never as `??`. The rule works as advertised by `c8b53ac`.

**F2 — `__pycache__` is NOT ignored, and the defect is live and growing.** HEAD's
`.gitignore` is a single line (`.ufo/interactive-sessions/`). `git check-ignore -v`
returns **exit 1** for `verifiers/__pycache__/a.pyc`, `__pycache__/a.pyc` and
`corpus/__pycache__/a.pyc`. No other ignore source exists: `core.excludesFile` unset,
`.git/info/exclude` has no active patterns, no subdirectory `.gitignore`, no
`.gitattributes`.

Live state at measurement: `verifiers/__pycache__/` held **three** pyc files
(`verify_corpus_independent` 46460 B, `verify_corpus_integrity` 56353 B,
`verify_skill_checklist` 107287 B), all with mtime `2026-10-19 00:46:44`–`00:46:48`.
Two of those three (`verify_corpus_independent`, `verify_corpus_integrity`) were
**never tracked** — so the untracked-bytecode surface has grown from the 2 files
`4e92f36` removed to 3. The pyc appeared *during* this scout run (the first
`git status --short` at ~00:46:0x showed only `?? .ufo/round-21/`; the re-run showed
`?? verifiers/__pycache__/`). This scout ran only git/read commands, so the
regeneration was produced by a concurrent process in this repo, which is itself the
proof that regeneration is continuous, not historical.

**F3 — the regeneration trigger is an import, not a script run.** `verifiers/*.py`
never import each other (`grep -nE '^\s*(import|from)\s+(verify_|verifiers)'` and
`grep -nE 'importlib|runpy|exec\(|__import__'` over `verifiers/*.py` both return
nothing), and running a verifier as `__main__` writes no bytecode — proven: in the
copy, `rm -rf verifiers/__pycache__ && python3 verifiers/verify_surfaces.py --self-test`
left `__pycache__` absent. Importing the three modules as libraries reproduces the
live state exactly (control probe: `?? verifiers/__pycache__/` appears, `check-ignore`
still exit 1). So the trigger is an out-of-tree harness that imports these modules —
any such run re-dirties the tree.

Circumstantial attribution (not proof): in the same window the pycs regenerated, the
sibling round-21 artifacts appeared — `.ufo/round-21/scouts/{A2,A3,A5,F1..F7,H2,M3,M6,R1,R5}.md`
and `.ufo/reports/round-21/` (all untracked, `ls -la .ufo/round-21/scouts/`, 00:46–00:50).
That is consistent with concurrent F-axis lanes re-running the live gates — which is
exactly the import that writes bytecode — but I did not observe a process, so the
attribution stays circumstantial.

**F4 — blast radius on gates is nil.** The corpus instruments read
`git ls-files` (tracked-only), so untracked bytecode cannot move a corpus verdict.
The two `root.iterdir()` walks in `verify_harness_claims.py` are scoped elsewhere
(`verifiers/verify_harness_claims.py:471` roots = `~/.agents/skills`,
`~/.config/opencode/skills`, `~/.claude/skills`; the other at line 269 iterates
caller-supplied skill roots). No verifier checks working-tree cleanliness. So this is
a hygiene/history defect, not a gate-verdict defect — it does not colour any round-21
axis measurement.

**F5 — root and `verifiers/` are otherwise clean.** The stray sweep (22 name
patterns, incl. `*.orig`/`*.rej`/`*.bak`/`*.swp`/`.DS_Store`/`node_modules`/`.venv`/
`.mypy_cache`/`.pytest_cache`/`*.log`) returned empty. Repo root has no untracked
entries at all. `verifiers/` has exactly one untracked entry: `__pycache__/`.
The only other untracked paths in the repo are this round's scratch dirs,
`.ufo/round-21/` and `.ufo/reports/round-21/` (`claims.json` and the sibling
fragments are sibling lanes' files, not mine). Neither is ignored
(`git check-ignore -v .ufo/round-21/a` → exit 1); see D3.

**F6 — the `4e92f36` commit message states a falsehood.** It claims the pycs are
"already covered by the lane .gitignore; these predate the rule". Both halves are
wrong. The rules were `__pycache__/` and `*.pyc`, present at `29c17be` (round-14) —
and commit `c8b53ac` **deleted both** in the same commit that **added** the two pycs
to tracking. The current `.gitignore` (byte-identical at `c8b53ac` and `4e92f36`:
`git show <rev>:.gitignore | od -c` → `.ufo/interactive-sessions/\n` both times) does
not cover `__pycache__`. So the files never "predated" a rule that covered them; the
rule was removed immediately before they were committed, and the follow-up cleanup
asserted coverage that had never existed. The net effect is that `4e92f36` removed the
symptom (tracked binaries) without restoring the cause's fix (the ignore rule), which
is why F2 reproduces within one day.

## Defects named (each: path:line + evidence)

**D1 — `.gitignore:1` — `__pycache__/` and `*.pyc` rules missing; bytecode regenerates untracked.**
`.gitignore` is 1 line / 27 bytes, contents `.ufo/interactive-sessions/` (`od -c`).
Evidence of the hole: `git check-ignore -v verifiers/__pycache__/a.pyc` → exit 1;
`git status --short` → `?? verifiers/__pycache__/` with 3 pyc files, mtime
2026-10-19 00:46. Evidence of the cause: `git show 29c17be:.gitignore` →
`__pycache__/\n*.pyc`; `git show c8b53ac -- .gitignore` → both lines deleted.
Fix is one line and was verified non-vacuously on a `/tmp` copy: appending
`__pycache__/` makes `check-ignore` return `.gitignore:2:__pycache__/` (exit 0) and
removes `?? verifiers/__pycache__/` from `git status --short` while the pycs are
present.

**D2 — commit `4e92f36` (no line; `git show -s --format=%B 4e92f36`) — false claim of ignore coverage.**
Body asserts "already covered by the lane .gitignore; these predate the rule".
Falsified by D1's evidence: the covering rules were deleted by `c8b53ac`, which is the
commit that introduced the tracked pycs. A LOG.md entry that repeats this claim would
be a second-order false claim; `grep -n -E '4e92f36|c8b53ac' LOG.md` currently returns
**no** hits (only `29c17be` is referenced, at `LOG.md:566` and `LOG.md:574`, in a
round-15 attribution note), so the false claim is confined to the commit message.

**D3 — `.ufo/round-21/` and `.ufo/reports/round-21/` untracked (severity: low, by design or oversight — operator call).**
`git check-ignore -v .ufo/round-21/a` → exit 1. Round-20's equivalents
(`.ufo/round-20/*.json`, `.ufo/reports/round-20/kotoba.md`) *are* tracked
(`git ls-tree -r --name-only HEAD -- .ufo`), so this round's scratch dirs will show as
untracked until a landing commit decides otherwise. Not a hygiene failure, but they
are the only untracked non-bytecode paths and they should be a deliberate decision, not
a default. No ignore rule needed if the round intends to track them.

**D4 — minor: `.gitignore` has a trailing newline now, unlike round-14's version.**
`od -c` at HEAD ends `...sessions/\n`; at `29c17be` the file ended `*.pyc` with no
newline. Harmless, and it means `printf '__pycache__/\n' >> .gitignore` appends
cleanly (verified on the copy). Recorded only so the fix patch has no surprise.

## Limits (what you did NOT verify)

- **Who regenerated the live pycs.** I established *that* they appeared mid-run and
  *that* an import reproduces it, but not *which* process did it — a concurrent
  sibling lane or the round harness. No process-level attribution was attempted.
- **Whether `4e92f36`'s false claim reached LOG.md prose.** I grepped only for the
  literal commit shas `4e92f36` / `c8b53ac` / `29c17be`. A paraphrase of the claim
  (e.g. "bytecode is ignored") would not have matched. Not exhaustively searched.
- **Global/system git ignore sources other than `core.excludesFile`.** I checked
  `core.excludesFile` (unset) and `.git/info/exclude`. I did not inspect
  `/etc/gitignore` or a system-level `gitconfig` excludes path; however
  `git check-ignore -v` is authoritative across all sources and returned exit 1, so
  the conclusion (not ignored) is sound regardless.
- **Gate re-runs.** Out of slice. I ran only `verify_surfaces.py --self-test` on a
  `/tmp` copy, and only to test bytecode regeneration. I did not re-run any live gate,
  so I hold no freshness (axis F) or sibling-adjacency (axis A) evidence.
- **Out-of-slice observation, low confidence, for the F scout:** that copy run
  reported `verify_surfaces.py --self-test` as `0 failure(s) over 70 assertions`,
  while `LOG.md` round-15 records `--self-test` `0/75`. A 70-vs-75 assertion-count
  discrepancy I did not chase; it may be an intentional change after round 15, or a
  stale LOG figure. Flagging, not claiming.
- **Not verified:** whether `4e92f36` is pushed. `git status -sb` reads
  `## master...origin/master [ahead 1]`, which suggests it is local-only, but I did not
  fetch to confirm.
