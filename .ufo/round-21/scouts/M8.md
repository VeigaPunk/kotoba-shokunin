## Findings

- **Red probe passes (slice answer).** Corrupting one commit-hash citation in the copy's
  corpus flips the independent instrument from exit 0 to exit 1 with the exact site named
  (`corpus/lessons/round-1.md:3: deadbeef`) and only that class drifting (`commit_unresolvable=1`;
  `commit_nonhash=0`, `report_dead=0`, index classes unchanged). The instrument is non-vacuous
  on the COMMITS family.
- **Agreement under fault.** The primary instrument fires on the identical mutation with the
  identical site string; both agree at HEAD 4e92f36 on the green baseline too
  (tracked_files=51, report_total=32, commit_total=27, all zero-classes 0), matching
  `verifiers/corpus-baseline.json` expectations.
- **Independent instrument is deterministic** (two byte-identical runs) and its own model
  falsification passes 52/52.
- **No over-fire on content edits**: a token-free prose append leaves exit 0.
- **Crash defect on unreadable tracked file** (Probe C): the independent instrument's
  missing-file handling is strictly worse than the primary instrument's.

## Defects named (each: path:line + evidence)

1. `verifiers/verify_corpus_independent.py:313` (and the same unguarded pattern at `:346` in
   `analyse_commits`): `with open(path, encoding="utf-8")` assumes every `git ls-files` entry
   exists in the working tree. A tracked corpus file deleted from the tree (a normal
   mid-round state) raises an uncaught `FileNotFoundError` -> traceback, exit 1.
   Evidence: Probe C above. This conflates a crash with the specified "1 any violation"
   exit (`:29` docstring contract: `0` clean, `1` violation, `2` environment unreadable) and
   emits no deterministic verdict output. `analyse()` only guards repo/corpus/README
   existence (`:381`-`:386`); `analyse_index` survives the same state via
   `os.path.exists` at `:275`, which is why the crash surfaces in the pointers pass first.
   Contrast: `verifiers/verify_corpus_integrity.py` on the same condition exits 2 with
   `INCONCLUSIVE: cannot read tracked file ...` — the independent instrument should match
   that behaviour (EnvError -> exit 2) or classify it.

## Limits (what I did NOT verify)

- Only one hash corruption was injected (one site, one class); the pointer and removal probes
  are single-site too. No fuzzing of the instrument's tokenizers, brace/glob expansion, or
  exclusion rules beyond its own self-test.
- Probes ran against the /tmp copy only; the live tree was never mutated (its
  `git status --porcelain` shows only untracked `.ufo/round-21/`, `.ufo/reports/round-21/`,
  `verifiers/__pycache__/`). `.ufo/reports/round-21/` is not mine — it appeared while I ran.
- I did not run `verifiers/fault_injection_corpus.sh`, and did not re-measure substrate
  versions (omp/opencode pins) or sibling dead-token counts — other slices own those.
- The exit-1-on-crash coincidence in Probe C means a caller checking only the exit code
  cannot distinguish crash from verdict; I did not audit other crash paths (e.g. non-UTF-8
  or unreadable-permission tracked files) beyond this one.
