## Findings

1. **Gate is non-vacuous and exact.** One appended dead report pointer turns
   `verify_corpus_integrity.py` from exit 0 (9/9) into exit 1, and the failing
   line names the precise site: `corpus/lessons/round-16.md:79:
   ../.ufo/reports/round-21/m3-dead-probe.md`. The site string is repo-relative
   and carries the citing line number, so it is actionable without --json.
2. **The failure is baseline-independent.** With `--no-baseline`, `equal`-mode ids
   report OBSERVE, so the only check that can produce DRIFT is a `zero`-mode one;
   exit 1 with DRIFT exactly on `corpus.pointers.report_dead` proves the zero-mode
   check itself carried the verdict, not a baseline mismatch on `report_total`
   (which also drifted, 32 -> 33, because a new pointer legitimately raises the
   checked population). This removes the "exit 1 for the wrong reason" reading.
3. **The commit-citation family is non-vacuous too.** A planted
   `commit \`deadbeef\`` (8 hex chars, not an object in the clone) yields exit 1
   naming `corpus/lessons/round-10.md:135`, with `commit_unresolvable` the sole
   DRIFT under `--no-baseline`.
4. **The gate is discriminating in the other direction as well.** The clean run
   exits 0 while the corpus still contains 8 excluded pointer sites (`<lane>`
   placeholders) and 2 quoted commit meta-findings; the checker does not blanket-fail
   on context text.
5. **Exit-code semantics verified live:** 0 = agree, 1 = drift, 2 = environment
   unreadable (non-repo; git repo without `corpus/`), 3 = baseline expected but
   absent. All four observed on this host today.
6. **Live-tree numbers at HEAD** (freshness evidence for this round): tracked=51,
   unindexed=0, stale=0, missing=0, 64 FILE-column patterns over 50 md files,
   report_dead=0/32, commit_total=27, unresolvable=0, nonhash=0, shapes
   relative=0/absolute=31/tilde=1/bare=0, quoted-excluded=2, pointer-excluded=8.
   Identical in the /tmp clone and in the live tree, so the clone is a faithful
   stand-in for the live surface.
7. **Provenance of `verifiers/__pycache__/` settled empirically.** Repeated
   `python3 verifiers/verify_corpus_integrity.py ...` runs in the clone created no
   `verifiers/__pycache__/` (it is absent after >=4 such runs); a single
   `python3 -c "import verify_corpus_integrity"` with `verifiers/` on `sys.path`
   created `verifiers/__pycache__/verify_corpus_integrity.cpython-314.pyc`. So the
   untracked `verifiers/__pycache__/` now in the live tree (4 `.pyc` files, mtimes
   2026-10-19 00:46:44-00:47:59) came from some concurrent lane *importing* the
   verifier modules, not from executing them as scripts.

## Defects named (each: path:line + evidence)

- **D1 - `verifiers/verify_corpus_integrity.py:40`: the claim "no writes anywhere"
  is unqualified and false on the import path.** Evidence: the module docstring's
  determinism paragraph states "no network, no writes anywhere". Execution as
  `__main__` honours it (clone shows no `verifiers/__pycache__/` after 4 runs),
  but importing the module writes `verifiers/__pycache__/verify_corpus_integrity.cpython-314.pyc`
  into the checked tree. Observed live artifact: `verifiers/__pycache__/` with 4
  `.pyc` files (`verify_corpus_integrity`, `verify_corpus_independent`,
  `verify_skill_checklist`, `verify_harness_claims`), mtimes today 00:46:44-00:47:59,
  untracked per `git status --porcelain`. A lane that imports these verifiers to
  reuse their pure functions therefore dirties the tree it is auditing; the claim
  should be scoped to "as a script" or the pycache suppressed. I did not delete it
  (out of my write scope) - the round owner should decide.
- **D2 - not a defect but a trap worth naming: `corpus.pointers.report_total` is
  `equal`-mode, so planting a probe pointer always double-fires the gate.** Any
  red probe that *adds* a pointer changes both `report_total` (32 -> 33) and
  `report_dead` (0 -> 1). Only the `--no-baseline` run isolates which check is
  load-bearing; a future probe record that cites the default run alone cannot
  distinguish "dead pointer detected" from "population changed". Recorded as a
  method note, not a code defect (the semantics are correct and documented).

## Limits (what I did NOT verify)

- INDEX-family non-vacuity (`corpus.index.{missing_paths,stale_patterns,unindexed}`):
  I planted a POINTERS-family token only. A red probe for the index family would
  need a planted `corpus/README.md` File-column token or a new tracked-but-unlisted
  file, which this slice did not cover.
- Pointer shapes other than `relative`: the planted dead pointer used `../`
  resolution. A dead `absolute`, `tilde` or `bare` pointer was not exercised live
  (the clean run shows 31 absolute + 1 tilde are checked, but none is dead).
- The quoted-dead-pointer exclusion (a dead pointer inside double quotes must be
  context, not a finding) is evidenced only by `--self-test` assertions plus the
  clean run's quoted/excluded counts - I did not plant a quoted dead pointer.
- `verifiers/verify_corpus_independent.py` (the independent derivation) was not run;
  no cross-check of the two corpus instruments is claimed here.
- No substrate/toolchain version measurement (that belongs to the F axis elsewhere);
  no harness-claims, checklist or fault-injection runs - other lanes own those.
- The `verifiers/__pycache__/` attribution is behavioural (script vs import), not a
  process trace: I did not observe which lane's command created the live `.pyc`
  files, only that script execution cannot have done it and import does.
