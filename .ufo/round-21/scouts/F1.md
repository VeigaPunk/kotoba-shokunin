   observation input) each drive it red with the correct DRIFT rows and exit 1,
   so the green is a measurement, not a no-op. Self-test passes 10/10.
2. **`verifiers/baseline.json` is byte-identical to its committed blob.**
   `cf7770db…` from both the worktree and `git show HEAD:…`, and
   `git status --porcelain` is empty for it. The pin set under test is the
   committed round-18 pin set, not a locally edited one.
3. **The omp substrate moved after the round-18 census and no gate reports it.**
   Live `bf1e86a9…` / mtime `2026-10-16 05:15:11` vs pin `ff59fc1b…` /
   `2026-10-14T08:39:28`. opencode is still the pinned `d9123b9b…` / v2.0.26.
   Every one of the 28 checks is derived from live observations and none of them
   reads `measured_against`; the sole binary-derived invariant,
   `omp.elf.template_sha256`, is unchanged by the rebuild
   (`c1f03c8e248eb40ec7735baab67f686fc2f254e00d2a0241ff220628461bdb51`, 273 B,
   equal to the pin), so the rebuild preserved the compression prompt and the
   cache keys. The practical reading for claim F: **round-18's `measured_against`
   pins are stale as a record of the substrate**, while the invariants they
   guard still hold. A round-21 re-census should re-record the omp sha/mtime
   deliberately and name the mechanism, exactly as `round18_move` did.
4. **The catalogue evidence is 4 days old, and the guard has no staleness
   pin.** Newest qualifying `<skills>` block is `2026-10-15T05:02:56.169Z` from
   `…/sessions/-Projects-shokunin-kumitate-shokunin/2026-10-15T04-50-57-644Z_…/CoverageCritic.jsonl`,
   while 763 session files were scanned and newer omp sessions exist
   (`-Projects-shokunin/2026-10-18T18-04-57-436Z_…jsonl`, mtime 2026-10-18
   15:47; `-Projects-shokunin/2026-10-19T01-49-51-979Z_…jsonl`, mtime 2026-10-19
   00:00) — both contain **0** `<skills>` literals, so the selection rule
   correctly skips them. The freeze invariant is intact on the newest
   qualifying block (7/7 lines byte-equal cache rows), but the block predates
   the omp rebuild by a day, so it witnesses the pre-rebuild renderer. No check
   pins `catalogue_timestamp`, so this cannot go red on age alone.
5. **Exit-code contract divergence between the two output paths** (defect D2):

   but `--json --no-baseline` returns 0. The command recorded in
   `measured_against.command` is exactly that JSON variant, so the pin's own

## Defects named

- **D1 — `verifiers/baseline.json` `measured_against` is inert metadata, and
  the omp binary sha it pins is unenforced.**
  Evidence: `grep -c "measured_against" verifiers/*.py verifiers/*.sh` returns
  **0 for all six files** (`verify_corpus_independent.py`,
  `verify_corpus_integrity.py`, `verify_harness_claims.py`,
  `verify_skill_checklist.py`, `verify_surfaces.py`,
  `fault_injection_corpus.sh`). The only `hashlib` use on a binary is
  `verifiers/verify_harness_claims.py:84` (`omp_template`) feeding
  `template_sha256` at `verifiers/verify_harness_claims.py:338`, and the only
  hash of the opencode binary is the substring probe at
  `verifiers/verify_harness_claims.py:477-478`
  (`b"customize-opencode" in binary.read_bytes()`). Neither the 28-check table
  (`verifiers/verify_harness_claims.py:524` onward) nor `checks` in
  `verifiers/baseline.json` contains any `*_binary_sha256` entry.
  Consequence: the live omp binary can be replaced (as it was on 2026-10-16)
  and the gate still prints `28/28 checks pass`, exit 0 — a stale
  `measured_against` block is indistinguishable from a current one to every
  automated consumer. Named as a defect, not drift: the pins read as enforced
  provenance and are not.
- **D2 — `--json --no-baseline` returns exit 0, contradicting the documented
  exit-code table and the text path.**
  Evidence: `verifiers/verify_harness_claims.py:658` —
  `return 0 if (baseline is None or all(r["verdict"] != "DRIFT" for r in results)) else 1`
  — short-circuits on `baseline is None` **before** the no-baseline branch at
  `verifiers/verify_harness_claims.py:681-682`
  (`print("no baseline — observations above only (exit 3)")` / `return 3`).
  The docstring contract is at `verifiers/verify_harness_claims.py:28-30`:
  `Exit codes: 0 all checks agree with the baseline; 1 drift; 2 the environment
  is unreadable …; 3 no baseline found`. Measured: `--no-baseline` → exit 3;
  `--no-baseline --json` → exit 0 with `Counter({'OBSERVE': 17, 'PASS': 11})`.
  The same `--no-baseline --json` argv is what
  `verifiers/baseline.json` `measured_against.command` records, so any harness
  that gates on that exit code reads "no baseline" as "all agree".
- **D3 — running any gate re-dirties the tree: `verifiers/__pycache__/` is
  untracked and not ignored.**
  Evidence: `.gitignore` is one line, `.ufo/interactive-sessions/` — no
  `__pycache__/` or `*.pyc` rule (the only `grep -n "pycache\|pyc" .gitignore`
  result is empty). HEAD itself is
  `4e92f36 cleanup: untrack 2 bytecode cache files`, removing
  `verifiers/__pycache__/verify_skill_checklist.cpython-314.pyc` (107 287 B) and
  `verifiers/__pycache__/verify_surfaces.cpython-314.pyc` (55 355 B) from
  tracking — but the on-disk directory survives, so `git status --porcelain`
  reports `?? verifiers/__pycache__/` after any `python3 verifiers/*.py` run.
  Observed live: the untracked entry appeared during this round's scout wave;
  the directory holds 4 pyc files, of which
  `verify_harness_claims.cpython-314.pyc` (00:47) is from this slice and
  `verify_corpus_independent` / `verify_corpus_integrity` /
  `verify_skill_checklist` (00:46) are from sibling scouts. The untrack commit
  is therefore incomplete: without an ignore rule the "clean tree at HEAD"
  state is not reproducible after the gates are run, and any round-21 scout
  asserting a clean worktree must whitelist this path. Not deleted here — the
  directory is shared with concurrently running scouts and this slice may not
  delete files.
