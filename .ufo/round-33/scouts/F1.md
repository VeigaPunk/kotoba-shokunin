## Findings
- **All M1 arms reproduce exactly.** One box -> exit 0 `PASS … evaluated 40 — 40 boxes mapped (8 executed, 0 delegated, 33 unexecuted)`; one *unexecuted* box -> exit 0 `evaluated 40 … 32 unexecuted`; all 33 unexecuted -> exit 0 `evaluated 8 — 8 boxes mapped (8 executed, 0 delegated, 0 unexecuted)`; keep 1 of 41 -> exit 0 `evaluated 1 — 1 boxes mapped (1 executed…)`. In each case the suite's only delta vs control is the box_map line.
- **Floor gap — `verifiers/verify_skill_checklist.py:897-900`.** The only floors are `if not boxes:` / `if not entries:` (non-empty), plus `>=1 valid executed:` (`:911-913`); parity is the `(section, sha256)` multiset at `:940-963` and `evaluated = len(boxes)` (`:985`). The map schema (`:30-37`, `load_map` `:395-432`) declares only `schema`/`file`/`normalization`/`boxes` — **no total** — so both parity sides move in step and nothing anchors the count. Contract `:57-58` says the same.
- Decoys, not floors: dropping *executed* boxes trips "no map entry with a valid executed: disposition" (that is what limits M1's "all 41 -> exit 1"); a decoy box added alone -> exit 1 "has no live box".
- **Fix sketch (validated).** Add an optional integer `box_total` to `kotoba-checklist-v1` (validated in `load_map`: positive int, `>= len(boxes)`), and in `check_box_map` at `:899` FAIL when `len(boxes) < box_total` or `len(entries) != box_total`, naming the floor. Pinned at 41: live `PASS evaluated 41` exit 0 (byte-invariant); all four shrinks -> exit 1 naming the floor; M1's one-sided classes still flip with unchanged exit classes (box-only/map-only/reword/extra-entry/floor-lowered -> 1, malformed floor -> 3); `--self-test` 0/1504.
- The map already claims the count in prose (`SKILL.md:126` "maps **all 41 boxes**"), so the pin is machine-readable restatement, not a new fact.
