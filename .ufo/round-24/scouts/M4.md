## Findings

1. **The landed pin guard's red ladder reproduces the round-23 claim in full.** Probes
   7-17 cover all six filed red probes plus the ns case: sha drift → 1 naming the pin,
   mtime-only drift → 1, missing binary → 2, bad pin value → 3 with no traceback,
   missing/null/non-mapping `measured_against` → 1 `VACUOUS`, one pin deleted → 1
   `PIN_ABSENT`. Text and `--json` agree on the code in every case (#18). The guard is
   deterministic (#19) and its `--self-test` is `0/46` on the copy (#5). No defect found
   in `check_substrate_pins.py`.
2. **ns-exactness holds on the landed body** (#10): a 1 ns mtime move is `delta_ns=-1
   tolerance_ns=0` → exit 1. The round-22 M4 finding 3 (canonical prototype blind to 1 ns)
   is closed by the landed `parse_iso_ns` precision-aware tolerance.
3. **The harness check-pin surface is where the regression lives.** Four classes, two of
   them silent:
   - **Silent class A (#26, #27):** deleting a `zero`- or `positive`-mode entry from
     `checks` leaves the gate green. `evaluate` never reads the baseline for those modes
     (`verify_harness_claims.py:560-564` set `ok` before the baseline branch at `:566`),
     so 11 of 28 entries (10 `zero`, 1 `positive`) are documentary-only — deletable with
     every gate green, the same shape as the round-21/22 `measured_against` debt that
     round 23 just closed. A `checks` block that is *read* can be deleted without a red.
   - **Silent class B (#28):** setting all 11 zero/positive `expect`s to `999999` also
     stays `28/28`. The baseline is not the checked source for those rows; the CHECKS
     table's literal is.
   - **Loud class (#22-25, #33):** the 17 `equal`/`at_least` entries ARE load-bearing —
     a corrupted expect, a deleted entry, or a flipped `mode` all red with the check id
     named. (Note #25: the baseline's `mode` field is documentary; the CHECKS table's
     mode decides.)
   - **Crash class (#30-32):** a structurally corrupt `checks` (`KeyError`), a list, or a
     non-mapping entry throws a **raw traceback** at `verify_harness_claims.py:569` with
     exit **1**, contradicting the script's own docstring contract (`:28-30`: "2 the
     environment is unreadable (missing binary / db / log); 3 no baseline found").
     `bad JSON` also exits **1** here (vs the pin guard's 3, #21) — so a broken baseline
     is indistinguishable from real drift by exit code, and the traceback is the only
     signal. The pin guard closes exactly this class for its own document (round-22
     P6/D1); the harness gate never got the same treatment.
4. **The two gates are complementary and neither covers the other's document.**
   #37: the pin guard exits 0 on a check-corrupted baseline (correct — it owns
   `measured_against`). #7-20: the harness gate exits 0 on every `measured_against`
   corruption (its documented scope). Between them, `baseline.json` as a whole has no
   single reader that fails on any structural corruption: the pin guard catches
   `measured_against` corruption but ignores `checks`, and the harness gate catches
   `equal`/`at_least` corruption but silently ignores `zero`/`positive` and crashes on
   structural `checks` damage.
5. **`grep -c measured_against` (#36)** confirms the debt closure is exactly one file —
   `check_substrate_pins.py:18`. The round-23 claim "0 readers across the six instruments"
   → "1 reader" reproduces.
6. **Claim-E count evidence for this lane:** the harness gate prints `28/28` (#1) and the
   baseline has 28 `checks` entries with `Counter({'equal': 15, 'zero': 10, 'at_least': 2,
   'positive': 1})`; `verify_surfaces.py` emits **7** PASS/FAIL lines (SCORECARD's "4
   checks" is stale, per claim E's fifth file); `verify_harness_claims` doc sites still say
   27 (`SKILL.md:109,456,461`, `corpus/README.md:34`, `corpus/knowledge/harness-verifier-round10.md:15,186`).

## Defects named (each: path:line + evidence)

1. **`verifiers/verify_harness_claims.py:560-564` (vs `:566-573`) — 11 of 28 baseline check
   entries are unread, so they are deletable/rewritable with the gate green.**
   Evidence: probe #26 (`checks.pop("oc.log.available_skills_hits")`) → `28/28 checks pass`,
   exit **0**; #27 (zero-mode `omp.catalogue.missing_names` deleted) → same; #28 (all 11
   zero/positive `expect`s → 999999) → same. `evaluate` sets `ok` for `mode == "zero"`
   (`:560`) and `mode == "positive"` (`:562`) before the `elif baseline is None` branch
   (`:566`), so `baseline["checks"][cid]["expect"]` (`:569`) is never consulted for those
   rows. Contrast #33: deleting the 17 equal/at_least entries gives `11/28`, exit 1 — the
   silence is mode-specific, not a general "baseline optional" design. This is the
   round-21/22 "unread pin block" defect class recurring one document deeper, and it
   contradicts `:35` ("regenerate … `verifiers/baseline.json`") in spirit: a regenerated
   block can lose 11 rows unnoticed.
2. **`verifiers/verify_harness_claims.py:569` — a structurally corrupt `checks` crashes
   with a raw traceback and exit 1 instead of the documented 2/3.** Evidence: probe #30
   (`checks` key removed) → `KeyError: 'checks'` traceback, exit **1**; #31 (`checks: []`)
   → `AttributeError: 'list' object has no attribute 'get'`, exit 1; #32
   (`checks["omp.db.rows"] = 14`) → same `AttributeError`, exit 1. Docstring contract at
   `:28-30` reserves 2 for "environment unreadable" and 3 for "no baseline found"; neither
   fires. Probe #21 shows the sibling guard handles the identical inputs with `NO_BASELINE`
   exit 3 and no traceback, so the fix shape already exists in-repo
   (`check_substrate_pins.py:127-135`, the `isinstance` guards).
3. **`verifiers/verify_harness_claims.py:650` — `json.loads` of an unparseable baseline
   propagates `JSONDecodeError` as exit 1.** Evidence: probe #21 `bad JSON` → traceback +
   exit 1, where the pin guard returns 3 (`NO_BASELINE`). Same class as defect 2; grouped
   separately because the fix site differs (`:650` needs a try/except around `json.loads`,
   `:569` needs a type guard in `evaluate`).
4. **`verifiers/verify_harness_claims.py:555-573` — an unrecognised id in `checks` is
   invisible.** Evidence: probe #29 (add `zz.bogus.check`) → `28/28`, exit 0. Iteration is
   over the CHECKS table only, so a `checks` entry that no longer corresponds to any check
   is neither reported nor rejected. The pin guard's counterpart behaviour is the
   `UNSUPPORTED` verdict (`check_substrate_pins.py:157-162`, discovered pins that cannot be
   resolved → exit 2), i.e. the sibling already implements the fail-closed reading of the
   same situation.
5. **Not a defect, recorded to prevent misreading — `verifiers/check_substrate_pins.py`
   exits 0 on a check-corrupted baseline (probe #37).** Correct by contract: the guard owns
   `measured_against`. The coverage gap in finding 4 is the *pair's*, not this file's; any
   round that wants whole-document integrity must extend one of the two.
