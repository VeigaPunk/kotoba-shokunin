## Findings

**F1 — the whole ladder is non-vacuous and matches the round-23 record, probe for probe.**
Every red class named in `SCORECARD.md:116` / `LOG.md:1231` /
`corpus/knowledge/substrate-pin-guard-round23.md:36-43` reproduces with the same exit code and the
same verdict word: sha drift 1, mtime-only drift 1, missing binary 2, corrupt baseline 3, missing/null
block 1 `VACUOUS`, deleted pin 1 `PIN_ABSENT` (commands 5-17, 21-25). Precedence 3 > 2 > 1 > 0 holds
in both directions (23, 24). No probe anywhere produced a `Traceback`. **Zero regressions found.**

**F2 — red-before replays exactly, and needs the census for its full pin.**
With the *full* 64-hex round-18 shas (`corpus/knowledge/instruction-surface-census-round13.md:22`
for omp, `corpus/knowledge/opencode-extraction-round14.md:96` for opencode) the replay is
`exit 1 DRIFT 2/3` naming both pins (command 20), byte-identical whether the script is the live one
or the /tmp copy (33). The round-23 docs quote only 8 hex (`ff59fc1b…`); the replay is therefore
reproducible *only* by an operator who goes to the census. Not a defect — a note for whoever writes
the round-24 record: pin the full 64 hex, or the ellipsis, once.

**F3 — the guard is hermetic in a `.git`-less export, unlike its checklist sibling.** Commands 2-4:
`cp -a` with `.git` removed, a `git archive` export, and `cwd=/` all give the same `OK 3/3 pins hold`,
because the default baseline is `Path(__file__).resolve().parent.parent/verifiers/baseline.json`
(`:56`, `:256-257`) — no cwd probe, no `git` call, no fixture lookup. Directly relevant to claim H:
the pins guard is an existing in-repo precedent that the "resolve relative to the script" fallback
works in an export, and the guard needs no equivalent of the checklist's `:386-392` heuristic.

**F4 — the `--self-test` "over `verifiers/fixtures/pins/`" claim is documentation-only.**
Five tracked sites say the self-test runs over the committed fixture dir (`SKILL.md:465`,
`SCORECARD.md:116`, `LOG.md:1231`, `corpus/README.md:57`,
`corpus/knowledge/substrate-pin-guard-round23.md:35`). The code reads none of it: `--self-test`
writes its own `mini.bin` into a `tempfile.TemporaryDirectory` (`:299-302`) and every case is
generated in tmp; `strace` shows **0** opens under `fixtures/pins` (command 28) and
`grep -c fixtures verifiers/check_substrate_pins.py` → **1**, the `--help` string at `:250`.
The committed `mini.bin` is byte-identical to the generated one (`d3b4640e…`, command 30) — i.e. the
dir records the fixture design, it does not supply it. `mini2.bin` and the 0755 `tripwire.bin`
sentinel (the hash-never-exec assertion's tripwire) are referenced by **nothing executable**:
`grep -rn 'fixtures/pins'` over tracked files hits only the five doc sites. Freshness-class defect
(doc vs code); no gate depends on it, so the fix is wording, not code.

**F5 — a mapping with only metadata keys reads as `PIN_ABSENT`, not `VACUOUS`.**
`verifiers/corpus-baseline.json` has `measured_against = {repo, head, head_subject, git_status,
command, note}` — no pins. Pointing the guard at it yields `exit 1` with 3 × `PIN_ABSENT`
(command 29), while the guard's docstring (`:14-17`) and the round-23 record both describe "the block
declares no pins at all" as `VACUOUS`. Both are exit 1 and both are fail-closed, so this is a naming
imprecision, not a hole — but the corpus baseline is the one live file that exercises it, and the
round-24 record should say which word covers it.

**F6 — the sha-drift line never prints the live sha, unlike the mtime line.** `:225-226` prints
`expect` and `observed` for sha drift, but the mtime DRIFT line (`:220-222`) prints only
`pinned_ns`/`observed_ns`/delta/tolerance. Cosmetic asymmetry in the reporting surface; both name the
pin. No behavioural consequence.

**F7 — claim-E supporting measurement (sibling slice owns the erratum).** Live
`python3 verifiers/verify_harness_claims.py` → **`28/28 checks pass`**, exit 0 (command 31), while
`SKILL.md:109`, `SKILL.md:456`, `SKILL.md:461` and `corpus/README.md:34` still say 27/27/27/27.
This is independent live evidence for claim E item 2 (the 27 → 28 errata).

**F8 — corrected self-measurement (recorded for honesty).** My first read of the census's omp sha
used `grep -o 'ff59fc1b[0-9a-f]*'` on `:22` and printed 63 chars; the value in the file is **64**
(`ff59fc1b484c1308a7247ad208305005627b3fac62b440737c2b183ac32074e`), and my own reconstruction from
the `…074e` tail is byte-identical to it. The 63-char reading was an artefact of my extraction, not a
defect in the census. No defect filed on it.

**F9 — blind spot left by design (no defect, recorded for the round-24 record).** A pin key outside
`DISCOVER_RE` (`^[a-z0-9_]+_binary_[A-Za-z0-9]+$`) is silently outside the checked set:
`omp_binary_sha256_v2`, `OMP_binary_sha256` and `omp.binary.sha256` all pass `OK 3/3` (command 19).
So "a deleted pin cannot shrink the set silently" is true for the three contract keys and for
well-formed discovered keys, but a *renamed* key is invisible. Out of scope for a red probe (no
round-24 claim covers it); named so it is not mistaken for coverage.

  probes (5, 9, 20), not from a real binary change.
- Did not re-run the round-21/22 archaeology for why `ff59fc1b…` was the round-18 sha; took the
  census and round-14 record as the source of the red-before strings.
- Did not check the *other* verifiers' red behaviour (surfaces, checklist, corpus integrity,
  independent, fault-injection) — sibling slices own those; only the harness gate was run (command
  31) and only for its 28/28 count.
- Did not exercise `--json` for every verdict (only DRIFT; the round-23 record claims text/`--json`
  agreement and the shared `VERDICT_CODE` table makes disagreement a code-level impossibility I did
  not test).
- Did not test on Python < 3.14; the docstring requires ≥ 3.11 and this host runs 3.14.7.
- Did not evaluate whether the five stale "27 checks" sites are all in claim E's scope — only
  measured that they are stale (F7).
- Did not adjudicate `mini2.bin`/`tripwire.bin`'s fate (delete vs keep as record); that is a
  round-24 decision, and deleting them would change a tracked-file count in the corpus baseline.
