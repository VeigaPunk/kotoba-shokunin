## Findings

**F1 — the `10` is real but host-conditional; 19/19 is the reading at HEAD.** At `d49dfa5`
on this host the author instrument (with `--no-baseline`) and the independent instrument both
read `report_dead=19/19`, exit 1, with **identical** shapes `{relative 9, absolute 8,
tilde 1, bare 1}`, `report_total=19`, `commit_total=18`, `commit_nonhash=1`,
`unresolvable=0` and the **identical 19 dead sites**. So the reproduce block's
`report_dead=10/19` (line 285) and §2's `report_dead` 10 (line 63) do not reproduce at HEAD.

**F2 — the round-12 number was not sloppy arithmetic: it was the host's path base.** The
recorded ten sites are `corpus/README.md:23,24,25,26,27,28,36,37,38` (the nine `../.ufo/`
rows) + `corpus/lessons/round-3.md:5` (the one bare token). Those ten are exactly the tokens
that die *independently of the host base*. The other nine sites are the eight host-absolute
(`/home/vgpnk/...`) plus one `~`-anchored token. Reconstructing the round-12 host state —
a private mount namespace where the lowercase `/home/vgpnk/projects/shokunin/.ufo/reports`
exists (command 7) — reproduces `report_dead=10/19` with **byte-identical shapes and totals**.
LOG.md:864 (round 17) records that this lowercase base is now absent ("every checked pointer
used the absent lowercase `/home/vgpnk/projects`, while the observed report tree is
`/home/vgpnk/Projects`"), which dates the flip. So: the correct erratum is not merely
`10`→`19`; the count is **host-conditional**, and the recorded ten was valid on a host that
carried the lowercase base. The record's §3 "host-anchored / not hermetic" finding is the
same property — §3 already knew the count moved with the host (it wrote "W0 from 10 to
19/19 dead" when the host `.ufo` was hidden), it just did not connect the default reading to
the base's presence.

**F3 — the `43 = 37` is a real tree-state glue, and the pairing is backwards for HEAD.** Both
halves are true numbers, on *different trees*:

- `43` is the **pre-round-12 `633859f`** live-tree reading — verified with the *pre-repair*
  script (`git show 4dd7753:verifiers/verify_corpus_integrity.py`), which reads 43 at
  `633859f`, and with the repaired script, also 43, and with the independent, also 43.
- `37` is the **pre-round-12 `7d15407`** reading, and also the reading of the round-11 tree
  `4dd7753` — on `7d15407` the repaired scanner and the independent agree at 37/37.

The sentence sits in §2, whose whole point is that the two instruments agree **on the live
tree**, and its neighbouring numbers (39 tracked / 25 pointers / 23 commits / shapes
`{absolute 24, tilde 1}`) are all `633859f`-era. On that tree the independent reads
`index_tokens=43`, so the `= 37` contradicts the sentence's own tree state. Neither 43 nor
37 occurs in the `d49dfa5` printout either (that tree reads 32). The honest sentence is
`43 = 43` for `633859f`, with the 37/37 figure labelled to `7d15407`.

**F4 — the errata is gate-neutral and applies cleanly.** The five-site patch (`/tmp/h24/errata.py`,
applied to a clone; diff 5 hunks / 13 net lines) leaves every gate byte-identical in outcome:
corpus `9/9 checks pass` exit 0, independent exit 0, surfaces exit 0, harness `28/28 checks
pass` exit 0, pins `OK 3/3` exit 0, corpus `--self-test` 88 assertions/0 failures,
independent `--self-test` 52/0, checklist `--self-test` 1504/0. The corpus gate stays 9/9
because `index_patterns`/`report_total`/`commit_total` are `equal`-mode (baseline-relative)
and the patch changes no count. The only difference between the unpatched and patched runs is
the tmp directory name echoed in a message string.

**F5 — an independent corroboration of the erratum target.** `LOG.md:1214` (round 23) already
names "the round-12 record's `10/19` (now `19/19` at `d49dfa5`)" as documentary debt, and
`SCORECARD.md:42` lists "round-12 10/19" among the standing errata candidates. So the target
value is agreed; what this scout adds is the *mechanism* (F2), which determines the wording.
