## Findings

**F1 — the PASS verdict holds; the slice's figure "518" does not.** Live HEAD `b889e78`
SKILL.md is **521 lines** (sha256 `84257c62…`, worktree == HEAD, commands 1-3), and
`trigger.line_budget` **PASSes: `evaluated 521 — 521 lines within budget 600 (from box at
line 244)`**, rc 0, in full (#4), filtered (#5), and `cp -a` copy (#6) modes. Headroom is
79 lines. The slice's "518" is the **round-23 probe value**, not the landed one: `dc4c0c0`
added a 5-line §Sources bullet (516→521, commands 9-10), while round-23 scout D7's
"518" was a 2-line-insert simulation on the then-516 file (#23 reproduces it exactly).
So the *verdict* (PASS, well within 600) is confirmed; the *number* 518 is a stale
round-23 draft figure. If round 24 records 518, the correct landed value is 521.

**F2 — gate counter vs `wc -l`: agreement on every normal file, and the gate is the
stricter one on the two divergence classes.** The gate counts `len(text.splitlines())`
(`verify_skill_checklist.py:1805`), `wc -l` counts newline bytes. On all 7 tracked docs
they agree (#11). They diverge only when (a) the file has no final newline — `wc` 520 vs
gate 521 (#13) — or (b) a line carries a non-`\n` Unicode separator such as U+2028 — `wc`
520 vs gate 521 (#14). In **both** cases the gate counts *more* lines than `wc`, i.e. it
is conservative: a `wc -l`-based claim can never *under*-report the gate's number. The live
SKILL.md carries no exotic separators and ends in `\n` (#12), so the two counters are
identical (521 == 521) with no hazard.

**F3 — threshold boundary and source re-verified.** PASS is `n ≤ limit` (strict `>` at
`:1090`): 599/600 PASS, **601 FAIL** (#15), on real files and via direct calls (#16). The
limit comes from the **box**, not `--max-lines`: exactly one box matches `LINE_BOUND_BOX_RE`
(`:362-363`), at `SKILL.md:244` (`- [ ] File ≤ 600 lines; …`), first-integer `600`
(`INT_RE`, `:364`, `box_line_budget` `:1073-1081`). `--max-lines` applies only when no box
matches (#15/#16, `from --max-lines`). A second, later budget-like box does **not** win
(#16) — first match wins, matching round-23 M5's note.

**F4 — the export PASSes the line budget (claim-H touchpoint).** In the `git archive HEAD`
export (no `.git`), `trigger.line_budget` is **PASS 521** (#18) — the line-budget check is
cwd/git-independent and survives the export. The export's *other* reds (#19: `name_directory`,
`citation_resolves`, `governance.citation_resolves`) are copy-location artifacts — `../.ufo/`
and `../PROTOCOL.md` are outside `git archive`'s scope (the export ships 452-`.ufo`=248
tracked files; `.ufo/` is tracked but its `../` siblings are not) — the same artifact class
round-23 C1 recorded. The line-budget check itself is unaffected.

**F5 — an adjacent freshness defect in the same file (evidence for claim E item 5).** The
harness check count is stale in the SKILL.md prose: `SKILL.md:109` `**27 checks**`,
`:456` `27/27 checks`, `:461` `27 checks` — but the live gate prints **`28/28 checks pass`**
(#20, rc 0) and `--self-test: 0 failure(s) over 10 assertions` (#21). So `27` should be `28`
at all three SKILL.md sites (and the harness doc's own `27 checks` at
`corpus/knowledge/harness-verifier-round10.md:15,186` — claim E item 2's territory). The
`27/27` at `:456` is inside a round-10 historical record line ("re-verified … 27/27 checks")
and should be corrected with the historical-record convention, exactly as claim E requires.
