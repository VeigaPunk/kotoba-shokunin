## Findings

### The convention, stated from the repo's own rule

`PROTOCOL.md:135` — *"A filed report is a record: a correction to it lands in the
correcting round's own report, or as an erratum appended after the filed bytes in a
new commit and naming the text it supersedes — never a rewrite of the filed bytes,
labelled or silent."* Reinforced at `:349` ("Corrections sweep every mention") and
`:351` ("A falsified claim in an append-only file gets a named correction entry …
appended, never rewritten"). The in-tree precedent is the census's own
`**Round-18 errata (…, append-only)**` block (`:10`) and `**Historical note
(append-only errata)**` (`:164`), and the harness doc's dated parenthetical
(`harness-verifier-round10.md:112-114`). So the compliant form is: **keep the old
value, add the new value with a date/round label and provenance**.

### The gate the drafts do not mention: commit-citation counting

`verify_corpus_integrity.py` counts `commit \`<token>\`` citations across tracked
corpus `*.md` (`:139-140`) into `corpus.pointers.commit_total`, an **equal-mode** pin
(27). An erratum whose *provenance* is written in the repo's own citation idiom —
`commit \`b889e78\`` — adds one citation and flips the gate: measured
`commit_total 27 → 28`, exit **1** (command 6). The bare form `HEAD \`b889e78\`` does
**not** (command 5, exit 0). None of the five drafts uses the `commit \`<hex>\`` form
(command 7), and F3's round-23 block uses the safe bare `HEAD \`5a33c3e\``, so the
drafts as written are safe — but this is the trap the E lane must carry forward: **an
errata block in a corpus file must cite provenance as a bare `HEAD \`<hex>\`` (or a
sha256), never `commit \`<hex>\`.** This is the single real way claim E's "documentary
erratum" can flip a gate.

### Assertion-count archaeology (resolves an E1/E3 disagreement)

= **75**, round 18 = **70**, HEAD = **75**. Consequences the drafts get partly wrong:
