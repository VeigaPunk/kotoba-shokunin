## Findings

### 1. The live check count is 28; the round-10 doc says 27 — delta is exactly one id
`CHECKS` (command 4) = 28 ids, baseline `checks` = 28 (command 5), live run prints
`28/28` (command 1). `git show abef8aa` (command 6) proves the round-10 landing was

`("equal", "skills_rescan_max")`; pin `verifiers/baseline.json:121-124`, observed
live `3`). The same commit flipped the two permission ids `at_least → equal`.
Round 18 (`02302c5`, `LOG.md` § Round 18) is the provenance.

The docs that still say 27: `corpus/knowledge/harness-verifier-round10.md:15`
(`**27 checks**`) and `:186` (`| real host | exit 0, 27/27 |`); `SKILL.md:109`,
`SKILL.md:461`; `corpus/README.md:34`. All five are present-tense / self-described
as live (`:3-4` calls the doc "the human-readable half"; `SKILL.md:462` calls the
script "the authority for every harness number in this file"). Dated citations
(`SKILL.md:456`, `SCORECARD.md:28/65`, `SHONEN.md:20`, `LOG.md`, the round-N
lessons, the round-12 census) are correct as history and must not be swept —
`SHONEN.md:20` is dated ("round-10 harness-claim verifier (… 27 checks)") and is
not the round-24 E target ("SHONEN anchors" there are the PROTOCOL anchor).

**S5-only:** the delta is provable from git alone, so a landing lane need not
trust any doc's number: `git show abef8aa:verifiers/verify_harness_claims.py` →
`grep -c '": ("'` on the `CHECKS` block = 27.

### 2. Six of the eleven `oc.*` checks are live-vacuous (documentary debt)
The four log grammars the doc's rationale table (`:126-130`) relies on are absent
from the live log (command 7: 0/0/0/0; only `skills rescanned` survives, 13 lines).
Command 8 shows the six move on a crafted log, so they are not dead code — a PASS
today carries no evidence about the live catalogue, because the surface it reads
is gone:

| id | mode | pin | observed | why vacuous |
|---|---|---|---|---|
| `oc.log.init_count_max` | equal | 0 | 0 | no `message=init count=` lines |
| `oc.log.init_count_monotone` | zero | [] | [] | same source |
| `oc.dup.roots_both_sided` | equal | 0 | 0 | no `duplicate skill name` lines |
| `oc.dup.onesided_roots` | zero | [] | [] | same source |
| `oc.permission.skill_lines` | equal | 0 | 0 | no `evaluated permission=skill` lines |
| `oc.permission.skill_allow` | equal | 0 | 0 | same source |

The other five `oc.*` checks are live: `oc.log.skills_rescan_max` (equal 3),
`oc.roots.names_plus_builtin` (equal 7), `oc.roots.plugins_cache` (zero, false),
and `available_skills_hits` / `skills_tag_hits` (both zero, and sound as
*absence* checks — documented as such). So `28/28 PASS` certifies 22 checks with
live content over the two harnesses.

**S5-only:** the `+builtin` addend in `oc.roots.names_plus_builtin` is structurally
0 — command 14 finds no `customize-opencode` bytes in the installed 210 MB

So the doc row at `:126` ("builtin `customize-opencode` confirmed present in the

### 3. `at_least` is dead code and the doc's sentence about it is false
`evaluate()` (`verify_harness_claims.py:555-576`) reads the mode from `CHECKS`
(`:557`) and never from the baseline's per-check `mode` field (only `expect` is
read, `:569`). No `CHECKS` entry uses `at_least` (command 4), yet
`verifiers/baseline.json:109-117` still declares `mode: at_least` for the two
permission ids — a baseline/CHECKS mode mismatch on 2 ids (verified: mode diff
printed for `oc.permission.skill_lines` and `oc.permission.skill_allow`). The
`at_least` branch at `:573` is unreachable in every live run. Consequently
`corpus/knowledge/harness-verifier-round10.md:201-202` ("`oc.log` is append-only
and grows; snapshot checks there are `at_least`, so a log rotation would read as a
regression rather than a change of record") is **false**: the append-only log's
snapshot check (`oc.log.skills_rescan_max`) is `equal`/3, so a fourth rescanned
skill reads as DRIFT, exactly the failure mode that sentence claims is avoided.
