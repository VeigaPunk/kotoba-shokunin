## Findings

**F1 — the round-23 mtime-only red probe reproduces exactly as filed.**
Rows 1-9. A `/tmp` copy of `verifiers/baseline.json` with only
`measured_against.omp_binary_mtime` moved exits 1, names `omp_binary_mtime`,
prints `mtime drift (sha256 not compared)` with the exact `delta_ns` and
`tolerance_ns=0`, and leaves both sha pins `PASS`. It is ns-exact in both
directions (rows 2-3, ±1 ns). The record's wording — corpus/README.md:57,
SCORECARD.md:32,116, corpus/knowledge/substrate-pin-guard-round23.md:39-40,
LOG.md:1231 — is accurate as written.

**F2 — both drift directions are covered, and the pair is the guard's real
strength.** Row 23: replacing the bytes and restoring the pinned mtime to the
nanosecond is caught by the sha pin while the mtime pin passes. Row 24: moving
only the mtime by 1 ns with identical bytes is caught by the mtime pin. Neither
signal alone covers the other's blind spot; the round-23 record's claim that the
guard catches "the 2026-10-16 silent-rebuild class" is supported by measurement.

**F3 — offset restatement is instant-based, not text-based (rows 10-15).**
The same instant declared at `+02:00`, `-03:00`, `-04:00`, `-07:00` all `PASS`;
identical wall-clock text declared at a different offset `DRIFT`s with the
correct multi-hour `delta_ns`. This is the behaviour a pin document needs — a
re-pin may be written in any zone — and it is worth recording because the
docstring does not state it.

**F4 — coarse pins are honest, not silent (rows 16-18).** A 6-digit pin's
window is `999 ns` and a whole-second pin's is `999999999 ns`, both printed in
the PASS line (`tolerance …`); 10 fractional digits is `BAD_PIN` exit 3. The
guard cannot be weakened by writing a sloppier pin without the sloppiness
showing up in the output. **Consequence for the round: the live pin is 9-digit,
so `tolerance_ns=0` and `delta 0 ns` are the strongest possible readings — the
documented `delta 0 ns` is not an artifact of a loose window.**

**F5 — read-only, deterministic, hash-never-exec all confirmed independently
(rows 25-28).** Three outputs byte-identical; baseline and tree digests
unchanged across a run; `strace` shows exactly one `execve` (the interpreter);
no `EXECUTED` sentinel appears in `fixtures/pins/`. This re-derives round-23
scout V3's single-execve result.

**F6 — the pins guard's `--self-test` is the clean template for claim H
(rows 29-34).** `0 failure(s) over 46 assertions`, byte-identical on repeat, and
identical from cwd `/`, `/tmp`, the clone, and a `git archive` extract with no
`.git` anywhere. In the *same* extract, `verify_skill_checklist.py --self-test`
is `108 failure(s) over 1504 assertions`, exit 1 — scout F8's defect reproduces
exactly, at the same assertion total as the green clone run, which pins the
cause to fixture-path resolution rather than missing fixtures. The named
fallback is `find_repo_root()` at `verifiers/verify_skill_checklist.py:386-392`
("Nearest ancestor carrying a .git marker, else the file's directory") — the
pins guard has no such heuristic: its self-test builds every case in a
`tempfile.TemporaryDirectory` and its only repo-relative constant is
`DEFAULT_REPO = Path(__file__).resolve().parent.parent` (`:56`), used for the
default baseline path, never for the self-test. That is the shape claim H's fix
should copy.

**F7 — the live pin set and the record's digests re-derive (rows 45-47).**
Guard sha `fafe88d881eb…` and `mini.bin` `d3b4640e…` match the round-23 record;
474 lines as recorded; the "874 ns" parse-trap figure re-derives exactly from
`datetime.fromisoformat(pin).timestamp()` on the live pin.

**F8 — claim E's live values, re-measured at HEAD (rows 41-44).** Harness
`28/28` (docs 27); surfaces `7` checks, `38` ids, `5/5` opencode classes from
`6/6` rules, `9` excluded, self-test `75` assertions (SCORECARD.md:30 and :68
say `4 checks`, `28 assertions`, `41-class`/`41 entries`; round-9 lesson and
round-14 record say `9/9 opencode classes from 7/7 rules`). Each of these is a
documented stale count, so claim E's premise holds. The pins guard is **not**
wired into any sweep runner (`grep -rn check_substrate_pins` over `*.sh`,
`*.json`, `*.toml` outside `.ufo/round-2[234]/` is empty), and
`verify_skill_checklist.py` reports 10 checks that do not include it — so claim
E's "no gate flips on the corrected text" is not automatic: `trigger.citation_resolves`
and `governance.citation_resolves` in the checklist gate scan the corrected
files' citation tokens (38 and 198 tokens evaluated at HEAD), and a corrected
count that happens to be written as a bare `path:N` citation would be read by
those checks. Any errata touching a `file:line` form should be re-run through
`python3 verifiers/verify_skill_checklist.py` before landing.

## Defects named (each: path:line + evidence)

**M7-D1 — the mtime branch reports `DRIFT` (exit 1) where the contract promises
`UNREADABLE` (exit 2) for a pinned path that stats but cannot be read.**
`verifiers/check_substrate_pins.py:187` — `live_ns = binary.stat().st_mtime_ns`
— needs only `stat`, so it succeeds on a directory or a mode-000 file, and the
`except OSError` at `:188-191` never fires; the code then compares that
filesystem-object's mtime against the binary pin and reports `DRIFT`. The
docstring at `:16-18` reads "2 a pinned binary **cannot be read or stat'd**
(UNREADABLE)".
Evidence, row 35: with the omp sha pin deleted from a `/tmp` baseline copy and
`--omp-binary` pointed at a directory —
`FAIL omp_binary_mtime: mtime drift (sha256 not compared): pinned_ns=2026-10-16T05:15:11.226207850-03:00 observed_ns=1792388048415439459 delta_ns=249537189231609 tolerance_ns=0`,
summary `DRIFT 2/3 pins failed`, **exit 1**. Row 36 repeats it with a mode-000
file (`delta_ns=249537191263892`, exit 1). Row 37 shows the missing-path case
still exits 2 correctly, which isolates the defect: it fires only when `stat`
succeeds but the path is not a readable regular file. Severity is real but
narrow — with the shipped baseline both pins are present, the sha branch reads
the file first and returns `UNREADABLE` (exit 2) on the same broken path, so
`code_of` still yields 2. The tier is lost only when the sha pin is absent,
i.e. exactly the P7-C9/PIN_ABSENT configuration the guard is otherwise careful
to keep loud, and the operator then reads a nonsense `delta_ns` (~2.9 days)
attributed to a binary that was never a binary.

**M7-D2 — the sha256 path hangs the guard forever on a FIFO or an unbounded
device.** `verifiers/check_substrate_pins.py:93-98` (`sha256_of`) opens the
pinned path and reads to EOF with no size cap, no `O_NONBLOCK`, and no
regular-file check.
Evidence, rows 38-39: `timeout 10 python3 … --omp-binary $D/fifo` → exit 124
(killed, no output); `--omp-binary /dev/zero` → exit 124. Row 40 shows
`/dev/null` terminates, so this is not "any non-regular file" but specifically a
path that never reaches EOF. A guard whose contract is "a red guard is fixed by
re-record plus a mechanism note" should not be able to wedge an unattended
sweep; the round-23 docstring's determinism claim (`:34` "no wall clock, host,
pid or duration appears in either mode") is silent on blocking IO. Not
reachable from the shipped baseline (the pinned paths are regular files), so
this is a robustness gap rather than a live red.

**M7-D3 — the shipped `--self-test` cannot see M7-D1: its only directory-path
case uses the opencode path.** `verifiers/check_substrate_pins.py:399-400`
asserts `binary is a directory: exit 2` via `run(world(), "--opencode-binary",
str(tmp))`; `opencode` has no mtime pin in `world()`'s baseline, so only the
sha branch runs and the assertion passes for a reason unrelated to the mtime
branch. The cases that do point `--omp-binary` at a broken path (`:396` missing,
`:405` dangling symlink, `:410` mode 000) all still exit 2 because the omp sha
pin runs first and raises `UNREADABLE`. A one-line addition — point
`--omp-binary` at a directory in a baseline whose omp sha pin is deleted, and
assert exit 2 — would fail today and close the gap. Evidence: rows 35-37 versus
the 46-assertion self-test passing at row 29.

## Limits (what I did NOT verify)

- **No code change was made and none is proposed as landed.** M7-D1/D2/D3 are
  named from `/tmp` probes only; I did not patch `check_substrate_pins.py`, did
  not touch the live tree beyond read-only runs, and did not verify that a fix
  would leave the 46 self-test assertions green.
- **M7-D1's tier loss is conditional.** I did not test it with the shipped
  `verifiers/baseline.json` unmodified — with both pins present the sha branch
  short-circuits to exit 2 first, so the defect only manifests with the omp sha
  pin absent. I verified that configuration deliberately; I did not enumerate
  every other way to reach it.
- **The hang (M7-D2) was measured with `timeout 10`.** I did not confirm the
  read is truly unbounded (versus merely slower than 10 s), and I did not test
  other blocking special files (sockets, `/dev/random`, NFS-stalled paths).
- **Host-anchored results.** Rows 1-9, 20-21 and 41-47 read this host's real
  `~/.local/bin/omp` and `~/.opencode/bin/opencode`; they are statements about
  this installation, not about any clone. The export run (row 31) is green only
  because the host binaries exist.
- **Claim H is not decided here.** I reproduced F8 (row 33, 108/1504 exit 1) and
  measured the pins guard's cwd-independent self-test as the template, but I did
  not draft, apply, or test any patch to `verify_skill_checklist.py`, and did not
  re-run the checklist's red probes to check non-vacuity after a hypothetical
  fix. The claim's "LANDS ONLY IF the /tmp simulations are unanimous" condition
  is the H lanes' call, not mine.
- **Claim E counts were re-measured, not corrected.** I confirmed the live
  values (row 41-44) and that the guard is unwired, but I did not enumerate all
  seven stale sites' exact line numbers, did not verify that the proposed new
  values are the only ones in each file, and did not run the gate sweep after a
  hypothetical correction.
- **Self-test assertion count semantics.** I observed `46` (pins guard) and
  `1504`/`75` (checklist/surfaces) but did not audit how each counter is
  incremented, so I cannot say whether `46` is a count of assertions or of
  `rec()` calls.
- **`/tmp` is not private.** A sibling lane deleted `/tmp/h24/M7` mid-run; any
  lane reproducing rows 22-24 must re-create its own fake binary and re-pin it,
  because the pinned ns differs on every write.
