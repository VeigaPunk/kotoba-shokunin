## Findings

### F2-1 — All three pins HOLD; the hold is the ns-exact kind, verified at integer resolution

| pin (`verifiers/baseline.json`) | pinned | live | verdict |
|---|---|---|---|
| `omp_binary_sha256` (:5) | `bf1e86a935…54974` | byte-identical digest | **HOLD** |
| `omp_binary_mtime` (:6) | `2026-10-16T05:15:11.226207850-03:00` = `1792138511226207850` ns | `st_mtime_ns = 1792138511226207850` | **HOLD, ns-exact (0 ns delta)** |
| `opencode_binary_sha256` (:8) | `d9123b9bcd…13218c9` | byte-identical digest | **HOLD** |

No drift anywhere; zero pins drifted since round-21's re-pin (omm ctime `…511523208909` is
mtime+297 ms — the install/copy stamp, consistent). Consequence for the landing round: a
green-on-arrival guard means the red-before-green evidence **must** come from mutated
`/tmp` baseline copies (P1 vectors 9–12), not from the live substrate. This is the first
independent re-measurement of the round-21 pins by a lane that did not write them.

### F2-2 — opencode's mtime is a synthetic archive stamp, and the baseline correctly refuses to pin it

`/home/vgpnk/.opencode/bin/opencode`: `st_mtime_ns = 499162500000000000`
(1985-10-26T05:15:00-03:00 = 1985-10-26T08:15:00Z) while `st_ctime_ns =
1791733805098997789` (2026-10-11) and its parent dir mtime is Oct 11 12:50. The mtime
precedes the file's arrival on this host by ~41 years: it is carried by the archive, not by
installation. `measured_against` has **no `opencode_binary_mtime` key** — correct, and worth
preserving as an invariant. A guard that "completed" the pin set by adding an
`opencode_binary_mtime` would create a pin that cannot move on a normal upgrade
(archive-preserved stamp) — a forever-green check, i.e. an inert pin wearing a green badge.
The spec's "mtime ns-exact for **omp only**" is therefore load-bearing, not stylistic.

### F2-3 — Two different `opencode` artifacts are reachable; only one is the pinned binary

`which -a opencode` returns two paths: `~/.opencode/bin/opencode` (210 109 920 B ELF, sha
`d9123b9b…` = **the pin**) and `~/.local/bin/opencode` (1460 B **bash script**, sha
`b240efa9…`, mtime 2026-10-03 = a wrapper, *not* the pin). PATH order favours the pinned
one *today*, on this host, for this shell. Any guard that resolves the opencode path through
`shutil.which("opencode")` / `PATH` lookup inherits a one-line-PATH-edit failure: it would
happily hash a 1460-byte wrapper and then report DRIFT (noisy) or, if the pin were ever
re-derived from a live lookup, pin the wrapper (silent, wrong). The default must be the
absolute path `~/.opencode/bin/opencode`. Same directory also holds `omp-swarm` and the
pinned `omp`, so prefix/glob resolution (`*omp*`) is unsafe in both directions.

### F2-4 — The pin is nanosecond-precise; float64 cannot represent it, so the "obvious" comparator is wrong

Two independent float traps, both reproduced:

* `datetime.fromisoformat(pin)` keeps only microseconds (`.226207`), and `.timestamp()`
  rounds through a float: `int(…*1e9) = 1792138511226206976` → **−874 ns** vs live
  (command 12; independently confirms P1 cmd 5).
* Even the integer value itself does not survive float64: `float(1792138511226207850) =
  1.7921385112262077e+18`, `int(float(...)) = 1792138511226207744` → **−106 ns**; `math.ulp`
  at this magnitude is **256 ns**. At ~1.79e18 ns, one float step is a quarter microsecond.

Net: a comparator using floats *cannot* implement "ns-exact". Smallest working discipline:
integer-only math on `st_mtime_ns` and on a fraction-preserving parse of the pin string
(`re` 9 digits → `int`, `calendar.timegm(...)*10**9 + frac`). Both `k_int` and P1's
`k_fromiso` idiom satisfy this — verified equal on the real pin (command 13, drift 0 → HOLD).

### F2-5 — Drift fixtures built through floats silently shrink the delta under test (P7 class, fixture layer)

This is the finding I would most want in the merged design, because it makes a *passing*
test suite meaningless rather than red.

Command 13 vs 14, same comparator, different fixture builders:

| drift written | integer-built fixture encodes | float-built fixture encodes |
|---|---|---|
| `+0 ns` | `+0` | `.226208` = **+150 ns** |
| `+1 ns` | `+1` | `.226208` = **+150 ns** |
| `+128 ns` | `+128` | `.226208` = **+150 ns** |
| `+256 ns` | `+256` | `.226208` = **+150 ns** |
| `+512 ns` | `+512` | `.226208` = **+150 ns** |
| `−256 ns` | `−256` | `.226207` = **−850 ns** |
| `−512 ns` | `−512` | `.226207` = **−850 ns** |

A float-built fixture collapses seven distinct drifts into **two** strings (and both are
microsecond-formatted, so the generated pin no longer even *looks* ns-precise). A self-test
that loops `for drift in (0, 1, 128, 256, 512): assert comparator(...)` built this way will
report "5 assertions pass" while never once testing the ns field it claims to test — and,
because `.226208 ≠ .226207`, it will not even be self-contradictory. Silent shrink, hidden
inside the harness. Fix: fixtures must be built with `divmod(ns, 10**9)` + `%09d`
construction, and the self-test should assert that the **fixture's** ns value equals the
intended drift *before* asserting the comparator's verdict (P4 idiom + one pre-assertion).

### F2-6 — Pin-key selectors: the pin set is 3 keys inside a 6-key prose block

`measured_against` (6 keys, all `str`): `omp_binary_sha256`, `omp_binary_mtime`,
`omp_round21_note`, `opencode_binary_sha256`, `command`, `round18_move`. The three binary
pins are the only verifiable ones; the other three are prose (a 179-char note, a command
line, an 850-char round-18 narrative). A prefix selector (`startswith("omp_")`) picks up
`omp_round21_note` and would try to verify prose; a hard-coded count (`len(pins) == 3`)
turns a deleted pin into a silently smaller green set (P7). What survives both failure
modes: an explicit allowlist of the three pin keys, plus a "PIN_ABSENT"-style named failure
when an allowlisted key is missing (P1 cmd 17 shape) — and the observed key set reported in
`--json` so the count is visible rather than inferred.

### F2-7 — Cost is negligible; the guard can afford to verify both binaries on every run

Measured `sha256` at 2.4 GB/s: omp 104.6 ms + opencode 85.8 ms ≈ **0.19 s** of the run
(P1 measured 0.223 s end-to-end, consistent). No caching, sampling, or "hash only when
mtime moved" optimisation is warranted — and a conditional hash would reintroduce exactly
the trust-the-mtime weakness that F2-2/F2-9 show is cheap to forge.

### F2-8 — What the pin actually attests (scope statement for the guard's `--help`/docstring)

`cp -a`'d copy of omp at `/tmp/d23/copyprobe/omp-copy` matches **both** omp pins
(sha ✓, `mtime_ns` ✓) at a different inode (`484741` vs `19958702`) and a different path.
So the pins attest **bytes + mtime**, never path/identity/authority: they answer "the bytes
described by round 21 are the bytes on disk, and the mtime is untouched", not "this is the
binary the harness ran". Forging the mtime half costs one `os.utime` call; forging the sha
half costs 2^256 work. The load-bearing pin is the digest; the mtime is a cheap tamper hint
that catches the realistic failure (a silent rebuild whose digest *also* changed, i.e. the
round-18/round-21 scenario). Worth one sentence in the guard's docstring so no reader
over-claims it as an identity check.

### F2-9 — P6 TypeError class reproduced from the outside

Feeding a non-`str` pin into the fraction parser yields
`TypeError: expected string or bytes-like object, got 'NoneType'` (and the same for
`int`/`list`/`dict`/`bool`). A guard that reaches `re.search(pin, …)` before an
`isinstance(pin, str)` check dies with a traceback (uncaught → exit 1, no named pin) instead
of a named `PIN_MALFORMED`/exit 2–3. Live `measured_against` is all-strings today, so this
cannot fire from the committed baseline; it fires the moment a re-pin writes an int ns or a
JSON `null`, which is *the* most likely re-pin mistake. Type validation must precede parsing
for every pin key.

1. Integer-only ns math; never `timestamp()`/float. Pin → ns via 9-digit fraction + `timegm`.
2. Defaults are absolute paths `~/.local/bin/omp` and `~/.opencode/bin/opencode`; never PATH.

4. `isinstance(pin, str)` before any regex.
5. Self-test fixtures via `divmod` + `%09d`; assert the fixture's own drift first.

## Limits (what I did NOT verify)

* **Nothing was executed.** I did not run `omp --version` / `opencode --version` (no
  `--version`, no `--help`): no process of either binary was started, deliberately — this
  lane is hash+stat only (`hash-never-exec`). Consequently the version claims in the
  baseline prose (`v18.11.1`, `v2.0.26`) are **not** re-verified here; only bytes and mtime.
* **No TOCTOU test.** I did not race a rebuild against the hash (stat→hash window ~0.19 s,
  cmd 10). A rebuild landing mid-run is a real (small) false-hold hole in any stat-then-hash
  or hash-then-stat order; the cheap mitigation (re-`stat` after hashing and require a stable
  `st_mtime_ns`) is proposed, not tested.
* **No landed guard was run** — `verifiers/check_substrate_pins.py` does not exist (cmd 19);
  my comparators are scratch under `/tmp/d23/` (`nsexact.py` + heredocs), never in the repo.
* **Single host, single filesystem, single reading.** No cross-host or cross-FS mtime
  behaviour; no repeated sampling over time; no verification that the pins hold for any
  second process's view of the same files.
* **Did not hash the other artifacts** reachable in the same directories
  (`~/.local/bin/omp-swarm`, `~/.local/bin/opencode` wrapper, `~/.opencode/bin/opencode2`):
  only `file`/`ls`/`sha256` on the wrapper (cmd 9). Same for `~/.local/bin/omp-swarm`.
* **Did not touch** the skill/db/catalogue/checklist axes of claim P (other lanes), nor
  `LOG.md` (round rule: this lane writes only this fragment — the LOG entry is the
  integrator's step). No git-mutating command was run; the tree remains at `5a33c3e` with
  `?? .ufo/round-23/` as the only status line.
* **Write scope.** The only repo file written by this lane is this fragment. All probes wrote
  strictly under `/tmp/d23/` (`nsexact.py`, `copyprobe/omp-copy`); the live binaries were
  opened read-only; no `cp`/`touch`/`utime` was ever applied to a live path.
