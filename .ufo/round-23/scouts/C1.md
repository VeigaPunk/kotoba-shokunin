## Findings

**F1 — Verdict on the claim.** `type: "capability acquisition"` is correct per `AXES.md:40-41`
("A claim may instead be a capability acquisition …; it still lands a per-axis verdict"), and
the axis (freshness = drift detection against live surfaces) is right: the pins are the only
substrate-drift witness no gate reads. The capability table exists with the entry rule
(`SCORECARD.md:109-115`, placeholder `:113`), so the claim's "first row" target is real, not
aspirational. What is not yet sound is the *battery*: three of the six probes do not instrument
what the claim says they instrument (D1, D2, D8), two named defect classes have no probe at all
(D7, D8), and the merge recipe's body contradicts two of the claim's own words (D3, D2).

**F2 — Probe (e) is satisfied by the defective artifact (fatal for the P6 closure).**
`claims.json:36` specifies "(e) missing/null `measured_against` -> exit 1 (vacuity, the M6-D2
defect class)". Measured: the canonical prototype on `{"measured_against": null}` exits **1**
with a `TypeError` traceback (cmd 11) — i.e. the exact P6-D1 defect state *already exits 1*. The
probe as specified cannot distinguish hardened from defective; worse, it is **violated by the
fix**: the ladder the claim names (`claims.json:34`) puts "no `measured_against` object" at exit
**3**, and P6's hardening recommendation is exit **2** (`P6.md` D1: "emit the
UNREADABLE/VACUOUS-style stderr + exit 2"). A probe whose designed code equals the defect's code
is not a falsifier. Fix = exit 2-or-3 **and** the "no Traceback" clause that probe (d) already
carries.

**F3 — No probe for a non-string pin value (P7-C1 class).** `claims.json:36` has no probe for a
present-but-wrong-typed pin. Measured on the canonical body: `{"omp_binary_mtime": 12345}` →
exit 1 + `TypeError` (cmd 14). The brief's "P6 TypeError class MUST be closed" is therefore only
half-instrumented: (e) covers the non-mapping *block*, nothing covers the non-string *value*.

**F4 — No `--json` probe, though the mode-divergence class is an in-repo precedent.**
`claims.json:36-37` never mentions `--json`. This repo has already shipped exactly that defect:
`verify_harness_claims.py` returns 0 in `--json` where the text path returns 3 (round-21 F1-D2,
cited in `P1.md` F1 and `P8.md` 2b), and P7-C4 records the canonical's JSON error path emitting
0 bytes of stdout. The probe battery should assert code equality across both modes on at least
the (a)/(d)/(e) paths; today nothing does.

**F5 — Hidden trade, measured: the corpus re-record is under-specified by one field.**
The claim (`claims.json:36`) and the C4 skeleton (`.ufo/reports/round-23/kotoba.md`, "corpus-baseline
`tracked_files` 52 → 53") name only `tracked_files`. Measured in the landing's shape (cmd 7-8):
with the committed baseline the corpus gate exits **1** on **two** DRIFTs — `tracked_files` 53
*and* `report_total` **36** (expect 34), because the new doc and the README row each cite a
report pointer, matching the round-21 precedent note (`corpus-baseline.json:53`: "report_total
32 -> 34 (the new file and the new README row each cite the round-21 report)"). A re-record
implemented exactly as the claim writes it leaves the corpus gate red at landing — a
self-inflicted red gate, which `PROTOCOL.md` §Gate standard (Closure consequence) records as a
routable conformance defect. (If the landed doc cites no report pointer, only `tracked_files`
moves; the landing round should measure, not assume.)

**F6 — Hidden trade, measured: the SKILL.md gate-registry row is missing from the plan.**
`PROTOCOL.md:383` ("a child lane's *registry home* is its own `SKILL.md`") and `:405-406`
("closure grades no gate conformant until its registry row exists at the lane's *registry
home*") make the registry row a conformance requirement, not a style choice; the row's fields
are `name, gate|probe, entry command, verdict map, self-test command and spelling, pinned-value
path, write scope, owner` (`:386-388`). Neither `claims.json:34-38` nor the skeleton's landed-
changes list includes it, and the skeleton states "Intentionally unchanged: `SHONEN.md`,
`PROVINCE.md`, `SKILL.md`". `SKILL.md` today carries instrument bullets as prose (`:456-489`)
but no registry vocabulary at all (`grep -i "registry|verdict map" SKILL.md` → 0 hits), so the
landed gate arrives non-conformant. Cost is now nil, measured (cmd 17): one inserted bullet →
`line_budget` 517 (budget 600) PASS, and the checklist gate's three counts shift without any
pinned equality moving (`command_binary_resolves` 13→15, `citation_resolves` 35→38, both PASS)
— **no baseline re-record is forced by a SKILL.md bullet**.

**F7 — Probe (f) vs the merge recipe: the presence source is an unstated design element.**
`claims.json:36` demands (f) "deleted single pin -> exit 1 PIN_ABSENT", and the round's chosen
recipe is "canonical body + P1 exit-ladder" (P7's merge, `SCORECARD.md:40`). Measured: the
canonical body alone prints `OK 2/2 pins hold` exit **0** on the shrink input (cmd 9) while the
P1 prototype prints `PIN_ABSENT` exit **1** (cmd 10). So (f) cannot be delivered by the canonical
body as it stands: the design must add an explicit expected pin-key set — an element *no
prototype has* (P1 hardcodes three keys and thereby misses stray pins, P7-L3; canonical discovers
generically and thereby misses disappearances, P7-C9). The round-23 skeleton already records the
canonical's exit-0 as the motivating red (good), but the design decision is unrecorded in
`claims.json`; the landing must specify the key set *and* keep canonical's stray-pin catch, or
(b) and (f) will be green while a re-pin that *adds* an unknown pin stays invisible.

**F8 — The mtime contract is self-contradictory between the claim text and its own body.**
`claims.json:34` says "mtime ns-exact for omp"; the body the recipe names implements
`MTIME_TOLERANCE_NS = 2000` (cmd 16), and the claim's probe (b) (±1 s) passes under both
semantics. Measured boundary (cmd 15): pin −1 µs → PASS, pin −2 µs → `DRIFT omp_binary_mtime`,
µs-truncated pin → PASS. P1-F2's "ns-exact or the pin false-reds" and P7's "the ±2000 ns
tolerance is load-bearing" are different contracts; the claim inherits one and states the other,
and nothing in the battery discriminates them. One probe pair (Δ≤2000 ns vs Δ>2000 ns, plus a
µs-truncated pin) settles it and should be in the self-test.

**F9 — Capabilities-row honesty: achievable, but the claim does not say which run is the row's
evidence.** `AXES.md:57-64` admits a row only through a round that *demonstrates the capability
running*; a row without a passing demonstration is pre-claiming. The honest vehicle here is the
**committed** `--self-test` (P4's mutation cases on committed fixtures + `mkdtemp` scratch) plus
the in-round live run at a named commit; the six `/tmp`-copy probes are *not* closure-durable
pointers (`PROTOCOL.md` §Evidence standard: paths under `/tmp` "are not evidence — commit the
artifact or cite a reproducible command"), and P8's drafted row pointer is exactly a `/tmp`
red-before run. The claim's falsifier does anticipate the cheat ("the capabilities row claimed
without the demonstrated run") — but nothing in the battery designates the durable evidence, so
the round can land a true row or an asserted one and both look alike in the report. Also
measured: the pins hold live *today* at `5a33c3e` (cmd 3), so green-after is real and cheap;
red-before must come from mutated copies, and its durable form is the self-test, not the probe log.

**F10 — Falsifier quality.** The falsifier (`claims.json:38`) is well-aimed — it names the probe
mismatch, the traceback class, the never-exec property, and the capabilities-row abuse. But three
of its clauses have no counting command behind them: "any execution of omp/opencode binaries
(opencode.log must not gain lines)" (no probe does a before/after `wc -l` on that log, nor a
canary fixture), the JSON-mode clause (F4), and the capabilities-row clause (F9). One clause —
"any red probe exiting differently than specified" — is defeated by (e) being specified to the
defect's code. A falsifier without an instrument is an assertion; four of six probes are
instrumented today.

**Bonus finding (plan correction).** `P1.md` F5 asserts "`verifiers/corpus-baseline.json` pins
`corpus.index.tracked_files` …; a tracked new file under `verifiers/` moves it". Falsified by
measurement: the metric is `git ls-files corpus/` (`verify_corpus_integrity.py:6,433-435`), and
adding two tracked files under `verifiers/` left it at 52 (cmd 6). The claim's own 52→53 for the
corpus doc is right; the plan's reason was not.
