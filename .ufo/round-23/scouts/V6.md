## Findings

### F1 — The 874 ns trap reproduces exactly, on the live pin

`int(datetime.fromisoformat("2026-10-16T05:15:11.226207850-03:00").timestamp() * 1e9)`
= `1792138511226206976`; live `os.stat("~/.local/bin/omp").st_mtime_ns`
= `1792138511226207850`. Delta **−874 ns**. A guard written the naive way reports DRIFT on a
pin that is exactly right (P1 cmd 5, independently reproduced here with the same numbers).

### F2 — Decomposition: −850 ns truncation + −24 ns float grid

`fromisoformat` keeps only 6 fraction digits, so 850 ns of the pin is discarded before any
float appears (µs-truncated integer value `1792138511226207000`); the remaining −24 ns is the
float round-trip: the `timestamp()*1e9` product reaches `1.792e18`, past float64's 2^53 integer
range, whose ulp there is **256 ns** (the seconds float itself has ulp 238.4 ns). The error is
not a constant: over pins with the same µs and varying sub-µs digits the naive route errs
−24 ns (digits `000`) to −924 ns (digits `900`) — proportional to the digits it silently
drops. So a float-route guard would false-DRIFT by a *value-dependent* amount.

### F3 — Integer-ns comparison is exact and 1-ns sensitive; float comparison fails both ways

- `parse_iso_ns` (P1 recipe: `re` fraction digits `ljust(9,'0')[:9]` + `calendar.timegm`) gives
  `1792138511226207850` == live `st_mtime_ns` — integer equality matches with **zero tolerance**.
- Int compare detects a **+1 ns** pin (DRIFT, delta 1 — P1 cmd 11 reproduced).
- Float compare is the wrong instrument in *both* directions: (a) fed through
  `fromisoformat×timestamp` it false-DRIFTS (−874); (b) even between two ns-exact integers it is
  blind over a measured **−234..+22 ns** window at this value and misses **99.6 %** of 1-ns
  drifts (false PASS). Exactness is available; tolerance is only needed by lossy reads (D1/D2).

### F4 — The draft guard uses `stat().st_mtime_ns` (slice requirement)

`/tmp/d23/V6/v6_mtime_draft.py` (42 lines, sha256 `4dade147b74b2bf10590447582862253c04293a6f66ea7b8be749e601648b0fb`):
`observed = os.stat(path).st_mtime_ns` (line 20) and `observed == parse_iso_ns(pin)` — the
compare path contains no float token (grep: only the deliberately-naive probe line uses one);
`st_mtime_ns` is an int everywhere. 4/4 probes green, TZ-independent, tz-naive pins rejected.
Matches P1's prototype (`/tmp/P1/check_substrate_pins.py:65-76`: `os.stat(path).st_mtime_ns`,
`int(observed) == parse_iso_ns(expect)`) and P4's fixture prototype
(`/tmp/round22-p4/check_substrate_pins.py:71` `path.stat().st_mtime_ns`, `:123` ns-int pins).

### F5 — Merge-recipe hazard: the canonical body's mtime slot is NOT ns-exact (A/B proven)

The round-23 merge recipe takes "canonical body + P1 exit-ladder + P4 self-test idiom". The
canonical body (`/tmp/check_substrate_pins.py`, P5, sha `92627710…`) trims the pin to 6 fraction
digits (`:54-66`) and compares with `abs(live_ns - expect_ns) <= MTIME_TOLERANCE_NS = 2000`
(`:42`, `:98-106`). A/B on the same µs-truncated pin file: canonical **exit 0** (`PASS … delta
850 ns`), P1 body **exit 1 DRIFT**. If the canonical mtime path lands verbatim, the claim's
"ns-exact" wording is falsified by construction and the pin's last three digits are inert. The
mtime slot must take P1's `parse_iso_ns` + exact equality and the tolerance constant must be
deleted — with the ns-exact body the tolerance is not merely unnecessary, it is the defect.

### F6 — Scope facts around the mtime machinery

- Only omp carries an mtime pin (`measured_against` keys); opencode's mtime is synthetic
  (`st_mtime_ns 499162500000000000`, 1985-10-26) and stays unpinned — the ns machinery guards
  omp only, as P1 F3/P2 already specified.
- omp is a regular file (`lstat` mtime == `stat` mtime), so `stat()` follows nothing here.
- No repo verifier reads `st_mtime_ns` today (`verifiers/*.py` grep); the landed guard would be
  the first mtime-pin consumer in the tree.

## Defects named (each: path:line + evidence)

- **V6-D1 (blocker-for-merge, inverse of the trap) — `/tmp/check_substrate_pins.py:42` +
  `:98-106`:** `MTIME_TOLERANCE_NS = 2000`, `delta = abs(live_ns - expect_ns); ok = delta <=
  MTIME_TOLERANCE_NS`. Evidence: A/B probe above — accepts the µs-truncated pin (exit 0, delta
  850 ns) that P1's body reds; and any real drift ≤2000 ns (e.g. +1 ns re-touch, or the 850 ns
  the live pin actually encodes) is a silent PASS. Fix: exact integer equality (tolerance 0);
  write pins from `st_mtime_ns`.
- **V6-D2 (major, same file) — `/tmp/check_substrate_pins.py:54-66`:** `iso_to_epoch_us`
  deliberately truncates the fraction to 6 digits (`re.match(r"^(.*\.\d{6})\d*(.*)$")`),
  discarding the digits the pin encodes; the discarded residue surfaces as `delta_ns = 850` on
  the live pin and is neutralised only by D1. Fix: P1's 9-digit fraction → integer ns
  (`/tmp/P1/check_substrate_pins.py:48-61`).
- **V6-D3 (minor, permissiveness inherited by my draft from the P1 recipe shape) — draft
  `/tmp/d23/V6/v6_mtime_draft.py:11-18`:** the base string goes to `datetime.fromisoformat`,
  which on Python ≥3.11 accepts non-`T` separators — `"2026-10-16 05:15:11.226207850-03:00"` is
  accepted (probe 6). Not a claim falsifier (pins are authored in-repo), but the merge should
  not claim a strict ISO shape it does not enforce; a `^…T…$` regex closes it.
- **Note (re-frames P2-V3 / P7-C6 as designed behavior, not defects):** a µs-precision pin MUST
  red — that is the writer's error signal (my draft probe 3, delta −850; P1 cmd 12). Any
  tolerance added to accept 6-digit pins reopens V6-D1. Corollary for the landing round: the
  re-pin ritual must emit `st_mtime_ns`; a pin written by any µs-truncating tool is a defect in
  the pin, provably detectable.
