## Findings

### F1 — The decision is about an event class this repo has never observed, and the live state is green in all four prototypes
The pin parses to the live inode **ns-exactly** (cmd 1: delta 0) and the omp mtime has held
`…11.226207850` for 3+ days across rounds 21→23 (cmd 2). Every recorded substrate movement in this
repo's history moved the **sha** as well (`LOG.md:896` round 18 `55016ef5→ff59fc1b`;
`LOG.md:1210`/`SCORECARD.md:32` round 21 `ff59fc1b→bf1e86a9`). So there is **no alert-fatigue
evidence** to weigh against mtime-strictness, and simultaneously no observed instance of the
mtime-only branch firing. Both facts matter in F2: the cost of exit 1 is unmeasured-but-plausibly-zero
(it has cost nothing so far because it has never fired), and the *benefit* is also unmeasured —
the verdict below is therefore about which failure mode is worse, not about a measured frequency.

### F2 — Q1 verdict: **exit 1 for mtime-only**, distinct reason; the case for exit 0 loses on family mechanics, not on semantics
The honest strongest case for exit 0: content identity is what every downstream invariant actually
depends on (`baseline.json:3` `omp.elf.template_sha256`, and the cache keys derived from it are all
content-derived), so a byte-identical rebuild invalidates nothing downstream; mtime is a packaging
artifact (opencode's own is the synthetic `1985-10-26`, i.e. mtimes are something packers *normalise*);
and `cp`/`touch`/archive-restore produce exactly this signature without any substrate event
(P1 cmd 22: plain `cp` → sha same, mtime moved). That case is real but it loses on three measured
points:

1. **There is no advisory tier to put it in.** `grep -rin warn verifiers/*.py verifiers/*.sh` → 0
   matches (cmd 4). Nothing in this repo consumes a verifier's stdout as a gate; the gate is the
   exit code plus the human/agent reading it in the same turn. "Report it but exit 0" therefore
   degenerates into "record the pin, read the pin, and never let it red" — i.e. the round-21 named
   debt re-created one layer down, which is precisely the P7 defect class (a recorded fact that
   cannot fire) that this round must close. Exit 0 must keep meaning *exactly as recorded*.
2. **It is the only witness of its class, and the class is reachable.** Byte-identical content is
   invisible to sha by construction; mtime is the sole witness. Reachability is not hypothetical on
   this host: sibling CLIs ship as versioned installs (`~/.local/bin/{agent,cursor-agent,devin}`
   → `~/.local/share/*/versions/…`, cmd 3), where re-running the same version is a normal
   operation; and a byte-identical rebuild is exactly what a reproducible-build toolchain produces.
   The freshness axis's stated purpose (P8 §capabilities row: catch the class the 2026-10-16 rebuild
   passed unnoticed) is *unannounced substrate rebuild*, which is what this is.
3. **The remedy is cheap and bounded.** Re-record the pin once, naming the mechanism — the
   `round18_move` / `omp_round21_note` idiom already recorded in `baseline.json:7,10`. The distinct
   reason string is what prevents fatigue: the operator sees *provenance-only* movement
   (`sha256 unchanged`) vs a content move.
4. Corroboration that this is not only P4's opinion: canonical (P5), P1 and P3 all independently
   landed exit 1 for the mtime-only case (cmd 5, case `c2-mtime-only+1s`: exit 1, 3/3 prototypes,
   reason string naming `omp_binary_mtime`), and the round-23 claim text already specifies it.
   **Rejected alternative** (recorded, not chosen): a distinct exit code 4 for provenance-only
   movement — the family ladder is 0/1/2/3 (`verify_surfaces.py:107-109`,
   `verify_corpus_integrity.py:82-87`), the claim text names 1, and automation branching on
   an unknown code is worse than one exit code plus a precise reason string.

### F3 — Q2 verdict: **two findings, one per pin key, never suppressed**
Measured reporting matrix on the both-move case (cmd 5, case `c3-both`: omp sha→64×`0`,
omp mtime→+1 s, live binary untouched):

| design | exit | findings | mtime finding present |
|---|---|---|---|
| canonical (P5), per-pin rows | 1 | 2 | yes |
| P1, per-pin rows | 1 | 2 | yes |
| P3, per-kind rows (sha / mtime / declared) | 1 | 2 | yes |
| **P4 stub, per-pin-row with `elif` suppression** | 1 | **1** | **no** |

P4 is the outlier, and its own self-test does not exercise the decision: case (b) *restores* mtime
to the pinned value (`/tmp/round22-p4/check_substrate_pins.py:139` `os.utime(target, ns=(ns0, ns0))`)
and then asserts `"mtime drift" not in out` (`:151`) — an assertion that is trivially true under
either design, because in that mutation the mtime genuinely does not drift. **The 4-case set
(a)-(d) contains no both-move case at all**, so the suppression contract is asserted but never
tested. Three measured reasons to report both:

1. **Convergence, measured** (cmd 7): an operator who re-pins every value the guard prints reaches
   green in **1 red run** under per-pin rows; under suppression, run 1 shows only sha, so the
   operator re-pins sha, and run 2 reds again on mtime — **2 red runs**, one extra full-hash run
   (0.22 s live + a re-edit of the same block). The guard's own remedy ("re-record deliberately")
   is the thing being made slower by suppression.
2. **Different facts, different obligations**: `omp_binary_sha256` and `omp_binary_mtime` are two
   recorded keys with two re-record obligations; reporting both is not double-reporting the same
   fact. Canonical's DRIFT summary already names each moved pin (`P7.md` finding 1); P8's landing
   plan (§2b) says exit 1 is "DRIFT naming **each** moved pin" — suppression contradicts the
   plan's own wording.
3. **Structural interlock with the P7 class**: the per-key table that produces per-pin findings is
   the same structure that closes the silent-shrink class. Re-measured in cmd 5 (case
   `c7-mtime-key-del`, `omp_binary_mtime` deleted): canonical's regex discovery → **exit 0, silent
   shrink** (`OK 2/2 pins hold`, = `P7.md` C9); P1's fixed table → exit 1 `PIN_ABSENT`; P3 → exit 1
   per-kind vacuity (`0 mtime pin(s) declared`). An `elif`-per-binary loop has no row left to hang
   the missing-key verdict on and has to bolt presence detection back on.
   **One refinement P4 could not express**: keep the distinct reason string, and let it *name the
   discriminator* — `mtime drift (sha256 unchanged)` vs `mtime drift (sha256 also moved)`. That
   preserves P4's legitimate goal (the reader can tell provenance-only movement from an ordinary
   rebuild) without encoding it as *invisibility*.

### F4 — The exit-1 verdict is only executable if the comparison is ns-exact (tolerance 0) and the FAIL line is re-pinnable
Two coupling facts, both measured, that must land with the F2 verdict or it degrades:

1. **Tolerance is a dead zone on this exact decision.** Canonical compares with
   `MTIME_TOLERANCE_NS = 2000` (`/tmp/check_substrate_pins.py:42`, used at `:106`). Measured
   (cmd 5): a pinned mtime of **+1 ns** and of **+1200 ns** both exit **0** under canonical, while
   P1 and P3 exit 1. The tolerance exists solely to absorb the µs-truncating parser
   (`/tmp/check_substrate_pins.py:14,57,65-66`), but the ns-exact recipe measures **delta 0** on the
   live pin (cmd 1), so the tolerance buys nothing and costs the round's own contract: the round-23
   claim says "mtime **ns-exact** for omp". Either the guard is ns-exact (then probe (b) is
   well-defined: any ns movement → exit 1) or it is fuzzy (then probe (b) has no defined boundary).
2. **Neither of the two divergent prototypes can round-trip its own prescription.** CANONICAL prints
   the live instant µs-truncated in UTC (`:160` prints `r['live']`, built at `:73` `dt.isoformat()`):
   `2026-10-16T08:15:11.226207+00:00` — 850 ns short of the truth. Measured (cmd 8): writing exactly
   that string back as the pin → canonical exit **0** (its tolerance hides the 850 ns it just
   dropped) but P1 and P3 exit **1** — so the "deliberate re-record" remedy *degrades the pin*, and a
   later ns-exact design immediately reds on a baseline that canonical itself told the operator to
   write. P1 prints the observed as an **ns integer** (`observed='1792138511226207850'`), which is
   not the baseline's pin syntax: writing that back yields a rejected pin (measured: exit 1, row
   `omp_binary_mtime DRIFT expect=1792138511226207850 observed='1792138511226207850'` — expect and
   observed are the *same digits*, an unactionable diagnosis; P3 handles the same shape cleanly with
   exit 3 `ERROR … missing/empty string value`, canonical crashes with a `TypeError` traceback).
   **Requirement for the merged design**: the mtime FAIL line must print the observed instant in the
   pin's own syntax (offset-aware ISO-8601, exactly 9 fractional digits, same offset convention),
   optionally alongside ns integers. Then a re-pin is a copy of the printed token, and the exit-1
   remedy is mechanical.

Verified, not just proposed: `/tmp/f10/merge_stub.py` implements F2+F3+F4 for the mtime row
(per-key findings, no suppression, ns-exact, discriminator in the reason, ISO-9 token in the FAIL
line) and its `--self-test` is green — `0 failure(s) over 17 assertions` (cmd 9), including a
both-move case (two findings, `mtime drift (sha256 also moved)`, exit 1), an mtime-only case
(`sha256 unchanged`, one finding), and a **one-red-run** re-pin convergence assertion. That last
case is the assertion P4's 23-assertion set lacks.

### F5 — Provenance footnote the merged design should declare (not fix)
ctime is the only witness of "rewrite then restore mtime" (it cannot be set by `os.utime`), and it is
live-measurable (cmd 2: ctime = mtime + 297 ms), but it is not `cp -a`-stable and moves on metadata
ops, so it is correctly not pinnable. Likewise the mtime pin's witness role is layout-dependent: for
a symlinked install (`agent`/`cursor-agent`/`devin` on this host, cmd 3) `os.stat` follows the link,
so a retarget to byte-identical content is invisible to both sha and mtime (P3 already names this).
Both belong in the guard's documented-limits section; neither changes the F2 verdict.
