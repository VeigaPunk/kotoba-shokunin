## Findings

**F1 — Live 9/9 confirmed at `5a33c3e`, and the self-test count matches the shipped record.**
`verify_corpus_integrity.py` exits 0 with all nine checks PASS; `--self-test` is `0 failure(s)
over 88 assertions` — the same 88 the round-11 doc pins at
`corpus/knowledge/corpus-integrity-round11.md:35`. The second witness exits 0 with the same
verdict set (equal-mode counts reported INFO).

**F2 — Blind agreement is total, and the arithmetic closes on both sides.**
My own tokenizers — written from the class spec, not importing the instrument — reproduce every
observable: 52 / 34 / 27, shapes 33 absolute + 1 tilde, 8 excluded pointer shapes, 2 quoted
commit citations, all zero-defect lists empty, and `index_patterns` 65 (my raw 66 tokens →
65 after my own brace expansion; the residual 66-vs-65 token difference is the one round-22 R4
already named at `corpus/README.md:44`). Raw-candidate arithmetic: 42 pointer candidates − 8
excluded = 34 checked; 29 commit candidates = 27 hex + 2 quoted. Independent `dead` resolution
was computed from each citing file's directory and agreed with the instrument's zero.

**F3 — The `measured_against` head pin has lagged 20 commits / 21 days, and it is inert by
construction — proven, not assumed.** `verifiers/corpus-baseline.json:6` names
`"head": "d85982d"` (2026-09-28, round-16) while HEAD is `5a33c3e` (2026-10-19); commit
`2ca8d01` (round 21) was the last to touch the file and left that field alone, because the
block is *declared historical* in its own prose
(`verifiers/corpus-baseline.json:52`, `notes.round16_redispatch`: "Historical `measured_against`
metadata above is retained as the earlier baseline record"). Inertness is executable: on a
`/tmp` clone I rewrote `measured_against.head` → `deadbee` and `measured_against.repo` →
`not-this-repo` (cmd 14) and **both** corpus instruments still exit 0. No `.py`/`.sh` under
`verifiers/` reads the field (cmd 15), and no python file in this repo's history ever
introduced it. So the head-lag is documentary debt in the precise sense: a writing, never a
reading. Everything *enforced* in the same file is current — the nine `checks` expectations
(52/34/27) verified live at cmd 3, with the refresh trail carried in the `notes` block
(rounds 19/16/21) rather than by rewriting the historical record.

**F4 — Boundary the P guard must respect: `corpus-baseline.json`'s `measured_against` is not a
pin block, and treating it as one creates a false-red or a silent-shrink fix.** The round-23
claim scopes the guard to `verifiers/baseline.json`'s three binary pins, which is right: if the
guard harvested `corpus-baseline.json` too, a green repo would go red on a by-design-historical
field, and the cheapest repair (deleting the field) is exactly the P7 silent-shrink defect
class. Recommendation for the landing round, if it wants the debt named in code: either leave
`corpus-baseline.json` out of scope explicitly (docstring line), or give it a fourth class —
documented-historical pin → exit 0 with a note, never PASS-by-absence.

**F5 — Landing arithmetic prediction (from the round-21 precedent, not measured).** Round 21
moved `tracked_files` 51 → 52 and `report_total` 32 → 34 because the new corpus file *and* its
README row each cite that round's report (`corpus-baseline.json:53`). By the same convention, a
round-23 corpus doc + README row should land at **tracked_files 53, report_total 36**
(34 + 2), `index_patterns` 65 → 67 (the new row's two tokens: file + the new `verifiers/`
instrument), `commit_total` 27 unchanged unless the new corpus file cites a commit. Recording
34 → 35 instead would mean only one of the two sites carries the pointer; the count detector
would not fail (mode `equal` only fires against a stale expectation) — it would just be
re-recorded wrong, which is why the two-site convention is worth restating in the landing note.
