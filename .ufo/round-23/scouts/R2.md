### F3 — `constant_table`'s correct resolution of `claude-md` rests on a char-class accident (risk, fail-closed)

The live dump contains a **shadowing second assignment**
`var G$ = "\u2026[cyclic reference elided for collab session]";`
(`/tmp/d23/r23/omp.txt:1130139`) *after* the real `var G$ = "claude-md"`
(`/tmp/d23/r23/omp.txt:889346`, immediately followed at `:889349` by
`Hj(u, G$, "CLAUDE.md")`). A naive
last-wins or `[^"]`-valued extractor (my first run) resolves the pair to the
shadow and **drops `omp:claude-md/CLAUDE.md` from the extracted set**. The
shipped code survives because `ASSIGN_RE`'s value class
`"([^"\\\n]{1,80})"` (`verifiers/verify_surfaces.py:296`) rejects the
backslash-bearing shadow value, so it never reaches the conflict logic
(`:300-308`) — the conflict branch never fires for this shadow. Failure mode if
it ever did match: `G$` would be conflict-dropped → group becomes
`<unresolved-var:G$>` → pair set loses `claude-md/CLAUDE.md` →
`no_uncovered_class` FAILs (fail-closed, never a silent wrong pass; and the
reverse ordering would surface an *extra* undeclared pair, which also FAILs).
Named as a design fragility with evidence, not a live defect: rows 1 and 11
both show the shipped resolution is correct today.
