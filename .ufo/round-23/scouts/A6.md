## Findings

### F1 — The blocking condition is an unsatisfiable predicate, not a form mismatch

`checkShonen` grades each box line in two coupled steps:

- `:340-341` — `if (canon !== undefined && box.text !== canon) push(…#box-text)`. `box.text` comes from
  `BOX_RE = /^- \[(.)\] (.*)$/` (`:329`) via `:333`, i.e. **everything after `- [x] `**.
- `:348-350` — the verifier-id branch runs only when `box.mark === 'x' && box.text === canon`, and then
  computes `lines[box.idx].slice(('- [x] ' + canon).length).trim()`.

Case analysis over the whole space of `box.text` for a canonical box with mark `x`:
`text ≠ canon` → `#box-text` (`:341`); `text = canon` → the guard is true, and the slice at `:349` is
taken from a string whose text is exactly `canon`, so it is **always `''`** → `#no-verifier-id`
(`:350`). The two cases are exhaustive, so **every possible `[x]` line on a canonical box yields ≥1
shonen finding**, and `:526` (`ordered.length === 0 ? CLEAN : FAILED`) turns any finding into exit 1.
The slice at `:349` tests a value its own guard has already proven empty — a dead predicate; the
gate demands a token using a variable it zeroed out. Probes: `x-bare`, `x-id`, `x-id-trailsp`,
`x-ok-id`, `x-all4-id`, `x-prose-suffix`, `x-id-in-evidence`, `x-5th` — eight shapes, all exit 1.

### F2 — The defect is not `[x]`-specific, and the id cannot be supplied elsewhere

`tilde-annot` shows the same `:341` exact-equality rule rejects an annotation on a `[~]` line, so no
box line may carry any annotation under any mark. `x-id-in-evidence` shows the id cannot be supplied
in the indented evidence line instead: the finding is identical to `x-bare` (1 × `#no-verifier-id`).
`x-5th` shows the only line that escapes the id requirement — `CANON_BOXES[b]` is `undefined` for
`b ≥ 4`, which skips both `:341` and `:348` — is itself a finding (`#box-count`), so there is no
legitimate escape.

### F3 — No suppression channel exists

The CLI (`:833-852`) accepts `--selftest | --repo | --snapshot | --all | --round | --label | --repos
| --json | --registry | --help` — no allowlist, no severity, no `--accept`. A pre-registered
exception cannot be expressed to the gate; it can only be expressed in prose beside a red exit.

### F4 — The gate never tests the conformant form; the spec's own checker saw a phantom version first

`SELFTEST_CASES` (`:766-780`, case `fx-shonen-dev`) exercises only the **bare** `[x]` (no id) plus a
prose line — the two deviations it expects are exactly today's behaviour. No case carries
`[x] <canon> <id>`, so the unsatisfiability is invisible to `--selftest`, which passes 12/12 (cmd 4).
The aggregator's own spec doc records the surrounding history: `l1-baseline.md:98-99` — *"the L1's
first pass compared each box body to a **prefix** of the canonical text and reported a phantom
verifier-id deviation on all 24 boxes"* — and `:110`/`:112` state the two requirements in adjacent
comment lines: *"text == BOX[i] exactly"* and *"'[x]' requires a `<verifier-id>` token on the mark
line"*. The prefix→exact "correction" removed the false positives and created the dead predicate;
the spec text was never checked for self-consistency.

### F5 — The requirement the fleet routes against is the unsatisfiable one

`PROTOCOL.md:417` prints the form as `` `[x] <verifier-id>` `` (no box text at all) while the gate's
own `#no-verifier-id` message reads *"carry no `<verifier-id>` token **after the box text**"* — three
readings (`[x] <id>`, `[x] <canon>`, `[x] <canon> <id>`), of which the gate implements the one that
makes its sibling check impossible. The fleet's ledger has been routing to it for 14 rounds:
`AGGREGATE.md:1667` — *"Routed per repo: add the verifier-id to the mark line (kengaku, kagi)"*; D-63
(`:721`) and §11.5 P-j (`:778`) propose mechanically requiring exactly that id; §14.7's census
(`:1643-1657`) reports *"0 of 6 `[x]` marks carry the `<verifier-id>` the mark-line form requires"*
and D-134 (`:1893`) restates it. Every one of those rows prescribes an act no lane can perform under
the gate's bytes. The census's number is right; its cause is unstated, so the deficiency has been
read as lane sloppiness rather than as a gate defect.
