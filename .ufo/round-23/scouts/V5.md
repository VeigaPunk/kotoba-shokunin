## Findings

1. **(a) The required red flip works only in the presence-enforcing drafts.**
   The canonical draft-of-record is *deaf to shrink*: deleting
   `opencode_binary_sha256` leaves a clean `OK 2/2 pins hold`, exit 0
   (independently reproduces P7 defect C9; same for omp-sha and omp-mtime).
   Deleting all three pins reaches exit 2 `VACUOUS`, i.e. the guard only notices
   at zero — a one-pin shrink is a silently narrower green. P1's hardcoded
   three-key list flips correctly (exit 1 `PIN_ABSENT` naming the key) and the
   merged candidate reproduces P1's flip *plus* names the pin in the summary
   line (`DRIFT 1/3 pins failed: opencode_binary_sha256 (pin_absent)`), which
   is what the round-23 claim's probe (f) asks for.
2. **(b) Recorded extra-pin behaviors differ in all three drafts.** Canonical:
   any `^(omp|opencode)_binary_(sha256|mtime)$` key is measured generically —
   a *correct* stray pin is absorbed and silently counted (`OK 4/4`, exit 0, no
   marker); a *wrong* stray pin is caught (exit 1, named); but a pin for an
   unregistered prefix (`cursor_binary_sha256`) is **silently ignored** (exit 0,
   `OK 3/3`) — an inert pin, the exact class this guard exists to abolish. P1:
   every extra key is invisible, including a bogus `opencode_binary_mtime`
   (exit 0) — P7 L3 reproduced. Merged candidate: recognized-prefix extras are
   measured and marked `UNREGISTERED` (holding → exit 0; wrong → exit 1);
   unregistered-prefix pins → exit 1 `PIN_UNSUPPORTED`; non-pin-shaped keys and
   prose ignored (exit 0).
3. **Contract argument (the slice's (b) deliverable).** The invariant the
   round has to keep is *"a pin in `measured_against` is never inert"*. Under it
   the two possible extra-pin classes are not the same question:
   - **Measurable extra pin (registered prefix).** *Measure, never ignore.*
     Ignore-with-note (P1, and canonical for unknown prefixes) recreates the
     debt: the file would claim a pin the guard does not check, and a NOTE line
     is read by nobody — the round-21 lesson in miniature. Between "measure and
     stay green if it holds" (canonical/merged) and "fail on any unregistered
     pin", the former is right for this repo: failing would red a
     factually-correct substrate, and the remedy ("edit code to add the key you
     already pinned correctly") conflates pin data with the enforced table. The
     merged candidate keeps canonical's measure-it behavior and adds an
     explicit `(UNREGISTERED)` marker so set growth is legible in both text and
     `--json` — a note attached to a *measurement*, not a substitute for one.
   - **Unmeasurable extra pin (unknown prefix, e.g. `cursor_binary_sha256`).**
     *Fail, not note.* The guard cannot check it, so ignoring it leaves exactly
     the inert pin the round is closing; `PIN_UNSUPPORTED`/exit 1 with the
     remedy ("register the substrate or remove the pin") is the only behavior
     that keeps the invariant. This is the strictest departure from canonical
     and the one place where ignore-with-note is indefensible. If the landing
     round prefers the repo's `mode: equal` set idiom (a red on *any* extra
     pin-shaped key), the change is one line: emit `PIN_UNREGISTERED` exit 1
     instead of measuring; but that will red a corrected re-pin until the table
     is edited, so it was not chosen.
   - Prose keys (`command`, `round18_move`, `omp_round21_note`, and any
     non-pin-shaped name such as `omp_binary_size`) stay ignored, silent, exit
     0 — they are not pins.
4. **The merged candidate is canonical-body-compatible and closes the class.**
   Green control 3/3 (0 ns delta, not canonical's 850 ns tolerance pass);
   sha-drift and missing-binary behavior mirror canonical (`DRIFT` naming /
   exit 2, empty stdout); every red probe above matches the round-23 claim's
   (a)-(f) expectations; exit ladder 0/1/2/3 with JSON `exit_code` parity in
   both modes; no tracebacks in 21 variants (canonical: 3). It also fixes two
   mtime-contract defects the merge must not inherit: canonical's flat 2000 ns
   tolerance silently swallows a **1 ns pin move** (`mtime-plus-1ns` → exit 0
   PASS) while P1's strict cells false-red a µs-precision pin (`mtime-6digit`
   → exit 1). The merged rule is precision-aware: 9-digit pins compare exactly
   (delta must be 0), shorter pins get ≤1000 ns truncation residue (documented
   limit). Its known gap: no `--self-test` (owned by sibling lanes / P4 idiom)
   and no version pins — both out of this slice.

## Defects named (each: path:line + evidence)

  discovery-derived, never declared, so a partial pin deletion is a silent
  green.** Evidence: `--baseline shrink-oc-sha.json` → exit 0 `OK 2/2 pins

  probe (f) cannot pass on this body.
- **V5-D2 (major) — canonical `:42`, `:55-67`, `:106`: a flat 2000 ns
  tolerance makes an ns-precision pin unable to see a 1 ns move,** while the
  same tolerance is load-bearing for the *correct* live pin (delta 850 ns).
  Evidence: `mtime-plus-1ns.json` → exit 0 PASS. Contradicts the round-23
  claim's "mtime ns-exact for omp".
- **V5-D3 (major) — canonical `:44` `PIN_RE` scoped to `omp|opencode`:
  a pin-shaped key for any other substrate (`cursor_binary_sha256`) is

  An ignored pin is an inert pin (P6 recorded the same boundary; this probe
  makes it a named defect with a fail-closed candidate remedy).

## Limits (what I did NOT verify)

- The merged candidate is a **probe artifact**, not the landed file: no
  `--self-test`, no committed `verifiers/fixtures/pins/`, no corpus doc,
  `SCORECARD`/`corpus-baseline` integration (52→53) — all owned by the landing
  round and sibling lanes. Its only use here is contract evidence for the
  shrink/extra classes.
- No live binary was mutated or executed; "drift after a real rebuild" remains
  proven only via baseline-content mutations (same limit as P1/P6/P7).
  `opencode.log` was not touched by any run (no exec path exists in the drafts,
  static grep).
- Extra-pin policy was probed with `opencode_binary_mtime`, `cursor_binary_sha256`,
  `omp_binary_size`, prose only; no fuzzing across other prefixes/kinds, and no
  JSON-schema-level (duplicate-key, Unicode, huge-file) cases.
- P1 was probed only through the shared battery; its `--self-test` and
  `--omp-binary/--opencode-binary` overrides were not re-run (P7 covered them).
- Python 3.14.7 only; timestamps assumed offset-carrying (naive pins treated as
  UTC by canonical and merged — not probed beyond P7's `mtime-naive`).
