## Findings

**F1 — the PATH hazard is live on this host, and the guard class must be PATH-free by
construction.** `type -a opencode` still resolves the pinned binary first, but the mise/npx
shim `/home/vgpnk/.local/bin/opencode` (1460 B, mtime Oct 3 17:44) is a real second carrier,
and any directory ahead of `.opencode/bin` wins outright (probe: with the shim dir first,
`command -v opencode` → the shim). A `which`-based guard therefore attests the wrong file:
`naive_which_guard.py` under that PATH exits 1 with `resolved=/tmp/d23/v8/shim/opencode`,
while the absolute-path guard exits 0. `env -i` with a poison-only PATH proves independence
from PATH *and* from ambient env (no `HOME` needed — the defaults are absolute strings like
`verify_surfaces.py:126-129`, not `Path.home()` derived); the zero `POISON` marker count
proves no `sha256sum`/`stat`/`which` subprocess is spawned (the hash is `hashlib` in-process
= hash-never-exec). Independent corroboration from a sibling slice this round: V9 ran an
audit hook over `open/os.*/shutil.*/subprocess.Popen/os.exec/os.system` plus
`strace -f -e trace=%file,%process` and saw exactly one `execve` (the interpreter) with no
reference to the pinned binaries (`V9.md:40-42`).

**F2 — symlink semantics are load-bearing: the guard must follow (`os.stat`), and the
anti-laundering property then holds.** Following measures the effective file: link and chain
PASS with delta 0 ns, a link to a *different* binary DRIFTs (exit 1), a dangling link is
UNREADABLE (exit 2). `os.lstat` would read the link's own mtime (`…240495191433`,
"now") against a ns-exact pin and red spuriously — a symlinked install (a plausible
packaging shape) would be a false DRIFT, not a missing file. The JSON reports the path *as
configured* (`binary: links/omp-link`), so the report cannot be mistaken for the resolved
target while the observed sha/mtime still attest the target's bytes.

**F3 — chmod 000 is exit 2, and the exit code is the easy part; the hard part is not lying
about which channel died.** `os.stat` needs no read permission, so on a chmod-000 subject the
*mtime pin remains measurable and can PASS* while the sha pin cannot be read at all. My first
implementation measured both channels in one call and reported all three pins UNREADABLE
(misleading: the mtime channel was fine). Splitting `stat_path()` (regular-file gate +
`st_mtime_ns`) from `hash_path()` (the only byte channel) yields, on the real 253 MB copy
under the live baseline: `PASS omp_binary_mtime (delta 0 ns)` + `UNREADABLE omp_binary_sha256
(open failed: [Errno 13] Permission denied)` + exit 2 — the same code, an honest report, and
no traceback (P7 probe 15's traceback is closed by catching OSError at every syscall site).

**F4 — non-regular targets are a hanging-gate hazard, cheaply closed.** A FIFO configured as
the binary makes a naive `open()` block forever (demonstrated: `timeout 5` → exit 124), and
`/dev/zero` makes it read forever. Gating on `S_ISREG` from `os.stat` *before* opening, then
re-gating on `os.fstat(fd)` after an `O_RDONLY|O_NONBLOCK` open, makes all of FIFO, character
device, directory and symlink-to-FIFO return exit 2 in 0.030 s. For a gate that may run
unattended (a healthcheck, a loop), "cannot hang" is as important as "cannot pass vacuously".

**F5 — the two must-close classes are closed at the CLI level in the merged design.**
P7-C9: deleting one of the three pins now exits 1 `PIN_ABSENT` naming it (the canonical body
exits 0 `OK 2/2` — silent shrink). P6-D1/C1: a non-string pin value is BAD_PIN exit 3 with
zero traceback lines, and `measured_against: null|5` is VACUOUS exit 1 with zero traceback
lines. Presence enforcement + `isinstance` guards are the two lines that carry this; both
must survive into the landed file.

**F6 — the mtime compare can be precision-derived, which satisfies both lineages at once.**
A 9-fraction-digit pin is compared nanosecond-exact (`allowed = 0`); fewer digits tolerate the
truncated residue (`10**(9-n)-1`). Measured: +1 ns on a 9-digit pin → exit 1 DRIFT (P1's
probe, kept sharp); the µs-truncated pin `…226207-03:00` → exit 0 PASS (P7-L1's false
positive, killed); +1 s → exit 1. A fraction-less pin is BAD_PIN exit 3 (it cannot attest
sub-second precision). My variant is strictly better than either round-22 choice (canonical's
fixed 2000 ns tolerance would green P1's 1 ns probe; P1's exact compare would red P7's µs pin)
— but two sibling slices this round measured the same pin and chose a *third* rule I now
recommend over mine: V6 and V7 keep the ns-exact compare, delete the tolerance, and reject a
coarser-than-9-digit mtime pin at load as BAD_PIN exit 3 (`V6.md:55-81`, `V7.md:101-113`;
V7 self-test s4/s5). That is fail-closed: a pin too coarse to express the subject is loud
instead of silently excusing up to 999 ns of drift. See D-V8-9 for the one measured
difference (`.226207-03:00` → exit 0 PASS under mine vs BAD_PIN exit 3 under V7's).

**F7 — relative and `~` paths behave the way argparse does, and the default baseline is not
CWD-shadowable.** A relative override resolves against the CWD; `~` is *not* expanded
(exit 2 with the literal path in the message — a footgun worth a `--help` sentence, or an
explicit `expanduser`). With the family default `Path(__file__).resolve().parent.parent`, a
`verifiers/baseline.json` planted in the CWD is ignored (explicit absolute `--repo` → 3 PASS);
only an explicit relative `--repo .` picks up the planted file, which is the operator asking
for it.

**F8 — integration costs at the new HEAD, re-measured.** `verifiers/corpus-baseline.json:15`
still expects `corpus.index.tracked_files` = 52 (round 22 never landed the guard), so landing
`verifiers/check_substrate_pins.py` + `verifiers/fixtures/pins/*` moves it; and `SKILL.md`
carries a per-instrument bullet inventory at `:456-480` (five bullets today) whose sixth
bullet has to be folded into an existing line or it breaks the round-22 line-budget repair.
Both costs are real and unpaid.

## Limits (what I did NOT verify)

- My prototype is scratch, in `/tmp/d23/v8` — not the landed file, not committed, and its
  `--self-test` spins its fixtures in a `TemporaryDirectory` at runtime instead of reading
  committed fixtures (P8 §4c calls for `verifiers/fixtures/pins/`). Assertion count 40 with 0
  failures is evidence about the design, not about a landed artifact.
- The 40-assertion self-test was run only on python3 3.14.7/this host; `env -i` runs were done
  with `/usr/bin/python3` and no `HOME`, which my absolute-path defaults tolerate — a
  `Path.home()`-derived default would not (I did not build that variant).
- I did not test NFS/`noexec`/immutable-flag mounts, SELinux/ACL denials, a chmod-000 subject
  under a different uid, or an EACCES on a *parent* directory distinct from chmod-000 on the
  directory itself (only the latter, via the self-test).
- No strace/LSM-level proof that no subprocess is spawned — the evidence is static (grep) plus
  the poison-shim marker count (0); an exec of a binary *not* named like my shims would be
  invisible to that marker.
- TOCTOU between `os.stat` and `os.open` is bounded but not eliminated (the `fstat` re-gate
  catches a swap to a non-regular file; a same-size regular-file swap between the two calls
  would only be caught by the sha compare, which is the pin's job).
- I did not verify the guard against a real opencode *upgrade* (no way to mutate the live tree
  read-only); drift probes used /tmp baseline copies and /tmp copies of the binaries.
- Concurrency: sibling scouts were writing `/tmp/pins-selftest-*` (P4-lineage leaked dirs) while
  I ran; my leak assertion was made race-free (temp-dir existence check), but the host's
  pre-existing leak count I report (32 at first count) is a moving number, not a measurement.
- The live host's `opencode.log` was not used as an "did anything exec the binary" oracle —
  concurrent lanes write it; the poison-marker and static checks are my evidence instead.
