## Findings

1. **The four asked-for ladder rungs hold on the fixed merged draft**, with zero
   tracebacks in all 16 cases (cmd 7): (a) → 3, (b) → 3, (c) → 1, (d) null → 1 and
   each non-dict → 3. Precedence 3 > 2 > 1 > 0 is real (cmds 12/17/18), and the
   `--json` path returns the same code as the text path in every probed case, with an
   `"error"`/`"exit_code"` envelope on the 1/2/3 paths (cmd 8/21) — closing P7 C4 and
   avoiding the harness's `--json → 0` defect the claim calls out.
2. **The merge boundary re-created the P6-D1/P7-C1 TypeError/KeyError class — in a new
   place, on the green path.** Draft v1 (cmd 4) carried two result schemas: PASS/FAIL rows
   `{"pin","expect","live","ok"}` and PIN_ABSENT rows `{"pin","verdict","expect","observed"}`
   (pre-fix `:82-83`, `:100-101`, `:108`). The two consumers each assumed one schema —
   `failed = [r["pin"] for r in results if not r["ok"]]` (pre-fix `:173`) raised
   `KeyError: 'verdict'`-adjacent failures and the classifier `if any(r["verdict"] in …)`
   (pre-fix `:191`) raised `KeyError: 'verdict'` on PASS/FAIL rows — so a **healthy live
   baseline exited 1 with a traceback after printing `OK 3/3 pins hold`** (cmd 13, D-V4-1).
   Fix: one uniform schema (`verdict` + `ok` on every row, renderer and classifier both
   verdict-driven; fixed `:175`, `:177`). Landing implication: uniformity of the result
   schema is a landing blocker, not a cosmetic detail — the class survives every
   behavioural probe that only inspects single-pin rows.
3. **(d) decision record the integrator must ratify.** My draft treats *missing or null*
   `measured_against` as vacuity → **exit 1** (claim letter (e), M6-D2 class) but a
   *present non-dict* `measured_against` (list/str/int/bool) as a malformed baseline →
   **exit 3** (`:159`, `:163`). Alternative readings exist: everything non-dict → 1
   (one-line change: drop the shape branch), or all shape errors → 3 including null.
   Recorded as D-V4-2; the claim's letter (a)–(f) does not settle the non-dict case.
4. **P6-D1 and P7-C1 are closed in the merged draft**, verified executably: null/int/bool
   `measured_against` → named error, exit 3, tb=0 (was `TypeError: 'NoneType'/'int' object
   is not iterable`, exit 1 + traceback, P6 cmd 12-13); non-string pin value → exit 3
   tb=0 (was `TypeError: expected string or bytes-like object, got 'int'`, P7 C1);
   EACCES while hashing → exit 2 tb=0 (was a `PermissionError` traceback, P7 probe 15).
5. **The P7 C9 silent-shrink class is closed**: the known-pin presence guard emits
   `PIN_ABSENT` for a deleted known pin (f-one-pin-missing → exit 1, cmd 7) while generic
   discovery still enforces stray recognized pins (x-stray-pin → exit 1, 1/4 failed) —
   both directions of the P7 C9/L3 duality coexist in one design.
6. **Read-only and non-executing, verified**: no write/exec call on the run path (cmd 24),
   live `baseline.json` sha unchanged (cmd 23), opencode log untouched (cmd 22), no temp
   dirs leaked by `--self-test` (cmd 19), deterministic byte-identical stdout in text and
   JSON modes (cmds 8/20).
7. **Residual, not a draft defect**: exit 3 now spans two different repair actions —
   "baseline file wrong" (a/b/missing) and "a pin value inside it is wrong"
   (x-mtime-int, x-garbage-mtime; canonical/P6 used 2 for the latter, `garbage` case).
   The message names the pin, so the diagnosis is honest; the code alone is not
   discriminating (D-V4-3, info).

  schema, same four files → 0/1/1/1, tb=0 (cmd 7).

  non-dict `measured_against` → exit 3 (`/tmp/d23/V4/check_substrate_pins.py:163`) while
  round-23's claim letter (e) mandates 1 for the missing/null case only
  (`.ufo/round-23/claims.json`, claim P `after`; M6-D2). Evidence: cmd 7 rows
  `d-ma-list/string/int/bool` exit 3 vs `d-ma-null` exit 1. Either choice is defensible;
  the record here is that the draft was *not* forced into a single rule by the claim text.
- **D-V4-3 (S4 minor)** — exit 3 conflates "baseline file malformed" with "one pin value
  malformed": `:91` raises `BaselineError` (→3) for a non-string pin, and `:106` for an
  unparseable ISO pin. Evidence: cmd 7 `x-mtime-int` → 3; cmd 12 `'garbage'` mtime → 3;

  Diagnosis names the pin, so this is a code-granularity remark, not a correctness bug.

  guard exits 0 (P6's "silent coverage boundary", reproduced by code reading, not probed
  here — see Limits). The `KNOWN_PINS` tuple adds presence enforcement for today's three
  pins only, not a registry extension hook.
- **Positive controls that must survive the landing merge** (all re-verified this lane):
