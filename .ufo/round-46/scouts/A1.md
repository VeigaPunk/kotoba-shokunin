# A1 — adjudicate live-JSON producer trust

## Ruling

Split **provenance** from **internal consistency**. Under the comparator’s current contract, a caller-supplied `--live-json` file is trusted as the live producer’s captured output; the comparator does not authenticate who created it. Therefore an altered, single-source `mode` or `verdict` is a producer-input trust failure, not proof that the ordinary live producer emits bad data. The receipt hashes the exact bytes consumed, but a digest is not producer provenance.

Do not extend that boundary to contradictory copies. If an input supplies multiple row channels, decision-bearing metadata (`mode` and `verdict`) should agree across them, just as values do. The producer’s top-level `observed` object is also a real redundant view of row observations and should be reconciled for overlapping checks. A literal top-level `summary` is not emitted by the producer; reject it as outside the producer shape rather than treating it as an authoritative summary.

Thus C2 should classify a forged lone mode/verdict as caller-selected live-input trust, but keep conflicting row-channel metadata and a contradictory top-level observed projection as consistency work. Do not declare the entire “mode/verdict/summary shadow” class trusted: it mixes sole-source producer claims with mismatching copies.

## Contract versus producer emission

The comparator says it is source-blind and “only transports both instruments’ own outputs” (`verifiers/compare_harness_independent.py:11-15`). Its mode-aware protocol explicitly reads `mode` from the live payload (`:41-50`); `parse_live` takes observed values, verdicts, and modes from records (`:569-595`); the exit decision treats any live verdict other than `PASS` as failure (`:1069-1075`). For file input, `build_meta` reads `--live-json` and assigns `live_exit = 0` (`:2139-2153`). The receipt contract records input bytes and hashes, not their author (`:93-104`). These clauses make mode/verdict operative producer claims, but do not authenticate a supplied file.

There is a contract/emission mismatch worth preserving in the ruling: the channel paragraph says the live instrument publishes `results`, `rows`, and a dotted `checks` map (`:29-39`), while the producer’s actual `--json` branch prints `{"observed": observed, "results": results}` (`verifiers/verify_harness_claims.py:648-660`). `evaluate` adds `mode`, `observed`, `expected`, and `verdict` to each result row (`:522-579`); the top-level `observed` object is the separate aggregate view. It emits no top-level `summary`. The channel paragraph should not be used as evidence that normal live output contains duplicated `rows`/`checks` channels.
