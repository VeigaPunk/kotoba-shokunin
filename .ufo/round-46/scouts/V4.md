# V4 — verify-livejson-boundary

## Finding

The real `verify_harness_claims.py --json` producer **does emit `mode` and `verdict` on each `results` row**; those are not fields the comparator invented. Its top-level keys are only `observed` and `results`. There is no top-level `mode`, `verdict`, or `summary`, and no row-level `summary`.

The captured `observed` top-level value is a nested `{ "omp": ..., "opencode": ... }` observation object. The 28 `results` rows each have exactly `check`, `expected`, `mode`, `observed`, and `verdict`. In the captured run, all 28 verdicts were `PASS`; row modes counted 17 `equal`, 10 `zero`, and 1 `positive`.

The comparator's live parser selects a `results`/`rows`/`checks` record list and reads each row's `observed`, string `mode`, and string `verdict` (`compare_harness_independent.py:274-283, 580-595`). It does not read the producer's top-level `observed` object or any top-level `mode`, `verdict`, or `summary`. The comparator's own `--json` report has its own `headline`/`agreement` summary; that is a different output contract from the producer's live JSON.

Important boundary: with `--live-json`, the comparator reads the caller-selected file directly and sets its input exit to 0; it does not rerun the live producer (`compare_harness_independent.py:2185-2198`). Thus a top-level `summary`/`mode`/`verdict` shadow is not a producer field the comparator consumes (it is ignored, not rejected), while row-level `mode`/`verdict` are genuine producer fields that the comparator trusts from the supplied bytes. This confirms the normal producer contract; it does **not** prove a caller-supplied row cannot be altered or establish producer provenance. No mutated-payload arms were run by this seat.
