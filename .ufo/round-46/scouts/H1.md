# H1 — live-JSON producer trust boundary

## Finding

The comparator does not authenticate a live producer. The registered baseline trusts the row's `observed` and `mode` as caller-supplied inputs and does not reconcile the live `verdict` or top-level `observed` summary with those rows. Its documentation describes value/status agreement among published row channels, but does not define a contract for `modes`, `verdicts`, or `summary_paths` shadows.

The tested uncommitted candidate snapshot adds and documents a narrower consistency contract: a full producer payload must carry `modes`, `verdicts`, and `summary_paths`, and one-copy edits that contradict the rows fail closed. The current producer emits those mirrors and its fresh payload passes. The candidate explicitly says this is **not provenance authentication**. A caller can still coherently rewrite inputs; moreover, the candidate does not bind `summary_paths` to the canonical field for a check. The decoy-path probe below preserved exit 0 while the actual `observed.omp.template_bytes` summary disagreed with the row. So the caller contract exists in the candidate for copy-consistency, not for authenticity or canonical summary-path meaning.

## Live JSON trust map

The distinction is whether the comparator checks consistency between copies or independently recomputes/authenticates the value. In `--live-json` mode, none of the live measurements is re-derived from the host.

- **`results` / `rows` / `checks` records and IDs:** all published row channels are parsed and their IDs, `observed` values, and available status fields are reconciled. Conflicting ID aliases are rejected. This catches contradictory row copies (exit 2), but the row `observed` itself remains the live value supplied to the join. `parse_live` uses the first record channel after reconciliation (`current-comparator-snapshot.py:659-678`).
- **Row `mode` and top-level `modes`:** for full producer payloads, the candidate requires a check-keyed map with exactly the row IDs and requires each row's string mode to match it in every channel (`:602-641`). The row mode is what `parse_live` returns and `compare` uses; the map is a mirror, not an independently sourced rule (`:659-678`, `:701-723`). The predicate implementation supports `equal`, `zero`, and `positive`; an unknown mode is un-adjudicated and fails, but supported modes are not authenticated against the producer's `CHECKS` table. A coherent change from `equal` to `positive` can change the join result.
- **Row `verdict` and top-level `verdicts`:** the candidate requires the same exact-key/string/mirror consistency checks as for modes (`:602-641`). The row verdicts feed the exit gate; non-`PASS` yields exit 3 after the join (`:1131-1165`). They are not recomputed from the live observation or baseline. Coherent forgery is still caller-authored data.
- **Top-level `observed` and `summary_paths`:** if `observed` contains `omp` or `opencode`, the candidate treats it as a full producer payload and requires all three mirror maps (`:591-606`). `summary_paths` must cover the row IDs; each path must be a two-string path rooted at `omp` or `opencode`, exist in the summary, and equal the row's `observed` (`:643-656`). This verifies the caller-selected path's value, not that the path is the canonical extractor for that check. It does not re-run the observation logic.
- **Live row `expected`:** it is not the main join value. `build_meta` reads it only for the secondary informational count; the join uses live `observed` against independent-derived values (`current-comparator-snapshot.py:2405-2412`).
- **`--live-json` provenance and receipts:** `build_meta` assigns `live_exit = 0` when reading a file and hashes the exact input for the receipt; it does not verify that a named producer generated it (`:2331-2344`). The receipt is an input digest, not a producer signature or attestation. The pinned candidate snapshot documentation states this limit directly (`:41-50`).

The live producer currently constructs `observed`, `results`, `modes`, `verdicts`, and `summary_paths` together (`verifiers/verify_harness_claims.py:658-668`). That producer implementation is evidence of the standard schema, not a trust anchor for a separate caller-supplied JSON file.

## Contract decision and limits

At the registered baseline, callers had no documented contract for the `mode`/`verdict`/summary shadows beyond row-channel value reconciliation. In the pinned candidate snapshot, callers do have an explicit documented contract for *consistency*: full producer payloads carry `modes`, `verdicts`, and `summary_paths`, and contradictory copies fail closed. The documentation also explicitly leaves producer identity and coherent fabrication untrusted. Therefore the candidate bounds the old one-field false-green, but does not turn `--live-json` into authenticated evidence. The decoy-path result is an additional gap between a generic “summary path matches the row” check and a canonical per-check path contract.

If canonical summary correspondence is a requirement, derive the allowed path from a trusted check-to-extractor mapping (rather than the payload's `summary_paths`) and probe a forged alternate path. Otherwise the docs should state plainly that the caller chooses a path and the comparator checks only its self-consistency. This report is evidence, not an implementation change. It did not run duplicate-raw-JSON-member probes, comparator self-test, floors guard, or corpus gates; it makes no claim about those gates or the sibling C2b duplicate-member door. No product comparator, producer, scope, fixture, registry, or Git state was changed by this seat.
