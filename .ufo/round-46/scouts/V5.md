# V5 — duplicate JSON-member detection

**Finding:** On the frozen comparator, duplicate object members are silently decoded last-member-wins; the parser does not reject duplicates and has no duplicate-aware strict-mode switch. The shared worktree snapshot tested later in this report rejects duplicate members with named exit 2, including scope-file JSON. This is parser behavior under synthetic raw-byte inputs, not a claim that the normal producers emit duplicate members.

## Parser interpretation

The frozen source uses ordinary `json.loads()` in both `extract_json()` paths (`:207-243`) and in `load_scope_file()` (`:792-800`), with no duplicate-pair hook. Its `--strict-headline` option changes comparison strictness only: the duplicate-top-level-results arm still exits 0 under it. `--strict-json` is not a recognized CLI option.

At the tested worktree SHA, `_unique_json_object()` raises `DuplicateJSONMemberError` (`verifiers/compare_harness_independent.py:159-171`); `extract_json()` applies it to both whole-text and balanced-object parsing (`:233-271`), `load_payload()` names the error (`:690-697`), and `load_scope_file()` applies the same hook (`:886-903`). Thus current candidate behavior is strict-by-default across the tested payload and scope-file surfaces, not an opt-in strict JSON mode.
