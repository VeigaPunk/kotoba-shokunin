## 5. The volatility hazard (`--prefer-online` + path pinning)

- **H1 — refresh mutates in place.** Wrapper `:40` passes `--prefer-online` on **every** invocation; npm docs: "staleness checks for cached data will be forced, making the CLI look for updates immediately even for fresh package data" (`.../npm/docs/content/using-npm/config.md:1525-1533`; `docs/content/commands/npm-exec.md:320-322`). The npx dir is keyed only by the spec string (`libnpmexec/lib/index.js:250-262`), so a new 1.x reifies into the **same** `e2094862b59aac7b` and replaces the bytes at the pinned path.
- **Observed refresh.** Packument cache entries: full fetch `2026-10-20T21:33:39.780Z` (install run, 2.7 s before the files), abridged fetches `2026-10-21T15:30:20.401Z` and `.594Z`; the cache dir mtime is `12:30:20.635 -0300` = `15:30:20.635Z` — 235 ms after the refetch, same second — with no file newer than Oct 20. A wrapper/npx invocation at 12:30 local (not this lane) revalidated the packument and touched the dir. Contents did not change only because `latest` was already 1.19.3; on the next 1.x publish they would.
- **H2 — spec changes move the path.** `sha512("opencode-ai@1.19.3")[:16] = 3043e87e1f9e3343` (computed). Changing the wrapper's package spec, or moving to `@opencode/cli`, silently yields a different dir; a path pin then points at nothing.
- **H3 — the cache is disposable.** `_npx` prune / `npm cache clean` removes the path with no version change. Precedent this round: `~/.opencode/bin/opencode` vanished by channel removal and the default gates went `UNREADABLE` / exit 2.
- **H4 — absence is diagnosed unevenly.** `check_substrate_pins.py` → `UNREADABLE` exit 2; `verify_surfaces.py` → `EnvError` exit 2; `verify_harness_claims.py:477-478` guards `if binary.is_file()` and leaves `builtin=0` otherwise, so a dead pin degrades a count instead of naming the missing substrate [INFERENCE: contributes to the 21/28 at BASE].
- **H5 — execution side effects.** Any gate or human that runs the wrapper triggers the npx refresh and, on real runs, writes `~/.local/share/opencode/log/opencode.log` — the observation surface of `verify_harness_claims.py:54`. `check_substrate_pins.py`'s "never executes a pinned binary" contract must be preserved. npm's postinstall itself executes `opencode --version` (`postinstall.mjs` `verifyBinary`), so installs are not inert either.

**Implications for the C1 re-pin:**

- Pin the **bytes**, not the channel: use `/fast/scratch/kotoba-r47/shared/bin/opencode-1.19.3` (or `--opencode-strings` on the frozen dump) and set `opencode_binary_sha256 = 179ca421…`.
- If the npx path must be the default, pin version + sha and document the sha as ephemeral; never pin `~/.local/bin/opencode` (a 1.4 KB bash script) as the substrate.
- Do **not** discriminate by BuildID: the round-8 1.18.x binary and 1.19.3 share BuildID `c30f169b…` (`corpus/knowledge/opencode-offer-trace-round8.md:6`); v2 alone has `5afca266…`.
- Root fix (outside this lane's write scope): make `package="opencode-ai@1.19.3"` in the wrapper, or drop the `:40` refresh, so the cache dir becomes version-keyed and `--prefer-online` cannot upgrade it. Report to the operator.

## 8. Counterexamples and open points

- BuildID does not identify the version: 1.18.x and 1.19.3 share `c30f169b…`.
- No host copy of the 2.0.26 ELF remains, so the old pin is re-established only through npm tarball identity, not through host bytes.
- The 1.19.3 binary contains "OpenCode 2.0" upgrade UI text; that is evidence the v1 CLI knows v2 as a separate major install, not proof of what happened on this host.
- The log has no 1.19.3 `cli starting` lines even though `postinstall.mjs` ran `opencode --version` at install time; where v1 logs (or whether `--version` initializes logging) is unresolved.
- The wrapper uses mise's npx (26.12.0 / npm 11.20.0); `command -v npx` in my shell resolved fnm's node v24.21.0. Two npm installations exist; the wrapper forces mise's.
- `npm`'s `latest` could not have moved during measurement: `latest=1.19.3` both in the cached packument and live. The 12:30 refresh therefore changed only metadata, not the installed tree.
