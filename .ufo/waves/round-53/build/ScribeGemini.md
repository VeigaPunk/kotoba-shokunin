## 2. Answers

### 2.1 Which always-on file names it reads

- **Default: one name, `GEMINI.md`.** `docs/cli/gemini-md.md:3` — "Context files, which use the default name `GEMINI.md`, are a powerful feature". Source: `DEFAULT_CONTEXT_FILENAME = 'GEMINI.md'` (`memoryTool.ts:11`), and the default is a single string (`memoryTool.ts:16`).
- **The name is replaceable by one name or a list** via `context.fileName`. `gemini-md.md:96-98` — "To specify a different name or a list of names, use the `context.fileName` property." The page's example is `gemini-md.md:105` — `"fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"]`. The settings reference types it as string or string array, `configuration.md:1697-1698` — "The name of the context file or files to load into memory. Accepts either a single string or an array of strings." — with `**Default:** `undefined`` at `:1699`.
- **`AGENTS.md` is read only when configured.** Repo-wide at the pin, `git grep -n -I 'AGENTS\.md' 451a02f -- docs packages` returns exactly two hits: the example list at `docs/cli/gemini-md.md:105` and a test fixture name `'CUSTOM_AGENTS.md'` (`packages/core/src/config/config.test.ts:1089`). There is no fallback: with the default configuration a repository's `AGENTS.md` is not a context file.
- **`CLAUDE.md` is not named at all.** `git grep -n -I 'CLAUDE\.md' 451a02f -- docs packages` → 0 hits. It can only be read if a user lists it in `context.fileName`; it is not a default and the docs never mention it.
- **Other names in the docs:** `CONTEXT.md` appears only inside that same example list (`:105`). `MEMORY.md` appears nowhere in `docs/`; it is an internal constant, `PROJECT_MEMORY_INDEX_FILENAME = 'MEMORY.md'` (`memoryTool.ts:12`), used as the preferred project-memory index in the project-memory directory with a fallback to the legacy context-name files (`memoryDiscovery.ts:342-380`). It is adjacent machinery, not a repo always-on rule file.
- **Where they are read from** (`gemini-md.md:13-36`): global `~/.gemini/GEMINI.md`; workspace directories and their parents; and just-in-time scanning of a directory and its ancestors when a tool touches a file. All found content is sent with every prompt — `gemini-md.md:13-15`: "It loads various context files from several locations, concatenates the contents of all found files, and sends them to the model with every prompt."

### 2.2 What it does when two of them exist in one directory

Three distinct cases, and only one of them is documented:

1. **Only the default is configured** (the normal case): a second file with another name in the same directory is not a context file. The loader enumerates configured names only (`memoryDiscovery.ts:470` `getAllGeminiMdFilenames()`; `:463` `findUpwardGeminiFiles`), so `AGENTS.md` beside `GEMINI.md` is invisible.
2. **Both names are configured and both files exist: both load, neither wins.** The loader checks every configured name in the directory (`memoryDiscovery.ts:485-494`) and the collected path list is returned sorted — `memoryDiscovery.ts:430` `return unique.sort();`. The test named "should keep multiple memory files from the same directory adjacent and in order" (`memoryDiscovery.test.ts:370`) configures `['PRIMARY.md', 'SECONDARY.md']`, plants both and `expect(result).toHaveLength(2)` (`:390`). The source comment states the grouping, `memoryDiscovery.ts:460-461` — "Files are ordered by directory level (root to leaf), with all filename variants grouped together per directory." Because the list is string-sorted, the order inside one directory is filename order, not the order of the `context.fileName` array (the global-directory list is the exception: it is returned in configured order, `memoryDiscovery.ts:318-332`).
3. **The two names are one physical file** (symlink, hard link, case variant on a case-insensitive filesystem): deduplicated by device and inode, `memoryDiscovery.ts:47-49` — "Deduplicates file paths by file identity (device + inode) rather than string path." — so only the first path is kept.

The docs state no rule for case 2 or 3: `grep -iE 'both .*(files?|exist)|duplicate|same content'` over `gemini-md.md`, `configuration.md` and `memport.md` returns nothing. Case 2 is sourced from the code and its test only.

### 2.3 Does it honour a redirect

- **Config pointing at another name — yes, documented.** `context.fileName` (above). This is the only redirect the docs name explicitly.
- **`@AGENTS.md` import — the mechanism is documented, the AGENTS.md example is not.** `gemini-md.md:73-75` — "importing content from other files using the `@file.md` syntax. This feature supports both relative and absolute paths." Imports are processed on read, before concatenation (`memoryDiscovery.ts:223-232` calls `processImports`), so an `@AGENTS.md` line inside `GEMINI.md` pulls that file's bytes in. Rendering: the default `tree` format wraps the imported text in `<!-- Imported from: AGENTS.md -->` … `<!-- End of import from: AGENTS.md -->` (`memoryImportProcessor.ts:365`); a failed target leaves `<!-- Import failed: AGENTS.md - <message> -->` (`:375`) and does not abort the load. Recursion stops at depth 5 (`:196`; docs `memport.md:101-102`), and an import outside the allowed directories is refused with a path-traversal comment (`:337`), consistent with `memport.md:95-97` — "The `validateImportPath` function ensures that imports are only allowed from specified directories".
  - Format caveat, code-only: `context.importFormat` has no documented default (`configuration.md:1703-1704` `**Default:** `undefined``), the code defaults it to `'tree'` (`config.ts:1271` `this.importFormat = params.importFormat ?? 'tree';`). Under `'flat'` a failed import is silently dropped — no comment, a debug-only log line (`memoryImportProcessor.ts:290`), the `@path` token stays in the text (flat branch `:223-313`, catch `:284-293`) — so the documented "error comment" (`memport.md:108-109`) holds only for the default format.
- **Symlink — not documented, and no docs text anywhere mentions symlinks for context files.** `grep -rn -i 'symlink\|symbolic link' docs --include='*.md'` returns only skills `link`, extension `link` and npm install hits. The loader reaches the file through `fs.access`/`fs.readFile` on the configured name (`memoryDiscovery.ts:485-494`, `:223`), which follows a symlink [INFERENCE — Node fs semantics; no test in the tree covers a symlinked context file]. If both a symlinked `GEMINI.md` and its real `AGENTS.md` are configured, the inode dedupe of case 3 means one of them is read.

### 2.4 Documented size limit

- **No per-file byte or token limit is documented for context files.** `grep -iE 'size limit|maximum (file )?size|[0-9]+ ?(KB|MB|bytes)'` over `gemini-md.md`, `memport.md` and `configuration.md` returns nothing. The tutorial only advises brevity, `memory-management.md:112-113` — "Keep it focused: Avoid adding excessive content to `GEMINI.md`."
- **Documented numeric caps are breadth caps, not file caps:** 200 directories for discovery (`configuration.md:1714-1715` — "Maximum number of directories to search for memory." — `**Default:** `200``) and the import recursion depth of 5 (`memport.md:101-102`).
- **Code corroboration:** `readGeminiMdFiles` reads each file with no size check (`memoryDiscovery.ts:223`). A 20 MB cap exists in the tool file-read path (`packages/core/src/utils/constants.ts:12` `MAX_FILE_SIZE_MB = 20`; enforced at `packages/core/src/utils/fileUtils.ts:604`), and the context loader does not use it [INFERENCE from the absence of any size test in the loader path].
