Mechanism (why it is dead today): `verifiers/verify_corpus_integrity.py:273–279`
`report_pointer_exists()` resolves filesystem paths only and grants the fleet fallback only to a token
that `startswith(".ufo/reports/")`; the matched token includes the `HEAD:` revision prefix
(`UFO_POINTER_RE`, line 146–148, lets `[^\s`\"]*?` absorb `HEAD:`), so both arms miss. `git cat-file`
is never consulted.

### Why the gate-side change is in-lane, and already designed

- The object **does** resolve in the fleet, measured now:
  `git -C /home/vgpnk/Projects/shokunin cat-file -e HEAD:.ufo/reports/round-77/kotoba.md` → **rc 0**;
  the lane does not carry the path (`-C kotoba-shokunin … cat-file -e` → **rc 128**), so the citing-repo-then-fleet
  order is exactly what is needed.
- The content-identity arm R1 declares is satisfied by the resolved bytes, measured:
  `git show HEAD:.ufo/reports/round-77/kotoba.md` → **8547 B**, `## SHONEN` occurrences **1** (≥400 B,
  heading present).
- The resolution branch is already written and tracked at base:
  `.ufo/waves/round-80/build/Kb80E04DeadPointer.patch` adds, in `report_pointer_exists()`, a
  `<rev>:<path>` arm — `head, _, rest = token.partition(":")`; if `rest.startswith(".ufo/reports/")`,
  `git cat-file -e <token>` in the citing repo's repository root, else in the fleet root — and adds the
  self-test arm `pointer/rev/dead` asserting `HEAD:.ufo/reports/round-53/kotoba.md` resolves while
  `nosuchrev:…` and a missing path stay dead. R1 strengthens that design with the content-identity
  check; it does not need a new convention.
- `PROTOCOL.md:383` leaves the gate's vocabulary to the lane; `PROTOCOL.md:370` only requires pins to
  be persisted in-repo. No operator-owned file changes under either disposition.

### Residual, and where it belongs

`HEAD` is a moving ref: a `HEAD:<path>` citation promises the path at whatever the fleet's HEAD is when
the gate runs, so a later fleet deletion or rename can re-dead a lane-committed citation through no
lane act. That is a citation-quality question already governed by the lane's own rule set
(`corpus/QUALITY.md` Q60: "An artifact cited with a revision must exist at that revision … The check is
`git cat-file -e <rev>:<path>`"), which does not yet say whether a moving ref qualifies. The lane can
extend Q60 itself (admit `<rev>:<path>` for closure-written, uneditable corpus files and require the
content-identity arm to hold at read time; otherwise prefer a bare fleet path). No operator input is
required, and nothing in round 81 depends on the answer — R1 closes the token either way.
