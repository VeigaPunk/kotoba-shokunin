## Counterexample / findings

1. **Q70 is bypassed when the pinned snapshot has no heading.** The frozen rule requires the quote after the first heading. `quote_location` only rejects the initial heading block under `if first_head is not None`; with no headings, any quote is accepted. Synthetic isolated fixture I: headingless snapshot containing only `The allowedTools option appears in this unrelated example for formatting only.` at view line 0 returned exit 0, `sdk allowed-tools surface documented 1 of 1`, and all conjuncts green. This combines the positional bypass with the counter's semantic weakness: a token-bearing quote unrelated to the claimed second grant channel is enough. The non-headingless version of this unrelated quote also reached 1/1 in fixture E.

   **Smallest correction:** require `heads` to be nonempty, then require the quote's first line index to be strictly after the first heading block; also require the quote to evidence the claimed grant statement, or mark the counter as strictly documentary-form evidence and keep semantic adjudication outside the count. The existing S249 page has headings, so this does not narrow its valid evidence.

2. **S249 anchor identity is looser than the plan's path claim.** `snapshot_named` is `SNAPSHOT_PATH in text or Path(SNAPSHOT_PATH).name in text`; fixture G replaced the anchor path with `unrelated/S249.md.bak`, kept the valid digest and got exit 0 / 1 of 1. Fixture F changed the anchor's fetched date to 1970 and byte count to 1 while preserving HTTP 200 and the correct digest; it also got exit 0 / 1 of 1. The anchor check compares only captured sha256 (counter lines 516–530). The optional fetch JSON checks byte counts, but does not bind these anchor fields.

   **Smallest correction:** parse the anchor as structured fields; require the exact snapshot path, actual snapshot byte length, expected capture date, and digest. Do not accept an expected basename as an arbitrary substring.

3. **Fetch record URL/status are not bound.** Fixture H set `S249.fetch.json` to an unrelated URL with HTTP 200, correct fixture digest and correct size; it passed 1/1. `_fetch_record_pin` recursively reads digest/size keys only; it never verifies `url`, `final_url`, or HTTP status. The page/SHA binding itself is location- and content-bound: fixture A, moving the snapshot away from the frozen path, exited 2; the self-test pin-mismatch arm also rejects changed bytes. Fixture D's unrelated page bytes passed only after rebinding the in-file pin to those bytes, so D does **not** establish a bypass against the frozen S249 pin; it does show the pin is the authority and URL provenance remains an external evidence claim.

   **Smallest correction:** when the fetch JSON exists, require its requested/final URL to equal the canonical URL and its HTTP field to be 200, in addition to matching digest and size.

4. **Requested worlds that are correctly handled:** B (S249 updated while S248 `used-by` remains `—`) exited 1 on conjunct (e); C (quote before first heading with coherent fixture pin) exited 1 on Q70. The fixed snapshot location is indeed location-bound; it is not a content-only movable pin. The self-test ran 47 worlds / 138 assertions with 0 failures.

## Entry semantic attack (E08 draft)

The draft correctly separates the hyphenated skill-file `allowed-tools` key from query-config `allowedTools`/`allowed_tools` (lines 38–39, 53–55), so it does **not** literally mislabel the query option as frontmatter. But line 47 overstates the page's restriction semantics: “the option absent from the skill file is the one that removes tools from view.” The cited raw 108 says the `skills` list removes *unlisted skills* from the model's view and rejects invocation through the Skill tool; it does not remove tools from view. This conflates restricting which skills are available with restricting the tool set. Also, the query option is session/query configuration, not a per-skill frontmatter field; the entry should explicitly say it is session-level and avoid describing it as per-skill scope just because the page's sentence says “for a project or personal skill.”

**Smallest correction:** change line 47 to say the `skills` option filters skill availability/invocation, not tools; state that the page does not establish per-skill scoping for the query-level `allowedTools` grant. Preserve the valid distinction between file frontmatter and query configuration.
