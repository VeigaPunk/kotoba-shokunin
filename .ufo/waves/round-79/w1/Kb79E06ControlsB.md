## Findings

**1. LOUD — WB5 is a gate-level false green inside the frozen battery (`check_gate_registry.py`).** Not a `6 of 6` breach, but the battery counts this gate: the green is unearned and no guard touches it. Two rows in `SKILL.md` lift the gate from `60 of 62` (exit 1) to `62 of 62` (exit 0) while the registry's own claim — "this verifier is run by this command" — is false: the commands run `check_r68_routed_repairs.py` and `check_r69_routed_repairs_v2.py`. Mechanism, from the gate's bytes: `judge_row` tests `if path not in r[2]` (substring test on the entry-command cell, `verifiers/check_gate_registry.py:183-184`), so a shell comment satisfies it; the `--self-test` and `in-file` cells are then satisfied by the *real* verifier's own source, which does have an exact `add_argument("--self-test")` (`:78-91`, AST walk over the file named by the **name** cell, not by the entry command). The registry gate therefore never executes or even reads the command it certifies. This is a *pre-existing lane gate* defect, reported as such (not repaired here — out of my write scope; the repair belongs to the L1 when the C1 repair set is chosen). World bytes: `build/Kb79E06ControlsB.WB5.patch`, commit `6ebcbe5aafdaaa98f40efebe3fa1e4e543bc733e`.

**2. LOUD — WB4a: the spot-check guard is scoped to the **round-73 base** blobs only, so every spot-check file written since (rounds 73–78) is editable and deletable with no guard hit.** Evidence: `spotcheck-identity` compares `_spotcheck_shas(clone, BASE)` to `_spotcheck_shas(clone, rev)` and reports only base paths (`verifiers/check_tip_battery.py:322-331`; `_spotcheck_shas` at `:231-241`); extra rev-side files produce an `INFO` line, never a failure. Sweep for readers of those files among the lane verifiers (`grep -rln 'verifier-spotcheck\|SPOTCHECK' verifiers/`): `check_r63/r66/r67/r68/r69/r69_v2/r75_routed_repairs.py`, `check_routed_repairs.py`, `check_seat_counts.py`, `check_skill_evals_v2.py`, `check_tip_battery.py`, `corpus-baseline.json`, `verify_corpus_integrity.py` — **none of them is one of the six battery gates except `check_tip_battery.py` itself and `verify_corpus_integrity.py` (whose only mention of the spot-check files is a comment at `:591`; it inventories corpus files and never hashes a spot-check body)**. Measured: the world moves nothing (`guards 5 of 5`, `1 of 6`, exit 1). Deleting such a file is equally unguarded, since `no-deletions` only enumerates **base** paths (`:255-257`).

**3. WB1/WB2 confirm the pins are the only thing standing between a gate and a gutting.** Both worlds make their gate read cleaner or green (WB1: `exit 0`) with a ≤1-line deletion inside an instrument; both are refused by `instrument-pin` alone (`guards 4 of 5`). Consequence for the C1 repair set (code-grounded, not a decision): **the six instruments cannot be edited at all** — `INSTRUMENT_PINS` accepts only base/pinned blobs, and 40-line caps do not even come into play. Every gate the battery runs must be made green from *data/tree* bytes.
