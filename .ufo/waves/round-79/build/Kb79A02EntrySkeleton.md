# `allowed-tools` in six clients: one field name, three value forms, four grant semantics

The lane's corpus names this frontmatter key twice and never says what a client does with it. Six pages opened on 2026-10-27 do state it, and they disagree on both halves of the field. The value form differs: a space-separated string in the open specification and a "space-delimited list" in Microsoft Agent Framework, a "space- or comma-separated string, or a YAML list" in Claude Code, and a YAML block sequence in the worked examples of Factory and Mistral Vibe, while pi's page prints the field with a one-line purpose and no form at all. The grant differs more sharply: Claude Code documents a per-turn permission pre-approval that expires with your next message and, in the same paragraph, says it "does not restrict which tools are available"; Factory documents review metadata that "does not add tools or sandbox standard skill invocation" and is explicitly "not a security boundary"; the specification, Microsoft Agent Framework and pi carry "pre-approved" together with "Experimental"; and Vibe's example writes the field without stating any semantics for it anywhere on the page.

Everything below is documentary: six pages fetched and pinned, no client installed, loaded, routed or refused. "Pre-approved", "does not add tools" and "Experimental" are the pages' own words, quoted from the snapshots, never observations of a runtime. The entry also records a page-internal tension rather than resolving it — Vibe says it follows the Agent Skills specification for format and then prints the list form the specification's own field table calls a space-separated string — because no page read here says which form Vibe parses.

**Three value forms under one name, and only one page states its tolerance.** The specification calls the value a space-separated string of tools (`S226-spec.md:176`); Claude Code is the only page that says which forms it accepts, and it accepts all three — "space- or comma-separated string, or a YAML list" (`S227-claude.md:404`). None of this is a parser test: no client was run, and a page that prints a form in an example has not said it rejects the other.

**The name promises restriction; four pages do not grant it.** Claude Code states the negative in the same paragraph as the grant: the field pre-approves during one turn and "does not restrict which tools are available: every tool remains callable" (`S227-claude.md:617`). ## What an author should do

- **Treat the field as pre-approval, never as a sandbox.** Claude Code grants it for one turn and then clears it, and says it "does not restrict which tools are available" (`S227-claude.md:617`); Factory says it "does not add tools or sandbox standard skill invocation" and is "not a security boundary" (`S228-factory.md:254`, `:298`). A workflow that needs a tool absent from the session is not fixed by listing it (Factory, `:282`).
- **Put the restriction where the page puts it.** Claude Code's `disallowed-tools` plus permission settings (`S227-claude.md:405`, `:632`); Vibe's `disabled_tools`, per-tool `permission` and `[tools.read_file] allowlist` (`S231-vibe.md:969`, `:972-976`, `:1039-1040`). Listing a tool in `allowed-tools` and expecting the rest to be blocked is contradicted by the first page and unsupported by the other five.
- **Write the form the target page prints, and prefer the scalar.** The specification's space-separated string (`S226-spec.md:182`) is what Microsoft Agent Framework's bytes call a scalar, and that page says a collection where a scalar is expected prevents loading (`S229-msaf.html:825`); the list form is what Factory and Vibe print in their examples (`S228-factory.md:235-238`, `S231-vibe.md:725-728`) and what Claude Code says it also accepts (`S227-claude.md:404`). Choose per client, and do not assume the list form travels.
- **Budget for one turn, not one session, on Claude Code.** The grant clears when you send your next message, and the page names permission settings for a session-wide allow rule (`S227-claude.md:617`); a skill that needs standing approval is relying on the wrong mechanism.
- **If the skill ships to claude.ai or the Skills API, keep the frontmatter to the specification's six fields.** `allowed-tools` survives that path; every other Claude Code-only key hard-errors (`S227-claude.md:421-432`).
