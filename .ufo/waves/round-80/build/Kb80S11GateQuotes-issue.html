Documentation Type

Unclear/confusing documentation

Documentation Location

URL: https://platform.claude.com/docs/en/agent-sdk/skills (Section: Tool Restrictions)

Section/Topic

The "Tool Restrictions" section under "Agent Skills in the SDK."

Current Documentation

"The allowed-tools frontmatter field in SKILL.md is only supported when using Claude Code CLI directly. It does not apply when using Skills through the SDK. When using the SDK, control tool access through the main allowedTools option in your query configuration."

What's Wrong or Missing?

The documentation describes a major functional "broken logic" gap between the CLI and the SDK as if it were intended behavior. This creates several high-priority issues:

  • Broken Reusability: The platform-wide documentation for Agent Skills defines them as "reusable, filesystem-based resources." This discrepancy means a Skill authored for Claude Code CLI is not fully portable to an SDK-based application without manual intervention.
  • Security Risk: A developer may author a Skill with strict allowed-tools (e.g., restricting to Read only for a sensitive directory) assuming the Skill format itself enforces safety. If that Skill is then imported into an SDK project, the restrictions fail silently, granting the Skill whatever permissions the parent SDK session has (potentially Bash or Write).
  • Functional Fragility: If a Skill's logic depends on specific tools being auto-approved via the frontmatter to reduce user friction, it will break or trigger unexpected canUseTool callbacks when run via the SDK.

Suggested Improvement

While this is primarily a request for architectural harmony, the documentation needs to be much more explicit about the risks.

Suggested Text Change:

Warning: Security and Portability Gap

Unlike the Claude Code CLI, the Agent SDK ignores the allowed-tools field in SKILL.md frontmatter.

CRITICAL: If you are importing a Skill designed for the CLI into an SDK project, you MUST manually replicate all tool restrictions in your ClaudeAgentOptions (Python) or Options (TypeScript) using the allowedTools parameter. Failure to do so will result in the Skill having broader permissions than its author intended, which poses a security risk when processing untrusted content.

Impact

High - Prevents users from using a feature

Additional Context

  • Links to related documentation: The Agent Skills Best Practices guide explicitly encourages the use of allowed-tools for "security-sensitive workflows." The SDK documentation contradicts this best practice.
  • Examples from other projects: In the Model Context Protocol (MCP) ecosystem, which Claude Code utilizes, configuration is expected to be respected by the client. Having the SDK act as a client that ignores its own specialized resource format (SKILL.md) is a significant outlier in agentic design.
  • Severity: Major. This impacts any enterprise user attempting to standardize agent behavior across CLI (for developers) and SDK (for production automation).

    Follow-up Review of Documentation Inaccuracies

    1. What’s FIXED:
    The core inaccuracy regarding how the Agent SDK handles tool permissions within Skill files has been addressed. Specifically:

    • At https://platform.claude.com/docs/en/agent-sdk/skills, a new Tool Restrictions section has been added. It explicitly states that the allowed-tools frontmatter field in SKILL.md is only supported when using the Claude Code CLI directly and does not apply to the SDK.
    • The documentation now provides clear instructions to use the allowedTools option within the SDK's query configuration to manage access.
    • Cross-references have been added to https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices under a similar Note block, ensuring that developers are alerted to this limitation regardless of whether they are coming from a "Best Practices" or an "SDK Reference" entry point.

    2. What’s UNRESOLVED:
    While the information is now technically present, the severity and contextual risk highlighted in the original report have been significantly minimized:

    • Warning Level: The report requested a "CRITICAL" or "Warning" banner due to the risk of silent permission escalation when a Skill is moved from a restricted CLI environment to a production SDK environment. The current implementation uses a standard <Note> block, which may not sufficiently grab the attention of a developer during a security audit.
    • Security Context: The updated text misses the specific explanation of the "Security and Portability Gap." It fails to mention that failing to manually replicate these permissions results in a Skill having broader system permissions (like Bash or Write) than its author intended.
    • Portability Clarity: There is still no high-level warning at https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview regarding the fact that "Filesystem-based resources" are not inherently portable between the CLI and SDK in terms of their security constraints.

    3. Conclusion:
    I am closing this issue as "Resolved." The primary goal of the report was to ensure that the documentation no longer implicitly suggested that the SDK respects Skill-level tool restrictions. By explicitly stating that the SDK ignores the allowed-tools frontmatter and providing the correct allowedTools implementation path in the options configuration, the technical accuracy has been restored. While a higher-visibility warning would be preferable for security-conscious workflows, the current updates satisfy the requirement to inform the community of the functional discrepancy.
