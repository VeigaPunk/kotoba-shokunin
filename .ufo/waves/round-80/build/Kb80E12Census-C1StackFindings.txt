So: **the bytes are right, the commit id is wrong.** S230's anchor asserts that pi-mono's `main`
resolved to a commit that is mistral-vibe's head and is not in pi-mono at all. The snapshot the row
pins is genuinely pi-mono's file at pi-mono's fetch-time head `bb65e3e4971…`; only the anchor's
commit id was copied from S231 (which correctly cites mistral-vibe's head). The row's own fetch record
(`S230.fetch.json`) carries the **correct** head, so the SOURCES.md anchor cell and its fetch record
disagree with each other — the Q62 "an anchor wrong" ground, not a content dispute.

Two consequences for the L1:

1. **The grammar class as published will mislabel it.** The S07 candidate derives the marker from the
   row's `raw.githubusercontent.com/badlogic/pi-mono/...` URL, so it reports
   `corpus/SOURCES.md:171: 7bb48f21… (repo badlogic/pi-mono)` — attributing mistral-vibe's commit to
   pi-mono. The gate's INFO class would therefore carry a wrong repository name, and the row's anchor
   would stay wrong underneath it. The class still clears the red (unresolvable 2 -> 0), but the
   reclassification must not be read as the corpus being correct.
2. **The anchor cannot be corrected in place.** `verifiers/check_sources_append_only.py` permits only
   `status`, `recheck` and `used-by` to change in a row (CORPUS rule 2); `anchor` is a protected cell.
   A correction is a **new supersede row** (plus the appended notice), never an in-place edit of
   S230's anchor.

**What this seat did NOT do:** it did not edit `corpus/SOURCES.md`'s S230/S231 anchor cells, did not
rewrite the r79 lesson, and did not add a supersede row — all of those are the L1's and the corpus
owners' calls, and the M45 append-only pattern forbids an in-place rewrite. The measurements above are
published so the L1 can decide with the evidence in hand.

## E. One more counter-side fact for E07 (the C2 counter seat)

The r79 draft counter's (c) conjunct requires the cited row's **anchor cell** to carry the literal
fetch record `fetched <ISO8601>Z, HTTP 200, <bytes> B, sha256 <hex>` (the draft's `FETCHED_RE`,
`.ufo/waves/round-80/build/check_allowed_tools.py:248-250`, read at `:962` via `row_[5]`). Measured
against the six C2 rows at base, that regex matches **none** of them:

    S226 anchor fetch-record: NO MATCH
    S227 anchor fetch-record: NO MATCH
    S228 anchor fetch-record: NO MATCH
    S229 anchor fetch-record: NO MATCH
    S230 anchor fetch-record: NO MATCH
    S231 anchor fetch-record: NO MATCH
    (cells with a fetch record: [] for all six)

The reason is textual, not substantive: the rows write `fetched 2026-10-27, HTTP 200, 7608 B,
sha256 \`9a67de89…\`` — a date without a time, and a **backticked, ellipsis-truncated** digest — while
the regex wants a full `YYYY-MM-DDTHH:MM:SSZ` and an unbackticked 64-hex digest. The rows' own
`S226.fetch.json` … `S231.fetch.json` records carry the full values (`fetched_utc`,
`sha256`), so the information is in the round-79 evidence but not in the shape the regex reads.

This is the C2 counter seat's call (the round-80 counter may read the fetch record from the snapshot
JSON rather than from the anchor cell), but the L1 should know that a (c) conjunct that reads the
anchor cell literally will read 0 of 6 on the committed rows. This seat's own 12 rows (S232-S243)
were written in the regex's shape (`fetched 2026-10-27T23:13:30Z, HTTP 200, <bytes> B, sha256
<64-hex>`, no backticks) so they do match — verified: the row generator asserts the shape and this
seat's rows are the reference example if the six C2 rows are ever re-shaped (which the append-only
rule forbids in place, so the fix would have to be in the counter's reader, not in the rows).
